## 1. 요구사항 ID 규칙

| 접두어 | 의미 |
|---|---|
| `REQ-F-0xx` | 서버 기능 요구사항 |
| `REQ-F-1xx` | 클라이언트 기능 요구사항 |
| `REQ-N-xxx` | 비기능 요구사항 (성능, 안정성, 사용성 등) |

- **우선순위**: 상(필수) / 중(가능하면 구현) / 하(추가 기능)
- **상태**: 미착수 / 진행중 / 완료 / 보류

## 2. 이해관계자 및 사용자

| 사용자 | 설명 |
|---|---|
| 일반 사용자 | 클라이언트로 접속해 메시지를 주고받는 사내 직원 |
| 관리자 | 서버를 실행하고 관리하는 사람 |

## 3. 핵심 개념: 메시지의 구성과 보관 위치

메시지는 **본문**과 **첨부파일**로 나누어 보관하고 전달한다. 실제 학교 사내 메신저를 사용하며 관찰한 동작을 바탕으로 정리했다.

| 구성 | 내용 | 서버 | 보낸 사람 PC | 받는 사람 PC |
|---|---|---|---|---|
| 본문 | 서식 있는 텍스트 (글자 크기·색 등) | 보관 (**90일**) | **보낸 내역**에 보관 | 접속 시 자동으로 받아 **받은 내역**에 보관 |
| 첨부파일 | 이미지, 문서 등 파일 | 보관 (**30일** 후 삭제) | 보관하지 않음 | 보관하지 않음 (링크를 눌러 내려받음) |

- 사용자 PC의 보낸 내역·받은 내역에는 **본문과 첨부파일 링크만** 남는다.
- 첨부파일 원본은 서버에만 있으며, 보관 기간이 지나면 링크가 **만료**로 표시된다.
- 사용자가 자기 PC에서 메시지를 지워도 서버나 상대방의 보관함에는 영향이 없다.

## 6. 사용 시나리오

### 시나리오 1: 오프라인 사용자에게 메시지 보내기
1. 사용자 A가 클라이언트로 서버에 접속한다.
2. A가 접속하지 않은 사용자 B에게 메시지를 보낸다.
3. 서버는 B가 오프라인이므로 메시지를 저장한다. A의 보낸 내역에 본문이 저장된다.
4. A가 프로그램을 종료한다.
5. 나중에 B가 접속하면 서버가 저장된 메시지 본문을 B에게 자동으로 전달한다.
6. B의 받은 내역에 메시지가 저장되고 화면에 표시된다.

### 시나리오 2: 첨부파일 내려받기와 만료
1. A가 파일을 첨부해 B에게 메시지를 보낸다. 파일은 서버에 업로드된다.
2. B가 접속하면 본문과 첨부파일 링크가 B의 받은 내역에 저장된다. 파일 자체는 아직 받지 않는다.
3. B가 링크를 누르면 서버에서 파일을 내려받는다.
4. 30일이 지나면 서버가 파일을 삭제한다.
5. 이후 B가 링크를 누르면 '만료'가 표시되고 파일을 받을 수 없다. 본문은 그대로 볼 수 있다.

### 시나리오 3: 내 보관함에서 메시지 삭제
1. B가 받은 내역에서 메시지 하나를 삭제한다.
2. B의 PC에서만 지워지고, A의 보낸 내역과 서버의 보관 데이터는 그대로 남는다.

## 7. 제약 사항 및 가정

- Java Swing으로 GUI를 구현한다.
- 본문 서식은 Swing이 지원하는 HTML 3.2 수준(글자 크기·색·굵기)으로 제한한다.
- 데이터는 서버와 클라이언트 모두 **텍스트 파일**로 저장한다. 외부 라이브러리(DB 드라이버 등)는 쓰지 않는다.
- 로그인에 비밀번호를 쓰지 않으므로, 다른 사람의 아이디를 알면 그 사람으로 접속할 수 있다. 수업 과제 범위에서 허용하는 한계이며, 필요하면 비밀번호를 추가한다.
- 사용자 계정은 관리자가 서버의 사용자 목록 파일에 미리 등록한다. 회원가입 기능은 없다.

## 8. 결정 사항 (구 미결정 사항)

| 번호 | 내용 | 결정 | 이유 |
|---|---|---|---|
| 1 | 서버의 메시지·첨부파일 저장 방식 | 텍스트 파일 (메시지 하나당 파일 하나) | 외부 라이브러리가 필요 없고, 메모장으로 열어 보며 디버깅할 수 있다. |
| 2 | 클라이언트 로컬 보관함 저장 방식 | 텍스트 파일 | 서버와 같은 형식을 써서 읽기·쓰기 코드를 공유한다. |
| 3 | 로그인 방식 | 아이디만 입력 (사전 등록된 사용자) | 부재중인 사람에게 보내려면 서버가 사용자 목록을 미리 알아야 한다. 구현을 단순하게 하려고 비밀번호는 생략한다. |
| 4 | 한 메시지의 받는 사람 수 | 여러 명 | 학교 메신저처럼 한 번에 여러 명에게 보낸다. 처음부터 목록으로 설계하는 편이 나중에 바꾸는 것보다 쉽다. |
| 5 | 서버의 본문 보관 기간 | 90일 | 첨부파일(30일)보다 길게 둔다. |
| 6 | 전달 완료된 본문의 서버 보관 | 전달 여부와 관계없이 90일 보관 | 삭제 규칙을 하나로 단순하게 유지한다. |
| 7 | 첨부파일 하나의 최대 크기 | 10MB (설정값으로 변경 가능) | 문서·사진에 충분하고, 파일을 조각내 보내는 기능 없이도 구현할 수 있다. |
| 8 | 단체 대화방 지원 여부 | 추가 기능(우선순위 하)으로 미룸 | 쪽지 방식 메시지를 먼저 완성한다. |
