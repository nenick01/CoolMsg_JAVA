## 1. 시스템 구성

```
[클라이언트 A] ──TCP──┐
                      ├── [서버] ─┬─ [메시지 저장소]   (본문)
[클라이언트 B] ──TCP──┘           └─ [첨부파일 보관소] (파일, 30일)

각 클라이언트 PC: [로컬 보관함] (보낸 내역 / 받은 내역, 본문만)
```

- 클라이언트끼리는 직접 연결하지 않고, 모든 메시지는 서버를 거친다.

### 1.1 프로젝트 구성

```
CoolMsg_JAVA/                  (Eclipse 워크스페이스 겸 VS Code 작업 폴더)
├─ docs/                       기획·설계 문서
├─ CoolMSG_JAVA_Common/        서버·클라이언트 공용 코드 (패킷, 프로토콜 상수)
│  ├─ src/coolmsg/common/
│  └─ test/coolmsg/common/     테스트 (실행 파일에 포함되지 않음)
├─ CoolMSG_JAVA_Server/        서버 프로그램  → Common 참조
│  ├─ src/coolmsg/server/
│  ├─ config/                  관리자 설정 (운영 파일 users.txt·org.txt·admin.txt는 Git 제외, 예시 sample/만 포함 — U24)
│  └─ data/                    실행 중 생기는 메시지·첨부파일 — Git 제외
├─ CoolMSG_JAVA_Client/        Swing 클라이언트 → Common 참조
│  ├─ src/
│  └─ (보관함·로그인 정보는 사용자 홈 폴더 ~/.coolmsg/ 에 저장, U34)
└─ .vscode/launch.json         VS Code 실행·디버그 설정 (서버, 클라이언트)
```

| 프로젝트 | 패키지 | 내용 |
|---|---|---|
| `CoolMSG_JAVA_Common` | `coolmsg.common` | 패킷 읽기·쓰기, 프로토콜 상수, 메시지 데이터 모양, "키=값+본문" 파일 형식 등 양쪽이 같은 규칙을 지켜야 하는 코드 (1.2 참고) |
| `CoolMSG_JAVA_Server` | `coolmsg.server` | **Swing 관리 화면**(서버 시작·중지, 사용자 관리, 조직도 관리), 접속 관리, 메시지 저장·전달, 첨부파일 |
| `CoolMSG_JAVA_Client` | `coolmsg.client` (예정) | Swing 화면, 로컬 보관함, 서버 통신 |

- 공용 코드는 Eclipse의 **프로젝트 참조**로 공유한다(`.classpath`의 `/CoolMSG_JAVA_Common`). 복사하지 않으므로 프로토콜을 고치면 서버와 클라이언트에 함께 반영된다.
- 실행할 때 작업 폴더는 각 프로젝트 폴더다. 그래서 아래의 `config/`, `data/` 경로는 각 프로젝트 폴더 기준이다.

### 1.2 Common 클래스 구조

**원칙: 서버와 클라이언트가 "같은 규칙"을 지켜야 하는 코드는 Common에 한 벌만 둔다.** 패킷 형식이나 파일 형식을 양쪽에서 따로 구현하면, 한쪽만 고쳤을 때 서로 말이 통하지 않는다.

| 패키지 | 클래스 | 역할 | 이렇게 둔 이유 |
|---|---|---|---|
| `coolmsg.common` | `ProtocolInfo` | 버전, 기본 포트, 크기 제한, 시간 제한 상수 | 양쪽이 같은 값을 써야 한다 |
| | `FormatException` | 패킷·파일·시각 형식 오류 (`IOException`의 하위 클래스) | 부르는 쪽이 파일·통신 오류와 같은 방식으로 처리할 수 있다 (U12) |
| `coolmsg.common.net` | `PacketType` | 명령 이름 목록 (`enum`: `PING`, `LOGIN`, `SEND` …) | 문자열 `"SNED"` 같은 오타를 컴파일 단계에서 잡는다 |
| | `HeaderKeys` | 헤더 키 이름 상수 (`reqId`, `reason`, `serverName`, `version`, `userId` …) | 서버와 클라이언트가 같은 키를 각자 문자열로 쓰다 오타로 어긋나지 않게 (구현 2단계에서 추가) |
| | `Packet` | 패킷 한 개: 종류 + 헤더(순서 유지 맵) + 데이터(`byte[]`) | 패킷을 "값"으로 다루면 테스트와 로그 출력이 쉽다 |
| | `PacketReader` | `read()`: 일반 패킷을 통째로 / `readFileTo()`: 파일 데이터를 64KB씩 디스크로 (**파일 메서드는 확장 때 구현**) | 작은 패킷은 단순하게, 10MB 파일은 메모리에 올리지 않게 (결정 12) |
| | `PacketWriter` | `write()`: 일반 패킷 / `writeFile()`: 디스크에서 64KB씩 소켓으로 | 위와 같음. 진행률 표시도 여기서 알린다 |
| | `ProgressListener` | "전체 몇 바이트 중 몇 바이트" 알림 인터페이스 | 통신 코드가 화면(`JProgressBar`)을 몰라도 진행률을 알릴 수 있다 |
| `coolmsg.common.model` | `MessageData` | 메시지 하나 (ID, 보낸 사람, 받는 사람, 참조, 시각, 본문, 첨부 목록, 회신·전달 원본) | 서버 파일·클라이언트 보관함·패킷이 모두 같은 모양을 쓴다 |
| | `AttachmentInfo` | 첨부파일 정보와 `ID\|크기\|만료\|이름` 변환 | 파일 이름을 맨 뒤에 두는 규칙을 한 곳에서만 구현 |
| | `DeliveryState` | `SENT` → `DELIVERED` → `READ`, "이 상태가 더 앞선가?" 판단 | "상태는 앞으로만" 규칙(2.6)을 한 곳에서만 구현 |
| | `HtmlText` | 본문 HTML 변환(일반 텍스트 → HTML), 빈 본문 검사, 목록 미리보기 (U37, 4단계), 허용 목록 정화·숫자 참조 되돌리기 (U59·U62, 7단계) | 서버(빈 본문 검사)와 클라이언트(작성·미리보기)가 같은 규칙을 쓴다 |
| | `OrgTree` | 조직도 트리와 `org.txt` 형식 읽기·쓰기, 부서 이름 규칙 (3.2, U54, 6단계) | 서버(파일·`ORG_OK`)와 클라이언트(조직도 화면)가 같은 형식 규칙을 쓴다 |
| `coolmsg.common.file` | `HeaderBodyFile` | "키=값 + 빈 줄 + 본문" 파일 읽기·쓰기 | 서버 메시지 파일과 클라이언트 보관함 파일의 형식이 같다 (결정 15) |
| | `AtomicFile` | **임시 파일에 다 쓴 뒤 이름을 바꿔** 저장 | 쓰는 도중 프로그램이 꺼져도 "반쯤 쓴 파일"이 남지 않는다 |
| | `HeaderFormat` | "키=값" 줄 읽기·쓰기 규칙(U1)과 엄격한 UTF-8 해석 | 패킷 헤더(`PacketReader`)와 파일 머리글(`HeaderBodyFile`)이 **같은 규칙**을 한 곳에서 쓴다 (U11) |
| | `TimeFormat` | 시각 문자열 형식을 한 곳에서 정함: **서버 PC 현지 시각, `yyyy-MM-ddTHH:mm:ss`** (U2) | 양쪽이 다른 형식을 쓰면 만료 계산이 틀어진다 |

- `HeaderBodyFile`은 **자기가 모르는 키도 지우지 않고 그대로 보존**한다. 그래서 서버는 `delivered.*`, `access`를, 클라이언트는 `read`, `state.*`를 같은 형식 위에 덧붙여 쓸 수 있다. 서버 전용·클라이언트 전용 정보는 Common에 넣지 않는다.
- **구현 상태 (2026-11-13)**: 위 표의 클래스를 모두 구현했다. 첨부파일 전송 메서드(`readFileTo`, `writeFile`)만 확장 때 구현한다(1.3). 테스트 71개 통과([테스트 기록](04_테스트기록.md)).
- `PacketReader`는 모르는 종류(`type`)의 패킷도 예외 없이 돌려준다(`getType()`이 `null`). 서버가 연결을 끊지 않고 `ERROR`로 응답하기 위해서다(3.7). 길이나 형식이 틀린 패킷은 `FormatException`이며, 이때는 스트림 위치가 어긋났으므로 연결을 닫는다.
- Common은 Swing도, 소켓 접속도, 서버·클라이언트 코드도 모른다. **아무것에도 의존하지 않는 바닥 계층**이라서 어느 쪽에서든 가져다 쓸 수 있다.

### 1.3 제출 범위와 확장 지점

과제 제출(2026-12-11) 범위는 요구사항분석서 9.1을 따른다. 빠진 기능 중 **첨부파일은 설계 뼈대만** 만든다. 프로토콜과 데이터 형식에 자리를 미리 두어, 나중에 기능을 채울 때 파일·패킷 형식을 바꾸지 않아도 되게 하기 위해서다.

**첨부파일 뼈대의 범위**

| 위치 | 제출 때 있는 것 | 제출 때 동작 | 확장할 때 할 일 |
|---|---|---|---|
| Common | `PacketType`의 `UPLOAD`·`DOWNLOAD`·`FILE*`, `AttachmentInfo`, `MessageData`의 첨부 목록, `attachment.N` 헤더 읽기·쓰기 | 형식만 있음. 첨부 목록은 항상 비어 있음 | `PacketReader.readFileTo()`, `PacketWriter.writeFile()` 구현 |
| 서버 | `AttachmentService`, `AttachmentStore` 클래스와 메서드 선언 | `UPLOAD`·`DOWNLOAD`에는 `ERROR reason=지원하지 않는 기능`, `attachment.N`이 있는 `SEND`에는 `SEND_FAIL` | 저장, 접근 권한(`access`), 만료 처리 |
| 클라이언트 | (없음) | 작성 창에 [파일 첨부] 버튼 없음 | 첨부 버튼, 첨부 링크, `TransferDialog` |

**그 밖의 제출 후 확장 항목**

| 기능 | 제출 때 상태 |
|---|---|
| 전달 | 첨부파일 재사용과 연결되어 있어 함께 미룸. `forwardOf` 헤더 자리는 있음 |
| 나에게 보내기 | 서버는 받는 사람에 자기 자신을 허용(설계 그대로). 클라이언트에 체크 상자만 없음 |
| 본문 속 이미지, 단체 대화방 | 없음 |
| 보관 기간 정리(`RetentionCleaner`), 보관 기간 설정 | 없음. 서버 데이터가 계속 쌓임(수업 규모에서는 문제없음) |
| 관리자 비밀번호 변경 | 없음. `admin.txt`를 지우고 다시 정하는 방법은 있음 |

### 1.4 컬렉션 활용

과제 요구사항 "컬렉션 활용"에 대응한다. 모두 **제네릭으로 타입을 지정**해 잘못된 타입이 들어가는 것을 컴파일 단계에서 막는다.

| 컬렉션 | 쓰는 곳 | 고른 이유 |
|---|---|---|
| `ArrayList<UserAccount>` | `UserDirectory`의 사용자 목록 | 등록 순서를 유지해야 한다(조직도가 없을 때 등록 순서로 표시, REQ-F-021) |
| `LinkedHashMap<String, String>` | `Packet` 헤더, `HeaderBodyFile` 머리글 | 키로 빨리 찾으면서도 **적힌 순서를 유지**한다. 파일을 다시 쓸 때 줄 순서가 바뀌지 않는다 |
| `ConcurrentHashMap<String, ClientSession>` | `SessionRegistry` (아이디 → 연결) | 아이디로 바로 찾고, 여러 스레드가 동시에 읽고 써도 안전하다 |
| `Object[]` (잠금 64개, 컬렉션은 아님) | `LockStripes` — `MessageStore`(메시지 ID), `PendingIndex`·`ReceiptQueue`(아이디) | 키마다 잠금을 새로 만들면 계속 늘어나므로, 고정 개수를 해시값으로 나눠 쓴다 (U16, 3.8) |
| `LinkedHashSet<String>` | `SEND`의 받는 사람·참조 정리, `PendingIndex` 목록 읽기 | 두 번 들어간 항목을 없애면서 순서는 유지한다 |
| `BlockingQueue<Packet>` (`LinkedBlockingQueue`) | `SendQueue` | 여러 스레드가 넣고 보내기 스레드 하나가 꺼내는 구조. 비어 있으면 꺼내는 쪽이 알아서 기다린다 (결정 9) |
| `ConcurrentHashMap<Integer, 대기표>` | 클라이언트 `Connection` (`reqId` → 응답 기다리는 곳) | 받기 스레드와 요청한 스레드가 동시에 쓴다 |
| `List<AttachmentInfo>` | `MessageData`의 첨부 목록 | 순서가 있는 목록. 제출 때는 항상 비어 있음 |
| `HashSet<String>` | 첨부파일 `access` 목록 (확장) | "이 사람이 들어 있나?"를 빠르게 확인 |
| `DefaultTableModel`, `DefaultListModel` | 관리 화면의 사용자 표, 접속자 목록 | Swing 표·목록이 쓰는 데이터 모델 |

## 2. 통신 프로토콜

클라이언트와 서버는 **TCP 소켓 하나**를 로그인부터 종료까지 유지하며 **패킷**을 주고받는다.

### 2.1 패킷 구조

> **용어**: 이 문서와 코드(`Packet`, `PacketReader`, `PacketType`)의 "패킷"은 IP 계층의 패킷이 아니라 **응용 계층 메시지**(이 프로그램이 정한 규약으로 주고받는 단위 하나)를 뜻한다. 소켓 프로그래밍에서 관례적으로 쓰는 이름이라 코드 이름은 그대로 둔다.
>
> | 계층 | 단위 | 이 프로젝트에서 |
> |---|---|---|
> | 응용 | 메시지 | `SEND`, `MSG` 한 건 (코드의 `Packet`) |
> | 전송 (TCP) | 세그먼트 | TCP가 바이트 흐름을 나눈 조각 |
> | 네트워크 (IP) | 패킷 | IP가 다른 컴퓨터로 보내는 단위 |
> | 데이터 링크 | 프레임 | 이더넷 등 |
>
> - 메시지 하나가 IP 패킷 하나와 1:1이 아니다. 큰 본문은 여러 IP 패킷으로 나뉘고, 작은 메시지 여럿이 한 패킷에 함께 실리기도 한다.
> - **TCP는 바이트를 빠짐없이·순서대로 전달하지만 메시지의 경계는 지켜 주지 않는다.** 한 번 보낸 메시지가 잘려서 오거나 다음 메시지와 붙어서 올 수 있다. 그래서 앞에 길이를 붙여 경계를 표시한다. 이 방식을 **길이 접두사 프레이밍(length-prefixed framing)**이라 하고, 헤더의 `key=value` 줄은 칸마다 이름표를 붙이는 역할이다(HTTP의 `Content-Length`·`이름: 값` 줄과 같은 생각).
> - 글자를 바이트로 바꾸는 것은 **인코딩**(UTF-8), 객체(`Packet`)를 바이트로 바꾸는 것은 **직렬화**(`PacketWriter`)다. 이 규약 전체가 **응용 계층 프로토콜**이다.
> - 서버는 이 규약으로 직접 포트를 열고 접속을 받는 **독립 실행 소켓 서버**다. HTTP를 쓰는 웹 서버(IIS, Apache)나 WAS(Tomcat) 위에서 실행하지 않는다. 자바만 있으면 그 PC에서 바로 실행된다(관리 화면이 Swing이라 화면이 있는 환경이 필요).

`DataOutputStream` / `DataInputStream`으로 아래 순서대로 쓰고 읽는다.

```
┌──────────────┬─────────────────────────┬───────────────┬──────────────────────┐
│ int 헤더길이 │ 헤더 (UTF-8 텍스트)      │ int 데이터길이 │ 데이터 (byte[])       │
│ 4바이트      │ "키=값" 줄들            │ 4바이트       │ 없으면 길이 0         │
└──────────────┴─────────────────────────┴───────────────┴──────────────────────┘
```

- **헤더**: 메시지 파일의 머리글과 같은 `키=값` 형식이다. 첫 줄은 항상 `type=명령`이다.
- **헤더 규칙 (U1, 엄격)** — 패킷 헤더와 파일 머리글에 똑같이 적용한다.
  - 줄바꿈은 `\n`만 쓴다. `\r`이 섞여 있으면 형식 오류.
  - 키와 값은 **처음 나오는 `=`에서만** 나눈다. 값 안의 `=`는 그대로 값이다(예: `reason=a=b`의 값은 `a=b`).
  - 같은 키가 두 번 나오면 형식 오류.
  - 값에 줄바꿈이 들어 있으면 **쓰기 전에 예외**를 던진다. 잘못된 패킷은 아예 만들어지지 않는다.
  - 이유: 형식이 조금 틀린 입력을 받아 주면 버그가 조용히 넘어가 나중에 엉뚱한 곳에서 터진다. 엄격하게 거부하면 문제가 생긴 그 자리에서 드러난다.
- **데이터**: 메시지 본문(HTML, UTF-8)이나 첨부파일 내용(바이너리)을 담는다.
- 길이를 먼저 보내는 이유: 본문에 줄바꿈이 있어도, 데이터가 이미지 같은 바이너리여도 어디까지가 한 패킷인지 정확히 알 수 있다. 받는 쪽은 `readInt()`로 길이를 읽고 `readFully()`로 그만큼 읽는다.
- **안전 장치**: 헤더는 최대 64KB, 데이터는 최대 11MB(첨부 10MB + 여유)로 제한한다. 이보다 큰 길이가 오면 잘못된 패킷으로 보고 연결을 끊는다(메모리 폭주 방지).
- 이 형식을 읽고 쓰는 `Packet` 클래스는 서버와 클라이언트가 **같은 코드를 공유**한다.

**예시: 메시지 보내기 패킷**

```
[헤더]
type=SEND
reqId=7
messageId=3f2a9c1e-8b4d-4c1a-9e2f-1a2b3c4d5e6f
receivers=lee,park
attachment.0=a81b0c2d-...

[데이터]
안녕하세요 <font color="red">중요 공지</font>입니다.
```

### 2.2 요청 번호(reqId)와 서버가 먼저 보내는 패킷

서버는 클라이언트가 요청하지 않아도 새 메시지(`MSG`), 접속 상태 변경(`PRESENCE`), 수신·읽음 알림(`RECEIPT`)을 **언제든 보낼 수 있다.** 그래서 클라이언트가 `SEND`를 보내고 응답을 기다리는 사이에 다른 패킷이 먼저 도착할 수 있다.

- 클라이언트는 요청마다 `reqId`(1부터 증가하는 번호)를 붙이고, 서버는 응답에 같은 `reqId`를 붙인다.
- 클라이언트는 **수신 전용 스레드 하나**가 모든 패킷을 읽는다.
  - `reqId`가 있는 응답 → 그 요청을 기다리던 쪽에 전달
  - `MSG` → 받은 내역에 저장하고 `ACK` 전송
  - `PRESENCE` → 조직도의 온라인 표시 갱신
  - `RECEIPT` → 보낸 내역의 수신·읽음 상태 갱신
  - 화면 갱신은 `SwingUtilities.invokeLater()`로 Swing 스레드에서 한다.

### 2.3 명령 목록

프로토콜 버전: **1** (`PONG`, `LOGIN`에서 확인)

**클라이언트 → 서버 (요청)**

| type | 헤더 | 데이터 | 서버 응답 | 로그인 전 |
|---|---|---|---|---|
| `PING` | `reqId` | 없음 | `PONG` | **가능** |
| `LOGIN` | `reqId`, `version`, `userId`, `password` | 없음 | `LOGIN_OK` / `LOGIN_FAIL` | **가능** |
| `UPLOAD` | `reqId`, `fileName` | 파일 내용 | `UPLOAD_OK` / `UPLOAD_FAIL` | 불가 |
| `SEND` | `reqId`, `messageId`, `receivers`, `cc`, `replyTo`, `forwardOf`, `attachment.N` | 본문 HTML | `SEND_OK` / `SEND_FAIL` | 불가 |
| `DOWNLOAD` | `reqId`, `attachmentId` | 없음 | `FILE` / `FILE_EXPIRED` / `FILE_DENIED` | 불가 |
| `ACK` | `messageId` | 없음 | 없음 | 불가 |
| `READ` | `messageId` | 없음 | 없음 | 불가 |
| `STATUS` | `reqId`, `messageId` | 없음 | `STATUS_OK` / `STATUS_FAIL` | 불가 |
| `ORG` | `reqId` | 없음 | `ORG_OK` / `ORG_NONE` | 불가 |
| `LOGOUT` | 없음 | 없음 | 없음 (서버가 연결 종료) | 불가 |

- `password`는 사용자가 입력한 비밀번호 원문이다. 서버는 `users.txt`의 솔트로 해시를 만들어 저장된 해시와 비교한다(3.2 참고). 원문은 저장하지 않는다.
- 통신을 암호화(TLS)하지 않으므로 같은 네트워크에서 패킷을 엿보면 비밀번호가 보일 수 있다. 수업 과제 범위의 알려진 한계다.
- 아이디가 없는 경우와 비밀번호가 틀린 경우 모두 `LOGIN_FAIL reason=아이디 또는 비밀번호가 틀렸습니다`로 똑같이 응답한다. 어느 쪽이 틀렸는지 알려 주면 있는 아이디를 알아내는 데 쓰일 수 있기 때문이다.
- 로그인 전에 '불가' 명령을 보내면 서버는 `ERROR`로 응답한다.
- `UPLOAD`·`DOWNLOAD`와 `FILE*` 응답은 **제출 범위에서 형식만 정의**되어 있다. 서버는 `ERROR reason=지원하지 않는 기능`으로 응답한다(1.3 참고).

**서버 → 클라이언트 (응답)**

| type | 헤더 | 데이터 | 의미 |
|---|---|---|---|
| `PONG` | `reqId`, `serverName`, `version`, `serverTime` | 없음 | 서버가 살아 있음 (연결 테스트·하트비트) |
| `LOGIN_OK` | `reqId` | 사용자 목록 + 접속 상태 | 로그인 성공, 이어서 밀린 `MSG`를 보냄 |
| `LOGIN_FAIL` | `reqId`, `reason` | 없음 | 아이디 또는 비밀번호 불일치(없는 아이디·삭제된 아이디 포함, **모두 같은 문구**), 프로토콜 버전 불일치, 이미 로그인된 연결에서 다시 로그인(U31) |
| `UPLOAD_OK` | `reqId`, `attachmentId`, `expiresAt` | 없음 | 업로드 성공 |
| `UPLOAD_FAIL` | `reqId`, `reason` | 없음 | 10MB 초과 등 |
| `SEND_OK` | `reqId`, `messageId`, `sentAt` | 없음 | 서버에 저장 완료 → 보낸 내역에 저장 |
| `SEND_FAIL` | `reqId`, `reason` | 없음 | `messageId` 형식 오류·다른 사람이 쓴 ID(U35), 없는 받는 사람, 없는 첨부파일 ID, 접근 권한 없는·만료된 첨부파일 등 |
| `FILE` | `reqId`, `attachmentId`, `fileName` | 파일 내용 | 첨부파일 다운로드 |
| `FILE_EXPIRED` | `reqId`, `attachmentId` | 없음 | 30일이 지나 삭제됨 |
| `FILE_DENIED` | `reqId`, `attachmentId` | 없음 | 이 파일이 첨부된 메시지를 보내거나 받은 적이 없음 |
| `STATUS_OK` | `reqId`, `messageId`, `state.{아이디}`, `readAt.{아이디}` | 없음 | 받는 사람별 상태 (2.6 참고) |
| `STATUS_FAIL` | `reqId`, `reason` | 없음 | 보낸 사람이 아님, 보관 기간(90일)이 지나 삭제됨 |
| `ORG_OK` | `reqId` | 조직도 데이터 (`org.txt` 형식) | 서버 설정대로 조직도 표시 (2.10 참고) |
| `ORG_NONE` | `reqId`, `reason` | 없음 | 조직도 설정 없음·읽기 실패 → 등록 순서로 임시 표시 |
| `ERROR` | `reqId`(있으면), `reason` | 없음 | 로그인 전 요청, 알 수 없는 명령 등 |

**서버 → 클라이언트 (서버가 먼저 보냄)**

| type | 헤더 | 데이터 | 보내는 때 |
|---|---|---|---|
| `MSG` | `messageId`, `sender`, `receivers`, `cc`, `sentAt`, `replyTo`, `forwardOf`, `attachment.N` | 본문 HTML | 새 메시지가 왔을 때 → 클라이언트는 저장 후 `ACK` |
| `PRESENCE` | `userId`, `online` (`true`/`false`) | 없음 | 누군가 로그인·로그아웃하거나 연결이 끊겼을 때, 접속 중인 **모든** 사용자에게 |
| `RECEIPT` | `messageId`, `userId`, `state` (`DELIVERED`/`READ`), `at`, `queued`(대기 파일에서 꺼낸 것이면 `true`) | 없음 | 받는 사람이 `ACK`·`READ`를 보냈을 때 보낸 사람에게. 보낸 사람이 오프라인이면 모아 두었다가 **로그인할 때** `queued=true`로 보냄 (2.6, U51) |
| `BYE` | `reason` | 없음 | 서버가 연결을 끊기 **직전**: 같은 아이디로 다른 곳에서 로그인, 관리자가 계정 삭제, 서버 중지. 클라이언트는 이유를 보여 주고 로그인 화면으로 (U30) |

**사용자 목록 형식** (`LOGIN_OK`의 데이터): 한 줄에 한 명, `아이디|이름|online` (등록 순서). 솔트·해시는 보내지 않는다. 부서는 조직도(`ORG_OK`)로 받는다.

```
kim|김철수|true
lee|이영희|false
```

**첨부파일 헤더 형식**: `attachment.0=attachmentId|크기|만료시각|파일이름`

- 파일 이름에 `|`나 `,`가 들어갈 수 있어서 **파일 이름을 맨 뒤**에 둔다. 앞의 세 칸만 `|`로 자르고 나머지는 전부 파일 이름으로 본다.
- `SEND`에서는 `attachment.0=attachmentId`만 보내고, 서버가 나머지 정보를 채워 `MSG`로 전달한다.

### 2.4 서버 연결 테스트

로그인 화면의 **[연결 테스트]** 버튼을 누르면 테스트 창을 띄우고, 입력한 서버 IP로 연결되는지 확인한다. 로그인과는 **별개의 짧은 연결**이다.

```
클라이언트                                       서버
  │ IP:9000에 연결 (제한 3초)                      │
  │── PING (reqId=1) ───────────────────────────▶│
  │◀──── PONG (reqId=1, serverName, version, serverTime)
  │ 응답 시간 계산 후 연결 종료                     │
```

| 결과 | 원인 (Java 예외) | 테스트 창 표시 |
|---|---|---|
| 성공 | — | 연결 성공, 서버 이름, 프로토콜 버전, 응답 시간(ms) — `PING`을 보낸 뒤 `PONG`을 받기까지 |
| 버전 다름 | `PONG`의 `version`이 1이 아님 | 서버와 프로그램 버전이 다름 |
| 연결 거부 | `ConnectException` | 서버가 꺼져 있거나 포트가 다름 |
| 시간 초과 | `SocketTimeoutException` (연결 3초, 응답 3초) | IP가 틀렸거나 방화벽이 막음 |
| 주소 오류 | `UnknownHostException` | 서버 주소를 찾을 수 없음 |

- 연결 시간 제한은 `socket.connect(new InetSocketAddress(ip, 9000), 3000)`, 응답 시간 제한은 `socket.setSoTimeout(3000)`으로 건다.
- 테스트는 Swing 스레드가 아닌 별도 스레드(`SwingWorker` 등)에서 실행한다. 그래야 최대 6초 동안 창이 멈추지 않는다.

### 2.5 접속 상태 (온라인/오프라인)

조직도에 누가 온라인인지 표시한다. **상태는 바뀔 때만 서버가 알려 주고, 클라이언트는 살아 있다는 신호만 주기적으로 보낸다.**

**방식 비교**

| 방식 | 동작 | 문제점 |
|---|---|---|
| 클라이언트가 주기적으로 조회 | 모든 클라이언트가 20~30초마다 "누가 온라인이야?" 요청 | 아무 변화가 없어도 계속 요청이 오고, 상태 변화가 최대 30초 늦게 보인다. |
| 서버가 주기적으로 전체 목록 전송 | 서버가 30초마다 모두에게 목록 전송 | 변화가 없어도 매번 전송한다. |
| **서버가 바뀔 때만 전송 (채택)** | 로그인·로그아웃이 생길 때만 `PRESENCE` 한 개 전송 | 연결이 조용히 끊긴 경우를 알아차리지 못한다 → **하트비트**로 보완 |

서버는 소켓 연결을 이미 갖고 있으므로 **누가 접속 중인지 원래 알고 있다.** 그래서 물어볼 필요 없이 바뀔 때만 알려 주면 된다. 부하는 시간이 아니라 로그인·로그아웃 횟수에 비례하고, 패킷 하나가 수십 바이트라 사내 규모(수백 명)에서는 문제가 없다.

**하트비트: 클라이언트가 주기적으로 보내는 것은 '살아 있음' 신호다**

- PC가 갑자기 꺼지거나 랜선이 빠지면 TCP는 연결이 끊긴 것을 한동안 알아차리지 못한다. 그러면 서버는 그 사람을 계속 온라인으로 보여 준다.
- 그래서 로그인한 클라이언트는 **30초마다 `PING`**을 보낸다.
- 서버는 한 클라이언트에게서 **90초 동안 아무 패킷도 오지 않으면** 연결을 끊고, 모두에게 `PRESENCE online=false`를 보낸다.
  - 구현: 서버에서 클라이언트별 소켓에 `socket.setSoTimeout(90000)`을 걸면, 90초 동안 읽을 것이 없을 때 `SocketTimeoutException`이 발생한다.

**흐름**
```
lee                            서버                          kim (접속 중)
  │── LOGIN ───────────────────▶│
  │◀── LOGIN_OK + 목록(상태 포함)│
  │                             │── PRESENCE (lee, true) ────▶│ 조직도에서 lee 온라인
  │── PING (30초마다) ─────────▶│
  │◀── PONG ────────────────────│
  ✕ (PC 강제 종료)               │
                                │ 90초 동안 패킷 없음 → 연결 종료
                                │── PRESENCE (lee, false) ───▶│ 조직도에서 lee 오프라인
```

### 2.6 수신 확인과 읽음 확인

받는 사람별로 메시지 상태를 세 단계로 관리한다.

| 상태 | 의미 | 바뀌는 때 | 보낸 사람 화면 |
|---|---|---|---|
| `SENT` | 서버에 저장됨 | `SEND_OK` | 전송됨 |
| `DELIVERED` | 받는 사람 PC에 도착함 | 받는 사람의 `ACK` | 안 읽음 |
| `READ` | 받는 사람이 열어 봄 | 받는 사람의 `READ` | 읽음 (읽은 시각) |

**`ACK`(수신 확인)와 `READ`(읽음 확인)를 나누는 이유**

- `ACK`는 "PC에 저장했다"는 신호라서 서버가 **다시 보낼지**를 판단하는 데 쓴다. `ACK`를 읽을 때 보내면, 받았지만 아직 안 읽은 메시지를 서버가 미전달로 보고 로그인할 때마다 다시 보낸다.
- 그래서 `ACK`는 메시지를 받아 저장하는 즉시 자동으로 보내고, `READ`는 사용자가 메시지를 열 때 보낸다.
- `READ`가 `ACK`보다 먼저 서버에 도착하면 서버는 `DELIVERED`까지 함께 처리한다.
- **읽은 시각(`readAt`)은 서버가 `READ`를 받은 시각**이다. 시계를 서버 하나로 통일한다(PC 시계가 틀려도 어긋나지 않음).
- **끊겨서 못 보낸 `READ`(U49)**: 클라이언트는 받은 내역 파일에 `readReported=true/false`를 따로 기록한다. 읽음으로 표시할 때 `false`로 두고 `READ`를 보내며, 로그인에 성공하면 `read=true`인데 `readReported=false`인 메시지의 `READ`를 모두 다시 보낸다. 서버는 이미 `readAt`이 있으면 무시하므로 두 번 가도 괜찮다. 늦게 보낸 `READ`는 읽은 시각도 늦게 찍힌다(알려진 한계).
  - `READ`는 응답이 없는 명령이라, 클라이언트는 "보내기 대기열에 넣었고 연결이 끊기지 않았다"를 알렸다고 본다. 넣은 직후 끊겨 유실되는 아주 짧은 틈은 남는다(알려진 한계).

**흐름**
```
kim (보낸 사람)                서버                           lee (받는 사람)
  │── SEND ───────────────────▶│ 저장 (lee: SENT)
  │◀── SEND_OK ─────────────────│── MSG ──────────────────────▶│ 받은 내역에 저장
  │                             │◀───────────────────── ACK ───│ (자동)
  │◀── RECEIPT (lee, DELIVERED)─│ lee: DELIVERED               │
  │    "안 읽음"                 │                              │ (사용자가 메시지 열기)
  │                             │◀──────────────────── READ ───│
  │◀── RECEIPT (lee, READ, at) ─│ lee: READ, readAt 기록        │
  │    "읽음 15:42"              │                              │
```

**보낸 사람이 오프라인일 때: 밀린 `RECEIPT`를 모아 두었다가 로그인할 때 보낸다**

- 서버는 상태를 메시지 파일에 기록하고(`delivered.{아이디}`, `readAt.{아이디}`), 보내지 못한 `RECEIPT`는 **보낸 사람별 대기 파일**에 한 줄씩 추가한다.
  - 파일: `data/receipts/{보낸 사람 아이디}.txt`
  - 한 줄 형식: `messageId|userId|state|at`
  - 보낸 사람이 접속 중이었지만 `RECEIPT`를 보내다 연결이 끊긴 경우에도 대기 파일에 넣는다.
- 보낸 사람이 로그인하면 서버는 `LOGIN_OK` → 밀린 `MSG` → **밀린 `RECEIPT`** 순서로 보내고, 다 보낸 뒤 대기 파일을 비운다. 대기 파일에서 꺼낸 `RECEIPT`에는 `queued=true`를 붙인다. 클라이언트는 이것으로 목록만 갱신하고 알림 창은 띄우지 않는다(U51).
- 클라이언트는 받은 상태를 자기 보낸 내역 파일에 기록한다. 그래서 로그인 직후부터 보낸 메시지 목록의 읽음 요약(예: `3/3`)이 맞게 표시된다.
- 메시지를 열 때의 `STATUS` 조회와 [새로고침]은 그대로 둔다. 대기 파일을 보내다 연결이 끊겨 일부를 잃더라도 이 조회로 다시 맞출 수 있다.

```
lee가 READ (kim은 오프라인)          서버
                                     │ readAt.lee 기록
                                     │ kim이 오프라인 → data/receipts/kim.txt 에 추가
                                     │   3f2a9c1e-...|lee|READ|2026-11-12T18:05:40
          ⋮ (다음 날)
kim ── LOGIN ──────────────────────▶│
kim ◀── LOGIN_OK ───────────────────│
kim ◀── MSG ... (kim이 받을 메시지)  │
kim ◀── RECEIPT (3f2a9c1e-..., lee, READ, 18:05:40)
                                     │ kim.txt 비우기
```

**상태는 앞으로만 바뀐다**

- 상태는 `SENT` → `DELIVERED` → `READ` 한 방향으로만 바뀐다. 클라이언트는 받은 상태가 **지금 기록된 상태보다 앞설 때만** 반영한다.
- 그래서 같은 `RECEIPT`가 두 번 오거나(대기 파일 + `STATUS`), `DELIVERED`가 `READ`보다 늦게 와도 결과가 같다.
- 보관 기간이 지나 보낸 내역에 없는 `messageId`의 `RECEIPT`는 무시한다.
- 받는 사람이 삭제되면 `STATUS_OK`에 그 사람을 `state.{아이디}=DELETED`로 알려 준다. 보낸 사람 화면은 '삭제된 사용자'로 표시하고 읽음 요약의 분모에서 뺀다(U4). `DELETED`는 저장되는 상태가 아니라 `STATUS` 응답에서만 쓰는 표시다.

**`STATUS_OK` 예시**
```
type=STATUS_OK
reqId=12
messageId=3f2a9c1e-...
state.lee=READ
readAt.lee=2026-11-12T15:42:07
state.park=DELIVERED
```

### 2.7 주요 흐름

**로그인과 밀린 메시지 받기**
```
클라이언트(lee)                          서버
  │── LOGIN (reqId=1, version=1, userId=lee, password) ─▶│ 버전 → 아이디·비밀번호 확인
  │◀──── LOGIN_OK (reqId=1) + 사용자 목록·상태 │── PRESENCE (lee, true) → 접속 중인 모두
  │◀──── MSG (messageId=A) ──────────────────│ pending/lee.txt 의 메시지 (3.8)
  │── ACK (messageId=A) ───────────────────▶│ delivered.lee=true → 보낸 사람에게 RECEIPT
  │◀──── MSG (messageId=B) ──────────────────│
  │── ACK (messageId=B) ───────────────────▶│
  │◀──── RECEIPT (messageId=C, kim, READ) ───│ data/receipts/lee.txt 의 밀린 알림
  │                                         │ (lee가 보낸 메시지 C를 kim이 읽음)
  │                                         │ 다 보낸 뒤 lee.txt 비우기
```

- 순서: `LOGIN_OK` → 밀린 `MSG`(받을 메시지) → 밀린 `RECEIPT`(내가 보낸 메시지의 수신·읽음 알림)

**첨부파일이 있는 메시지 보내기**
```
클라이언트(kim)                         서버                      lee (접속 중)
  │── UPLOAD (reqId=2) + 파일 ─────────▶│ 10MB 확인, 저장
  │◀──── UPLOAD_OK (attachmentId=X) ─────│
  │── SEND (reqId=3, attachment.0=X) ──▶│ 메시지 파일 저장
  │◀──── SEND_OK (reqId=3, sentAt) ──────│
  │  보낸 내역에 저장                     │── MSG ──────────────────▶│
  │                                      │◀────────────────── ACK ──│
  │◀──── RECEIPT (lee, DELIVERED) ───────│
```

### 2.8 규칙과 예외 처리

| 상황 | 처리 |
|---|---|
| `messageId`는 누가 만드나 | **클라이언트**가 UUID로 만든다. 서버는 **UUID 형식(`xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`, 16진수 소문자)만** 받는다(U35). 파일 이름으로 쓰이므로 `../` 같은 값으로 다른 위치에 쓰는 일을 막기 위해서다. 같은 ID가 이미 있으면: 보낸 사람이 같으면 재전송으로 보고 새로 저장하지 않고 `SEND_OK`(처음의 `sentAt`)만 다시 보낸다(중복 방지). 보낸 사람이 다르면 `SEND_FAIL` "이미 사용된 메시지 ID". |
| 로그인 때 밀린 메시지가 많음 | 밀린 메시지는 로그인 처리와 별도 작업으로 보낸다. 보내기 대기열이 **절반(250개) 이상** 차 있으면 빌 때까지 기다렸다가 이어서 넣는다(U36). 그래서 밀린 메시지가 수백·수천 개여도 대기열 한도(500개, U28)에 걸려 끊기지 않는다. |
| 본문 형식 | 4단계부터 본문은 항상 **HTML**이다(U37). 일반 텍스트를 쓸 때도 `<`·`>`·`&`·`"`를 바꾸고 줄바꿈을 `<br>`로 바꿔 HTML로 만든다. "빈 본문" 검사(U5)는 태그를 뺀 글자에 공백이 아닌 글자가 있는지로 한다. 1MB 제한은 HTML 바이트 기준. |
| `sentAt`, `readAt`은 누가 정하나 | **서버**가 정한다. PC마다 시계가 다를 수 있기 때문이다. |
| 같은 아이디로 두 번 로그인 | 기존 연결에 `BYE`("다른 곳에서 로그인하여 연결이 끊겼습니다")를 보낸 뒤 끊고, 새 연결을 허용한다(U30). 이때는 `PRESENCE`를 보내지 않는다(계속 온라인). |
| 이미 로그인한 연결에서 다시 `LOGIN` | `LOGIN_FAIL` "이미 로그인되어 있습니다". 기존 로그인은 유지한다(U31). 다른 아이디로 바꾸려면 로그아웃(연결 종료) 후 새로 접속한다. |
| ACK 전에 연결이 끊김 | `delivered`가 false로 남아 다음 로그인 때 다시 보낸다. 클라이언트는 이미 받은 `messageId`면 저장하지 않고 `ACK`만 보낸다. |
| 같은 메시지를 여러 번 열어 봄 | `READ`는 처음 한 번만 보낸다(받은 내역 파일에 읽음 여부 기록). 서버도 `readAt`이 이미 있으면 바꾸지 않는다. |
| 업로드는 했는데 `SEND`를 안 보냄 | 첨부파일은 30일 뒤 자동 삭제되므로 따로 처리하지 않는다. |
| 하트비트가 90초 동안 없음 | 서버가 연결을 끊고 `PRESENCE online=false`를 보낸다. 클라이언트는 "서버와 연결이 끊겼습니다"를 알리고 로그인 화면으로 돌아간다(자동 재접속 없음, U9). 반대로 **클라이언트도 90초 동안 서버에서 아무 패킷도 오지 않으면** 끊긴 것으로 본다(U32, 서버는 하트비트마다 `PONG`으로 답하므로 정상이면 30초마다 받음). |
| 여러 스레드가 한 클라이언트에 동시에 보냄 | 연결마다 **보내기 대기열(`SendQueue`)과 보내기 전용 스레드**를 둔다. 다른 스레드는 대기열에 넣기만 하므로 패킷이 섞이지 않고, 느린 수신자 때문에 멈추지도 않는다. (예: kim의 스레드와 park의 스레드가 동시에 lee에게 `MSG`·`PRESENCE`를 보내는 경우, 3.6 참고) |
| 보낸 사람이 오프라인일 때 생긴 수신·읽음 | 서버가 `data/receipts/{보낸 사람}.txt`에 모아 두었다가 로그인할 때 `RECEIPT`로 보내고 비운다. |
| 같은 `RECEIPT`가 두 번 오거나 순서가 뒤바뀜 | 클라이언트는 기록된 상태보다 앞선 상태(`SENT` → `DELIVERED` → `READ`)만 반영하므로 결과가 같다. |
| `SEND` 검사 (U5) | 받는 사람 1명 이상 필수(참조만으로는 불가), 받는 사람+참조 합계 100명 이하, 없는·삭제된 아이디 불가, 본문이 비었거나 공백뿐이면 불가, 본문 1MB(UTF-8) 이하. 하나라도 어기면 `SEND_FAIL`(무엇이 잘못됐는지 `reason`에 적음). 중복된 아이디는 하나로 합친다. |
| 응답이 오지 않는 요청 (U10) | 클라이언트는 요청마다 **10초** 시간 제한을 두고, 넘으면 실패로 처리해 화면에 알린다. `reqId` 없는 `ERROR`는 로그만 남긴다. 보내기가 시간 초과로 실패해도 같은 `messageId`로 다시 보내면 서버가 중복을 거른다. |
| 삭제된 사용자에게 가던 메시지 (U4) | 메시지 파일은 그대로 둔다. 보낸 사람의 읽음 확인에는 '삭제된 사용자'로 표시하고 읽음 요약(예: 1/3)의 분모에서 뺀다. 그 사람의 대기 파일(`receipts`, `pending`)은 **지우지 않고 남긴다**(U19: 되살리면 그대로 이어서 받음). |

### 2.9 접속 정보와 시간 설정

| 항목 | 값 |
|---|---|
| 포트 | 9000 (서버 설정값) |
| 서버 주소 | 로그인 화면에서 `IP` 또는 `IP:포트`로 입력 (기본값 `localhost`, 포트를 생략하면 9000, U26) |
| 보내기 대기열 | 연결당 최대 500개. 가득 차면 그 연결을 끊음 (U28) |
| 동시 접속 | 최대 400개. 넘으면 `ERROR`를 보내고 끊음 (U28) |
| 연결 테스트 시간 제한 | 연결 3초, 응답 3초 |
| 하트비트 간격 | 30초 (클라이언트 → 서버 `PING`) |

| 클라이언트의 끊김 판정 | 90초 동안 서버에서 패킷 없음 (U32) |

| 시각 형식 | 서버 PC 현지 시각, `yyyy-MM-ddTHH:mm:ss` (예: `2026-11-12T15:30:12`, U2) |
| 메시지 크기 | 받는 사람 + 참조 최대 100명, 본문 최대 1MB (U5) |

### 2.10 조직도

조직도의 부서 구조와 표시 순서는 **서버의 조직도 설정 파일(`org.txt`)**을 따른다. 설정을 받지 못하면 **사용자 등록 순서**로 보여 준다.

**흐름**
```
클라이언트                               서버
  │── LOGIN ──────────────────────────────▶│
  │◀──── LOGIN_OK + 사용자 목록 (등록 순서) │
  │── ORG (reqId=2) ──────────────────────▶│ 서버 메모리의 조직도 (org.txt와 같음)
  │◀──── ORG_OK (reqId=2) + 조직도 데이터   │  → 정상이면 ORG_OK
  │       또는 ORG_NONE (reqId=2, reason)  │  → 파일 없음·읽기 실패면 ORG_NONE
```

**클라이언트가 조직도를 그리는 규칙**

| 상황 | 화면 |
|---|---|
| `ORG_OK`를 받음 | 설정대로 부서 트리를 그리고, 부서·사용자를 설정 파일에 적힌 순서대로 표시 |
| `ORG_NONE`을 받음, 3초 안에 응답이 없음, 데이터 형식 오류 | **임시 표시**: `LOGIN_OK`의 사용자 목록을 받은 순서(= `users.txt` 등록 순서) 그대로 한 줄 목록으로 표시 (이름과 아이디) |
| 설정에는 없지만 `users.txt`에 있는 사용자 | 조직도 맨 아래 **'미배치'** 부서에 등록 순서대로 표시 (아무도 조직도에서 빠지지 않게) |
| 설정에는 있지만 `users.txt`에 없는 아이디 | 서버가 `org.txt`를 읽을 때 건너뛰고 서버 로그에 경고 |
| 설정에 있는 **삭제된 사용자** | 사용자를 삭제할 때 `org.txt`에서도 그 줄을 빼서 저장한다(U55). 그래도 남아 있으면(파일 저장 실패, 손으로 고침) 서버가 `ORG_OK`를 만들 때 걸러낸다 |
| 부서가 하나도 없는 `org.txt` | 설정이 없는 것으로 보고 `ORG_NONE` → 임시 표시 |
| 로그인 뒤 관리자가 추가한 사용자(클라이언트 목록에 없는 아이디) | 클라이언트는 그 줄을 건너뛴다(다음 로그인 때 보임, U50) |

- 등록 순서가 지켜지려면 서버가 사용자 목록을 **순서가 유지되는 자료구조**(`ArrayList`, `LinkedHashMap`)로 들고 있어야 한다. `HashMap`은 순서가 뒤섞인다.
- 서버는 시작할 때 `org.txt`를 읽어 메모리에 둔다. 관리 화면의 [조직도 관리]에서 저장하면 파일과 메모리가 **즉시** 바뀌고, 그다음 `ORG` 요청부터 새 조직도를 보낸다(서버 재시작 불필요, 3.5 참고).
- 조직도 데이터 형식은 `org.txt`와 같다 (3.2 참고). 서버는 주석을 빼고, 삭제된·없는 아이디를 걸러서 보낸다.
- 클라이언트는 `LOGIN_OK` 바로 뒤에 `ORG`를 보내고 **3초**만 기다린다(`ORG_RESPONSE_TIMEOUT_MILLIS`). 그동안 메인 창은 사용자 목록으로 먼저 열린다.

### 2.11 참조, 회신·전체회신, 전달, 나에게 보내기

**참조 (`cc`)**

- `SEND`와 `MSG`에 `cc`(참조 대상 아이디 목록)를 추가한다. 비어 있으면 줄을 생략한다.
- 서버의 처리(저장 후 전달, `ACK`, `READ`, `RECEIPT`)는 받는 사람과 **똑같다.** 화면에서만 '받는 사람'과 '참조'로 나누어 보여 준다.
- 보낸 메시지의 읽음 확인에는 참조 대상도 포함하고 `(참조)`라고 표시한다. 목록의 읽음 요약(예: `2/4`)도 받는 사람과 참조 대상을 합쳐 센다.
- 같은 사람이 `receivers`와 `cc`에 모두 있으면 서버는 `receivers`에만 남긴다.

**회신·전체회신** — 클라이언트 기능 (프로토콜 변경은 `replyTo` 헤더 하나)

| 기능 | 받는 사람 | 참조 |
|---|---|---|
| 회신 | 원본을 보낸 사람 | 없음 |
| 전체회신 | 원본을 보낸 사람 + 원본의 받는 사람 (나 제외) | 원본의 참조 대상 (나 제외) |

- 작성 창 본문은 **맨 위에 새로 입력할 공간**, 그 아래 **원본의 작성자와 보낸 시각**, 그 아래 **원본 본문 전체**로 채운다 (4.3 화면 참고). 가로줄은 넣지 않는다.
- 인용한 원본도 본문의 일부로 함께 전송된다. 그래서 회신이 이어질수록 인용이 아래로 쌓인다. 작성 창에서 고칠 수 있어 필요 없는 부분을 지울 수 있다(U61).
- `SEND`에 `replyTo=원본 messageId`를 넣는다. 지금은 기록만 해 두고, 나중에 대화 묶어 보기에 쓸 수 있다.
- 첨부파일은 회신에 포함하지 않는다.

**전달** — 원본 본문과 첨부파일을 다른 사람에게 보낸다 *(제출 후 확장, 1.3)*

- 작성 창 본문은 회신과 같은 형태로 채우되, 원본 정보에 **받는 사람**도 함께 넣는다. 받는 사람은 비워 둔다.
- 첨부파일은 PC에 원본이 없으므로 **서버에 있는 파일 ID를 그대로 다시 쓴다** (`attachment.N=원본 attachmentId`). 파일을 다시 올리지 않는다.
- 서버는 `SEND`를 받으면 각 첨부파일을 확인한다.
  - 보내는 사람이 그 파일에 **접근할 수 있는 사람**이어야 한다(첨부파일 정보의 `access` 목록, 3.2 참고). 아니면 `SEND_FAIL`.
  - 만료된 파일이면 `SEND_FAIL`. 클라이언트는 작성 창을 열 때 이미 만료된 첨부파일을 빼고 "만료된 첨부파일 1개는 제외됨"을 안내한다.
- 전달한 첨부파일의 만료 시각은 **원본 업로드 기준**이다. 작성 창의 첨부파일 옆에 만료일을 표시한다.
- `SEND`에 `forwardOf=원본 messageId`를 넣는다(기록용).

**나에게 보내기** *(제출 후 확장, 1.3)*

- 작성 창의 [나에게 보내기]를 체크하면 `receivers`에 내 아이디를 넣는다. 서버는 받는 사람에 자기 자신이 있는 것을 허용한다.
- 내 PC에서는 보낸 내역(`sent/`)과 받은 내역(`inbox/`)에 각각 저장된다. 폴더가 달라 중복 저장 검사와 충돌하지 않는다.
- 내가 받은 내역에서 열면 `READ` → 나에게 `RECEIPT`가 오며, 다른 받는 사람과 똑같이 처리된다.

### 2.12 파일 전송 진행률 *(제출 후 확장, 1.3)*

파일 크기 제한(10MB)과 패킷 구조는 그대로 두고, 파일 데이터를 **64KB씩 나누어 쓰고 읽으면서** 진행률 창을 갱신한다.

- 보내기(`UPLOAD`): 헤더와 데이터 길이를 먼저 쓴 뒤, 파일을 `FileInputStream`으로 64KB씩 읽어 소켓에 쓴다. 한 번 쓸 때마다 보낸 바이트 수를 진행률 창에 알린다.
- 받기(`FILE`): 데이터 길이를 읽은 뒤 64KB씩 읽어 `FileOutputStream`으로 바로 파일에 쓴다. 파일 전체를 메모리에 올리지 않는다.
- 이 방식은 상대방 입장에서 보면 패킷 하나와 똑같아서 **프로토콜 변경이 없다.**
- 진행률 창(`JProgressBar`)에는 진행률(%), 보낸 크기 / 전체 크기, 전송 속도, 남은 시간을 표시한다. 갱신은 `SwingWorker`의 `publish()` / `process()`로 Swing 스레드에서 한다.
- **취소**: 패킷 중간에 멈추면 받는 쪽은 다음 패킷의 시작을 찾을 수 없다. 그래서 취소하면 **연결을 끊고 로그인 화면으로 돌아간다**(자동 재접속 없음, U9). 서버는 연결이 끊긴 업로드의 미완성 파일을 지운다.
- 파일을 주고받는 동안에는 같은 연결의 다른 패킷(새 메시지 알림 등)이 잠시 늦어진다. 10MB는 사내망에서 몇 초 안에 끝나므로 허용한다. 더 큰 파일을 지원하려면 파일 전용 연결을 따로 여는 방식이 필요하다(추가 기능).

**`Outbox` 인터페이스를 두는 이유 — 순환 의존 끊기**

- `net`(소켓)은 패킷을 받으면 `service`를 부른다. 그런데 `service`도 처리 중에 다른 사람에게 패킷을 보내야 한다(예: `SEND` 처리 중 받는 사람에게 `MSG`). 그러려면 `service`가 `net`을 불러야 해서 **서로가 서로를 아는 순환**이 생긴다.
- 그래서 `service` 패키지에 `Outbox`라는 **약속(인터페이스)**만 두고, `net`의 `SessionRegistry`가 그 약속을 구현한다. `service`는 "누군가 보내 준다"는 것만 알고 소켓은 모른다.
- 덕분에 테스트할 때 `Outbox` 자리에 "보낸 패킷을 목록에 모아 두기만 하는 가짜"를 끼우면, 소켓 없이 `MessageService`를 검증할 수 있다.

**스레드 구성**

| 스레드 | 개수 | 하는 일 |
|---|---|---|
| Swing 스레드 | 1 | 관리 화면 (Swing 규칙상 화면은 이 스레드에서만 고친다) |
| 접속 받기 | 1 | `ServerListener`: `accept()`로 새 연결을 기다림 |
| 연결마다 받기 | 접속자 수 | 패킷 읽기 → `RequestDispatcher` → 서비스 |
| 연결마다 보내기 | 접속자 수 | `SendQueue`에서 꺼내 소켓에 쓰기 |
| 정리 | 1 | `RetentionCleaner` |

**시작 순서**
```
ServerMain.main()
  └─ SwingUtilities.invokeLater()            Swing 화면은 Swing 전용 스레드에서 만든다
       ├─ config/admin.txt 가 없음 → 관리자 비밀번호 설정 창 (4자 이상, 두 번 입력)
       ├─ config/admin.txt 가 있음 → 관리자 로그인 창 (5번 틀리면 종료)
       └─ 성공 → ServerContext 생성 (설정·사용자·조직도 읽기) → ServerFrame 표시
```

- 이전의 `UserStore`(읽기 전용)는 `UserDirectory`로 흡수하고 삭제했다(구현 1단계).

### 3.2 메시지 저장 방식

본문과 첨부파일을 **따로 저장**하고, 본문에는 첨부파일 ID 목록만 넣는다. 저장 매체는 **텍스트 파일**이다.

**메시지 (본문)**

| 항목 | 설명 |
|---|---|
| messageId | 메시지 고유 ID (`java.util.UUID`) |
| sender | 보낸 사람 아이디 |
| receivers | 받는 사람 아이디 목록 (여러 명, 나 자신 포함 가능) |
| cc | 참조 대상 아이디 목록 (없으면 줄 생략) |
| replyTo / forwardOf | 회신·전달한 원본 메시지 ID (없으면 줄 생략) |
| sentAt | 보낸 시각 |
| body | 본문 (서식 있는 텍스트, HTML 문자열) |
| attachment.N | 첨부파일 정보 `attachmentId\|크기\|만료시각\|파일이름` (프로토콜 2.3과 같은 형식) |
| delivered.{아이디} | 받는 사람·참조 대상별 전달 완료 여부 (그 사람의 ACK를 받으면 true) |
| readAt.{아이디} | 받는 사람이 읽은 시각 (그 사람의 READ를 받으면 기록, 안 읽었으면 줄 없음) |

**메시지 파일 형식** — 머리글(`키=값`) 다음 빈 줄, 그 뒤는 모두 본문

```
messageId=3f2a9c1e-...
sender=kim
receivers=lee,park
cc=choi
sentAt=2026-11-12T15:30:12
attachment.0=a81b...|204800|2026-12-12T15:30:12|회의자료.pdf
delivered.lee=true
delivered.park=false
delivered.choi=true
readAt.lee=2026-11-12T15:42:07

안녕하세요 <font color="red">중요 공지</font>입니다.
```

- 본문을 빈 줄 뒤에 두어 본문에 줄바꿈이나 `=`가 있어도 문제가 없게 한다.
- 아이디는 영문 소문자와 숫자만 허용해 `,`와 `=`가 섞이지 않게 한다.

**첨부파일** *(설계 뼈대만, 1.3)*

| 항목 | 설명 |
|---|---|
| attachmentId | 첨부파일 고유 ID |
| fileName | 원래 파일 이름 |
| size | 파일 크기 |
| uploadedAt | 업로드 시각 |
| expiresAt | 만료 시각 (업로드 후 30일, 전달해도 바뀌지 않음) |
| access | 이 파일에 접근할 수 있는 아이디 목록. **업로드할 때 올린 사람을 먼저 넣고**, 이 파일이 첨부된 메시지가 저장될 때마다 보낸 사람·받는 사람·참조 대상을 추가한다. `DOWNLOAD`와 `SEND`(첨부·전달) 때 확인 |
| 실제 파일 | 서버 보관 폴더에 `attachmentId` 이름으로 저장 |

- 최대 크기는 10MB (서버 설정값). 넘으면 업로드를 거부한다.

**사용자 목록 (`users.txt`)** — 관리 화면의 [사용자 관리]에서 추가·수정, 한 줄에 한 명 (`아이디|이름|솔트|비밀번호해시|상태`)

```
kim|김철수|6dfaf622a12019bd1d0f676016ec6564|6fe8c531475980...(64자)
lee|이영희|a457db60284bf89d9b3452f5ec832209|43f9aea4ef0b08...(64자)
```

- 소속 부서는 여기에 두지 않고 조직도(`org.txt`)에만 둔다. 같은 정보를 두 곳에 두면 한쪽만 고쳐 어긋나기 쉽다.
- **상태**: `active` 또는 `deleted`. 사용자를 삭제하면 줄을 지우지 않고 `deleted`로 바꾼다. 삭제된 아이디는 로그인·받는 사람 선택에서 빠지고, **같은 아이디로 다시 등록할 수 없다**(결정 14). 다른 사람이 같은 아이디로 등록되어 이전 사람의 미전달 메시지와 첨부파일 권한을 받는 일을 막기 위해서다.
- 5번째 칸이 없는 줄은 `active`로 읽는다(지금 예시 파일과 `UserStore`는 4칸 형식).

**비밀번호 저장** — 원문을 저장하지 않고 **솔트 + 해시**만 저장한다

| 항목 | 내용 |
|---|---|
| 방식 | `PBKDF2WithHmacSHA256` (Java 기본 라이브러리 `javax.crypto`) |
| 솔트 | 사용자마다 16바이트 무작위 값 (`SecureRandom`). 같은 비밀번호여도 해시가 달라진다. |
| 반복 횟수 | 65,536회. 일부러 느리게 만들어, 파일이 유출돼도 비밀번호를 하나씩 대입해 보기 어렵게 한다. |
| 결과 | 256비트 해시. 솔트와 해시 모두 16진수 문자열로 저장 |
| 비교 | 입력값을 같은 솔트로 해시해 `MessageDigest.isEqual()`로 비교 (비교 시간으로 정답을 추측하지 못하게) |

- 이 방식은 관리자 비밀번호(`admin.txt`)와 사용자 비밀번호(`users.txt`)에 똑같이 쓴다. 구현은 `coolmsg.server.security.PasswordHasher`.
- 저장소에 있는 예시 `users.txt`의 테스트 비밀번호는 파일 맨 위 주석에 적혀 있다.

**관리자 비밀번호 (`admin.txt`)** — 키=값 형식, **Git에 올리지 않는다**

```
salt=16진수
hash=16진수
```

**서버 설정 (`server.txt`)** — 키=값 형식, 서버 시작 때 읽음 (결정 13)

```
port=9000
serverName=CoolMsg 서버
bodyRetentionDays=90
attachmentRetentionDays=30
maxAttachmentMB=10
```

- 파일이나 항목이 없으면 기본값을 쓴다. 바꾸려면 파일을 고친 뒤 서버를 다시 켠다.
- **값 검사 (U21)** — 범위를 벗어나거나 숫자가 아니면 **그 항목만** 기본값을 쓰고 서버 로그에 경고한다.

  | 키 | 허용 범위 | 기본값 |
  |---|---|---|
  | `port` | 1024~65535 | 9000 |
  | `serverName` | 1~30자 | CoolMsg 서버 |
  | `bodyRetentionDays` | 1 이상 | 90 |
  | `attachmentRetentionDays` | 1 이상 | 30 |
  | `maxAttachmentMB` | 1~10 (패킷 데이터 상한 11MB 때문) | 10 |

- 사람이 고치는 파일이라 관대하게 읽는다(U11): 줄 끝 공백·`\r` 허용, `#` 주석과 빈 줄 무시, 모르는 키는 무시하고 경고, 같은 키가 두 번이면 나중 값을 쓰고 경고.
- 기본값이 적힌 예시 `server.txt`를 저장소에 둔다.
- `serverName`은 연결 테스트(`PONG`)에 표시된다.

**조직도 설정 (`org.txt`)** — 관리 화면의 [조직도 관리]에서 저장, **적힌 순서가 곧 화면 순서**

```
# D|부서 경로        (하위 부서는 > 로 구분)
# U|부서 경로|아이디  (그 부서에 속한 사용자)
D|한빛초등학교
D|한빛초등학교>교무실
U|한빛초등학교>교무실|kim
D|한빛초등학교>교육정보실
U|한빛초등학교>교육정보실|lee
U|한빛초등학교>교육정보실|park
D|한빛초등학교>행정실
U|한빛초등학교>행정실|choi
```

- `#`으로 시작하는 줄과 빈 줄은 무시한다.
- 줄마다 `|`로 나누기만 하면 되어 들여쓰기 방식보다 읽기 쉽다.
- `U` 줄의 부서 경로가 앞에서 `D`로 정의되지 않았으면 그 줄을 건너뛰고 서버 로그에 경고한다.
- 한 사용자가 여러 부서에 나오면 처음 나온 부서만 쓴다.
- **맨 위 부서는 하나**(기관 이름, U54). `D` 줄 중 `>`가 없는 것이 둘 이상이면 처음 것만 쓰고 나머지 줄(과 그 아래)은 경고 후 건너뛴다.
- **부서 이름 규칙(U54)**: 1~20자(앞뒤 공백 제외), `|`·`>`·줄바꿈 금지, 같은 부서 아래 같은 이름 금지.
- 사람이 손으로 고칠 수 있는 설정 파일이라 **관대하게** 읽는다(U11): 잘못된 줄은 건너뛰고 경고, 서버는 계속 동작. 파일을 읽지 못하면(인코딩 오류 등) `ORG_NONE`.
- 저장할 때는 `users.txt`와 같이 **맨 위 주석 블록을 보존**하고 `AtomicFile`로 통째로 다시 쓴다.

**서버 폴더 구조**

- 아래 `config/`·`data/`는 **기준 폴더**(`AppHome`, U63) 아래에 있다: jar·exe로 실행하면 그 파일이 있는 폴더, IDE에서 실행하면 작업 폴더(`CoolMSG_JAVA_Server/`). 관리 화면 로그 첫 부분에 실제 위치를 보여 준다.

```
CoolMSG_JAVA_Server/
├─ config/                            관리 화면에서 편집하는 설정
│  ├─ admin.txt                       관리자 비밀번호 해시 (처음 실행 때 생성, Git 제외)
│  ├─ server.txt                      서버 설정 (포트, 서버 이름, 보관 기간, 첨부 크기)
│  ├─ users.txt                       사용자 목록 (등록 순서 = 임시 표시 순서) — Git 제외 (U24)
│  ├─ org.txt                         조직도 설정 (없어도 서버는 동작) — Git 제외 (U24)
│  └─ sample/                         저장소에 올라가는 예시 (users.txt, org.txt)
└─ data/                              서버가 실행 중 만드는 데이터 (Git 제외)
   ├─ messages/{messageId}.txt        메시지 (본문)
   ├─ pending/{아이디}.txt             그 사람이 아직 받지 않은 messageId 목록 (색인, 3.8)
   ├─ pending/.clean                  서버가 정상 종료했다는 표시 (3.8.6)
   ├─ receipts/{아이디}.txt            그 사람이 오프라인일 때 생긴 수신·읽음 알림 (로그인 때 보내고 비움)
   └─ attachments/
      ├─ {attachmentId}.meta          첨부파일 정보 (키=값)
      └─ {attachmentId}.bin           실제 파일
```

- **설정(`config/`)과 실행 데이터(`data/`)를 나눈다.** 사용자 목록과 조직도는 관리자가 관리 화면에서 고치는 설정이라 예시와 함께 Git에 올리고, 메시지·첨부파일은 실행할 때마다 생기므로 올리지 않는다.
- 단, `admin.txt`는 PC마다 관리자가 따로 정하는 값이라 Git에 올리지 않는다(`.gitignore`).
- **예시와 운영 데이터를 나눈다 (U24).** `users.txt`와 `org.txt`는 관리 화면으로 바뀌는 운영 데이터라 Git에서 제외한다. 저장소에는 `config/sample/`의 예시만 올린다. 서버를 켤 때 `config/users.txt`(또는 `org.txt`)가 없으면 `config/sample/`의 예시를 복사해 쓴다. 복사에 실패하면 서버를 시작하지 않는다(U22와 같은 이유).
- 그래서 README만 보고 처음 실행한 사람도 예시 계정으로 바로 써 볼 수 있고, 관리 화면에서 만든 계정은 공개 저장소에 올라가지 않는다.
- `data/` 폴더가 없으면 서버가 시작할 때 만든다.

### 3.3 보관 기간과 삭제

| 대상 | 보관 기간 | 기간이 지나면 |
|---|---|---|
| 첨부파일 | 업로드 후 30일 | 파일 삭제, 이후 요청에는 '만료' 응답 |
| 메시지 본문 | 보낸 후 90일 (전달 여부와 관계없음) | 삭제, 그때까지 못 받은 사람은 받지 못함 |

- `RetentionCleaner`가 서버 시작 때와 하루 한 번 기간이 지난 데이터를 정리한다. 메시지 파일을 지울 때도 `MessageStore`의 메시지 ID별 잠금을 거친다(정리 중에 온 `ACK`와 겹치지 않게).
- 만료된 첨부파일의 정보(`.meta`)를 언제 지울지는 첨부파일을 확장할 때 정한다(5장 U3).
- **보관 기간 정리 전체가 제출 후 확장이다**(REQ-F-009 보류, 1.3).

### 3.5 서버 관리 화면

**관리자 확인 (서버를 켤 때)**

```
┌─ CoolMsg 서버 - 관리자 비밀번호 설정 ─┐     ┌─ CoolMsg 서버 - 관리자 로그인 ─┐
│ 처음 실행입니다. 관리자 비밀번호를     │     │ 관리자 비밀번호를 입력하세요.  │
│ 정해 주세요. (4자 이상)               │     │ [●●●●●●        ]             │
│ 비밀번호      [●●●●●●        ]        │     │          [확인]  [취소]       │
│ 비밀번호 확인 [●●●●●●        ]        │     └───────────────────────────────┘
│              [확인]  [취소]           │       틀리면 "(1/5)"처럼 남은 횟수 표시
└───────────────────────────────────────┘       5번 틀리면 서버 종료
        config/admin.txt 가 없을 때
```

- 관리자 계정은 **비밀번호 하나만** 있다(아이디 없음). 서버 PC 앞에 있는 사람만 관리 화면을 쓰기 때문이다.
- 비밀번호를 잊으면 `config/admin.txt`를 지우고 서버를 다시 실행해 새로 정한다. 서버 PC의 파일에 접근할 수 있는 사람을 관리자로 본다.

**관리 메인 창 — 탭 3개**

```
┌─ CoolMsg 서버 관리 ───────────────────────────────────────────────┐
│ [서버 상태] [사용자 관리] [조직도 관리]                              │
├──────────────────────────────────────────────────────────────────┤
│ 포트: 9000  프로토콜 버전: 1  ● 실행 중  [서버 중지]                 │
│ ┌ 접속자 ──────┐ ┌ 서버 로그 ───────────────────────────────────┐   │
│ │ 김철수 (kim) │ │ [09:01:12] 서버 시작 (포트 9000)              │   │
│ │ 이영희 (lee) │ │ [09:03:40] kim 로그인                         │   │
│ │              │ │ [09:05:02] kim → lee, park 메시지 저장         │   │
│ └──────────────┘ └──────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────┘
```

- 창을 닫으면 "접속 중인 사용자의 연결이 모두 끊어집니다" 확인 후 종료한다.
- **관리 화면이 열리면 접속 받기를 자동으로 시작한다(U25).** 포트가 이미 쓰이고 있으면(`BindException`) 중지 상태로 열고 오류 창과 로그로 알린다. 그 뒤 [서버 시작]으로 다시 시도할 수 있다.
- **로그 범위(U29)**: 서버 시작·중지, 연결 열림·닫힘(상대 IP와 닫힌 이유), 오류, 설정 경고를 남긴다. `PING`·`PONG`(하트비트)은 남기지 않는다. 로그 화면은 최근 1000줄만 유지한다. 다음 단계에서 로그인·메시지 저장 같은 주요 사건을 더한다.
- 관리 화면과 소켓 서버는 따로 동작한다. 서버가 중지된 상태에서도 사용자와 조직도를 편집할 수 있다.
- **[서버 중지] (U8)**: 접속 받기를 멈추고 접속 중인 연결에 `BYE`("서버가 중지되었습니다")를 보낸 뒤 **모두 끊는다**(U30). 저장된 데이터는 그대로이고, [서버 시작]으로 같은 포트에서 바로 다시 열 수 있다. 클라이언트는 '연결 끊김'으로 처리해 로그인 화면으로 돌아간다.

**[사용자 관리] 탭 — 사용자 표 (DB 목록처럼)**

```
┌ 순서 ┬ 아이디 ┬ 이름   ┬ 소속 부서     ┬ 비밀번호      ┬ 상태   ┐
│ 1    │ kim    │ 김철수 │ 교무실        │ ●●●● (설정됨) │ 접속 중 │
│ 2    │ lee    │ 이영희 │ 교육정보실    │ ●●●● (설정됨) │ 접속 중 │
│ 3    │ park   │ 박민수 │ 교육정보실    │ ●●●● (설정됨) │        │
│ 4    │ choi   │ 최지훈 │ (미배치)      │ ●●●● (설정됨) │        │
└──────┴────────┴────────┴───────────────┴───────────────┴────────┘
[추가] [수정] [비밀번호 초기화] [삭제] [새로고침]
```

- 표(`JTable`)에서 직접 고치지 않고, 버튼으로 여는 창에서 고친다. 실수로 값을 바꾸는 일을 막기 위해서다.
- 비밀번호는 해시만 저장하므로 원문을 보여 줄 수 없다. '설정됨'만 표시한다.
- 열은 순서·아이디·이름·소속 부서·비밀번호·상태(삭제됨/접속 중)다(6단계에 모두 구현).
- **삭제된 사용자도 표에 보인다**(U18). 등록 순서 자리에 회색으로 '삭제됨'을 표시하고, [수정]·[비밀번호 초기화]·[삭제]는 쓸 수 없고 [복구]만 쓸 수 있다.

**사용자 추가 창**

```
┌─ 사용자 추가 ──────────────────┐
│ 이름          [ 정다은       ] │
│ 아이디        [ jung         ] │  영문 소문자·숫자, 중복 불가
│ 비밀번호      [ ●●●●         ] │  4자 이상
│ 비밀번호 확인 [ ●●●●         ] │
│              [저장]  [취소]    │
└────────────────────────────────┘
```

- [저장]을 누르면 검사 후 `users.txt` 맨 아래에 추가하고 **바로 파일에 저장**한다. 새 사용자는 조직도의 '미배치'에 들어간다.
- 검사 (U17): 아이디 **영문 소문자·숫자 3~20자**, 아이디 중복(**삭제된 아이디 포함**), 이름 **앞뒤 공백을 뺀 1~20자, `|`·줄바꿈 금지**, 비밀번호 4자 이상, 두 비밀번호 일치. 하나라도 어기면 저장하지 않고 어느 칸이 왜 잘못됐는지 안내한다.
- **수정**: 이름만 바꾼다(이름 규칙은 추가와 같음). 아이디는 메시지 파일 곳곳에 기록되므로 바꿀 수 없다.
- **비밀번호 초기화**: 새 비밀번호를 두 번 입력받아 새 솔트로 다시 해시한다.
- **삭제**: 확인 후 `users.txt`에서 **`deleted`로 표시**하고(줄은 남김) 조직도에서 뺀다. 접속 중이면 `BYE`("계정이 삭제되었습니다")를 보낸 뒤 연결을 끊는다(U30). 이미 저장된 메시지는 지우지 않는다. 같은 아이디는 다시 쓸 수 없다. 그 사람의 대기 파일(`receipts`, `pending`)은 남겨 두고(U19), 보낸 사람 화면에는 '삭제된 사용자'로 표시된다(U4).
- **복구** (U18): 삭제된 사용자를 다시 활성으로 바꾼다. **새 비밀번호를 두 번 입력**받아 새 솔트로 해시한다(예전 비밀번호를 그대로 살리지 않음). 등록 순서는 원래 자리를 유지하고, 조직도에는 '미배치'로 돌아온다. 남겨 둔 대기 파일 덕분에 삭제 전에 못 받은 메시지와 읽음 알림을 다음 로그인 때 받는다.
- **파일 저장** (U20): 저장할 때마다 `users.txt`를 통째로 다시 쓰되, 읽을 때 기억해 둔 **맨 위 주석 블록**(`#`으로 시작하는 줄)은 그대로 다시 쓴다. 읽을 때 형식 오류로 건너뛴 줄이 있었으면, 서버 실행 후 **처음 저장하기 직전에** 원래 파일을 `users.txt.bak`으로 복사해 두고 서버 로그에 경고한다(건너뛴 줄이 사라지기 전에 보관).
- 저장에 실패하면(디스크 오류 등) 메모리의 사용자 목록도 바꾸기 전으로 되돌리고 오류 창을 띄운다. 메모리와 파일이 어긋나지 않게 하기 위해서다.
- 비밀번호는 해시로만 저장하므로 길이 상한과 문자 제한을 두지 않는다(4자 이상만 검사).
- `users.txt`는 서버를 켤 때 한 번만 읽는다. [새로고침]은 메모리의 목록을 표에 다시 그리기만 한다(U23). 파일이 있는데 읽지 못하면 서버를 시작하지 않는다(U22).

**[조직도 관리] 탭**

```
┌ 조직도 ─────────────────────┐   ┌ 미배치 사용자 ──┐
│ ▣ 한빛초등학교               │   │ 최지훈 (choi)  │
│  ▾ 교무실                    │   │ 정다은 (jung)  │
│     김철수 (kim)             │   │                │
│  ▾ 교육정보실                │ ◀ │                │
│     이영희 (lee)             │ ▶ │                │
│     박민수 (park)            │   │                │
│  ▸ 행정실                    │   │                │
└─────────────────────────────┘   └────────────────┘
[부서 추가] [이름 변경] [부서 삭제] [▲ 위로] [▼ 아래로]        [저장]
```

- 왼쪽 `JTree`에서 부서를 고르고 [부서 추가]하면 그 아래에 하위 부서가 생긴다. **맨 위 부서는 하나**(기관 이름)이고, 없으면 탭을 처음 열 때 서버 이름으로 만든다. 맨 위 부서는 이름만 바꿀 수 있고 삭제할 수 없다(U54).
- 부서 이름은 1~20자, `|`·`>`·줄바꿈 금지, 같은 부서 아래 같은 이름 금지(U54). 어기면 저장하지 않고 이유를 안내한다.
- [◀]: 오른쪽에서 고른 사용자를 왼쪽에서 고른 부서에 넣는다. [▶]: 부서에서 빼서 미배치로 보낸다.
- [▲ 위로] / [▼ 아래로]: 같은 부서 안에서 부서·사용자 순서를 바꾼다. 이 순서가 그대로 클라이언트 조직도 순서가 된다.
- [부서 삭제]: 하위 부서가 없을 때만 가능. 그 부서의 사용자는 미배치로 간다.
- [저장]: `org.txt`를 새로 쓰고 서버 메모리에도 바로 반영한다. 저장에 실패하면 메모리는 그대로 두고 오류 창.
- **저장하지 않고 탭을 떠나려 하면(U56)** "[저장] [버리기] [취소]"를 묻는다. 그래서 조직도를 편집하는 동안 [사용자 관리]의 변경이 끼어들지 않는다. 조직도 탭에 다시 들어오면 서버 메모리의 조직도와 최신 사용자 목록으로 다시 그린다(새 사용자·복구한 사용자는 미배치).
- **사용자를 삭제하면(U55)** 그 사람의 `U` 줄을 빼고 `org.txt`를 바로 다시 쓴다(복구하면 미배치로 돌아옴). 이 저장이 실패해도 사용자 삭제는 그대로 하고 서버 로그에 경고한다(보낼 때 걸러지므로 화면에는 나오지 않음).
- [사용자 관리] 표의 **소속 부서** 열은 부서 이름(경로의 마지막 부분)을 보여 준다. 배치되지 않았으면 `(미배치)`.

**편집 내용이 반영되는 시점**

| 바꾼 것 | 서버 | 클라이언트 |
|---|---|---|
| 사용자 추가 | 저장 즉시 로그인 가능 | 다른 사용자는 다음 로그인 때 사용자 목록에서 보임 |
| 비밀번호 초기화 | 저장 즉시 새 비밀번호로만 로그인 가능 | 접속 중인 연결은 **유지**, 다음 로그인부터 새 비밀번호 (U7) |
| 사용자 삭제 | 즉시 로그인 불가, 접속 중이면 연결 끊김 | 다음 로그인 때 목록에서 빠짐 |
| 조직도 저장 | 저장 즉시 `ORG` 요청부터 새 조직도 | 다음 로그인 때 새 조직도 (실시간 갱신은 추가 기능) |

### 3.6 동시성 규칙

여러 스레드가 동시에 같은 데이터를 건드리는 경우와, 그때 무엇이 막아 주는지 정리한다. **"절대 일어나면 안 되는 일"** 기준이다.

| # | 상황 | 막지 않으면 | 막는 곳 | 규칙 |
|---|---|---|---|---|
| C1 | lee와 choi의 `ACK`가 같은 메시지 파일을 동시에 고침 | 한쪽 `delivered`가 덮어써져 사라짐 → 재전송, 읽음 표시 오류 | `MessageStore` | 같은 메시지 ID의 "읽기 → 고치기 → 쓰기"는 그 메시지의 잠금 안에서만 |
| C2 | lee가 로그인하는 순간 kim이 lee에게 `SEND` | 서버가 lee를 오프라인으로 보고 안 보냄 + 로그인 쪽 밀린 메시지 조회는 저장 전에 끝남 → **다음 로그인까지 메시지 안 옴** | `LoginService`, `MessageService` | 로그인: **세션 등록 먼저 → 밀린 메시지 조회**. 보내기: **파일 저장 먼저 → 접속 확인**. 두 작업이 어떻게 겹쳐도 둘 중 하나는 반드시 메시지를 본다. 두 번 보내지는 경우는 클라이언트가 `messageId`로 거른다 |
| C3 | 같은 아이디 재로그인 후, 옛 연결의 정리 코드가 늦게 실행됨 | 옛 연결이 새 연결을 접속자 목록에서 지우고 `PRESENCE offline` 전송 → 접속 중인데 메시지를 못 받음 | `SessionRegistry` | 해제는 "이 아이디의 **현재 연결이 바로 나일 때만**" 한다. 아이디만이 아니라 연결 객체로 비교 |
| C4 | 로그인 때 `receipts/kim.txt`를 보내는 도중 새 `RECEIPT`가 추가됨 | "다 보낸 뒤 비우기"에서 새 줄까지 지워짐 → 읽음 알림 유실 | `ReceiptQueue` | "추가"와 "꺼내고 비우기"를 같은 아이디별 잠금으로 묶는다 |
| C5 | `LOGIN_OK`의 접속자 목록을 만든 직후 다른 사람이 로그인 | 그 사람의 `PRESENCE`를 못 받아 오프라인으로 보임 | `SessionRegistry` | 등록과 접속자 목록 만들기를 한 잠금 안에서. 등록 이후 일어난 변화는 내 `SendQueue`로 들어오므로 빠지지 않는다 |
| C6 | 느린 수신자(10MB 내려받는 중)에게 다른 스레드가 패킷을 보내려 함 | 보내는 스레드가 몇 초씩 멈춤 | `SendQueue` | 다른 스레드는 대기열에 넣기만 한다. 실제 쓰기는 그 연결의 보내기 스레드만 |
| C7 | 관리 화면에서 사용자 삭제와 그 사용자의 요청이 동시에 일어남 | 삭제된 사용자의 메시지가 저장됨 | `UserDirectory`, `SessionRegistry` | 삭제는 "삭제됨 표시 → 연결 끊기" 순서. 서비스는 요청을 처리할 때 보낸 사람이 아직 활성인지 확인한다 |
| C8 | 관리 화면(Swing 스레드)과 소켓 스레드가 사용자 목록을 동시에 읽고 씀 | 반쯤 바뀐 목록을 읽음 | `UserDirectory` | 모든 읽기·쓰기를 `synchronized` 메서드로만. 목록을 밖으로 줄 때는 복사본을 준다 |
| C9 | 소켓 스레드가 Swing 화면을 직접 고침 | 화면이 깨지거나 가끔 멈춤 (Swing은 스레드 안전하지 않음) | `ServerEventListener`, 클라이언트 `ClientController` | 화면 변경은 항상 `SwingUtilities.invokeLater()`로 Swing 스레드에 맡긴다 |
| C10 | 같은 사람에게 새 메시지(색인 추가)와 ACK(색인 삭제)가 동시에 일어남 | 삭제하려고 파일을 다시 쓰는 사이에 추가된 줄이 사라짐 → 그 메시지가 색인에서 빠져 재전송되지 않음 | `PendingIndex` | 같은 아이디의 추가·삭제·목록 읽기는 아이디별 잠금 안에서만 |
| C11 | 메시지를 저장한 뒤 색인에 쓰기 전에 서버가 꺼짐 | 메시지는 있는데 아무도 받지 못함 | `PendingIndex.rebuild` | 정상 종료 표시(`.clean`)가 없으면 시작할 때 메시지 파일 기준으로 색인을 다시 만든다 (3.8.6) |

**잠금을 걸 때 지킬 것**

- **잠금 안에서는 네트워크로 보내지 않는다.** 보낼 패킷은 잠금을 푼 뒤 `SendQueue`에 넣는다. 잠금을 쥔 채 느린 작업을 하면 다른 스레드가 줄줄이 멈춘다.
- **잠금은 가능하면 겹쳐 잡지 않는다.** 하나를 푼 뒤에 다음 것을 잡는다(3.8). 꼭 두 개를 함께 쥐어야 하면 `UserDirectory` → `MessageStore`(메시지 ID) → `PendingIndex`(아이디) → `ReceiptQueue`(아이디) 순서로만 잡는다. 순서가 엇갈리면 서로를 기다리며 영원히 멈추는 교착 상태(deadlock)가 생긴다.

### 3.7 예외 처리 목록

과제 요구사항 "예외 처리 및 안정성"(잘못된 입력, 존재하지 않는 데이터, 파일 오류)에 대응한다. 서버와 클라이언트를 함께 정리한다.

**잘못된 입력**

| 상황 | 처리 | 사용자에게 보이는 것 | 상태 |
|---|---|---|---|
| 관리자 비밀번호 설정: 4자 미만, 두 입력 불일치 | 저장하지 않고 다시 입력받음 | 오류 창 | 구현됨 |
| 관리자 로그인 5번 실패 | 서버 종료 | 오류 창 | 구현됨 |
| 사용자 추가: 빈 이름·아이디, 아이디 형식 오류, 아이디 중복(삭제된 아이디 포함), 비밀번호 4자 미만·불일치 | 저장하지 않음 | 어느 칸이 왜 잘못됐는지 안내 | 구현 (1단계) |
| 클라이언트 로그인: 빈 서버 IP·아이디·비밀번호 | 서버에 요청하지 않음 | 입력 칸 안내 | 구현 (2·3단계) |
| 메시지 보내기: 받는 사람 없음, 참조만 있음, 받는 사람+참조 100명 초과, 빈 본문(공백뿐 포함), 본문 1MB 초과 | 클라이언트에서 먼저 막고, 서버도 `SEND_FAIL` (U5) | 작성 창에 무엇이 잘못됐는지 안내 | 구현 (4단계) |
| 메시지 보내기: `messageId`가 UUID 형식이 아님, 다른 사람이 이미 쓴 ID | `SEND_FAIL` (파일 경로 조작 방지, U35) | — (정상 클라이언트는 생기지 않음) | 구현 (4단계) |
| 잘못된 패킷: 길이 상한 초과, 헤더 형식 오류 | 서버가 그 연결을 끊음 (메모리 폭주 방지) | 서버 로그 | 구현 (2단계) |
| 알 수 없는 명령, 로그인 전 요청 | `ERROR` 응답 | — | 구현 (2·3단계) |

### 3.8 MessageStore와 미전달 색인

로그인한 사용자에게 "아직 받지 않은 메시지"를 찾아 보내는 방법과, 메시지 파일을 안전하게 고치는 방법을 정한다 (결정 U14~U16).

#### 3.8.1 왜 색인이 필요한가

- 색인이 없으면 lee가 로그인할 때 `data/messages/`의 **모든 메시지 파일을 열어** `delivered.lee=false`인지 확인해야 한다. 비용이 O(전체 메시지 수)다.
- "로그아웃 이후에 보낸 메시지만 본다"는 방법도 검토했지만, **시각으로 '받았는지'를 추정**하는 방식이라 메시지가 빠지는 경우가 있다 (개발일지 2026-11-15).
  - 접속 중에 보냈는데 ACK 전에 끊긴 메시지는 보낸 시각이 로그아웃보다 앞이라 빠진다.
  - PC 강제 종료는 서버가 90초 뒤에야 알아차리므로, 그 사이에 보낸 메시지가 빠진다.
  - 서버 시계가 뒤로 가면 빠진다.
  - 메시지 파일 이름이 UUID라 "이후 메시지"를 고르려 해도 결국 모든 파일을 열어야 한다.
- 그래서 **사용자별 미전달 색인**을 둔다. 메시지를 저장할 때 받는 사람마다 "아직 안 받은 메시지 목록"에 ID를 한 줄 추가하고, **그 사람의 ACK가 왔을 때만** 지운다. 시각은 쓰지 않는다.

#### 3.8.2 핵심 원칙: 메시지 파일은 "사실", 색인은 "찾기 위한 목록"

- 받았는지에 대한 진짜 기록은 메시지 파일의 `delivered.{아이디}`다. 색인은 그것을 빨리 찾기 위한 **보조 목록**이다.
- 두 파일이 어긋나면 **메시지 파일을 기준으로 색인을 다시 만든다.** 그래서 색인은 망가져도 되살릴 수 있다.
- 쓰는 순서는 항상 **메시지 파일 먼저 → 색인 나중**이다. 중간에 꺼져도 "메시지는 있는데 색인이 없거나, 이미 받았는데 색인에 남은" 상태만 생기고, 둘 다 복구하거나 무시할 수 있다(3.8.5).

#### 3.8.3 파일

```
data/
├─ messages/{messageId}.txt     메시지 (사실)
├─ pending/{아이디}.txt          그 사람이 아직 받지 않은 messageId 목록 (색인)
├─ pending/.clean               서버가 정상 종료했다는 표시
└─ receipts/{아이디}.txt         (2.6 밀린 읽음 알림)
```

`pending/lee.txt` — 한 줄에 messageId 하나, 저장된 순서대로

```
3f2a9c1e-8b4d-4c1a-9e2f-1a2b3c4d5e6f
7b1c0d2e-1111-4a7b-8c9d-0e1f2a3b4c5d
```

- 같은 ID가 두 번 들어 있을 수 있다(복구·재전송 때). 읽을 때 `LinkedHashSet`으로 중복을 없애고 순서는 유지한다.
- 삭제된 사용자의 색인 파일은 **지우지 않는다**(U19). 삭제된 동안에는 로그인할 수 없어 쓰이지 않고, 되살리면 못 받은 메시지를 그대로 이어서 받는다.

#### 3.8.4 클래스

| 클래스 | 역할 | 이렇게 둔 이유 |
|---|---|---|
| `MessageStore` | 메시지 파일 만들기·읽기·상태 바꾸기(`create`, `load`, `markDelivered`, `markRead`) | 메시지 파일을 고치는 코드를 한 곳에 모아, 잠금을 빠뜨릴 수 없게 한다 |
| `StoredMessage` | 메시지 파일 한 개를 읽은 결과 = `MessageData` + 받는 사람별 `delivered`·`readAt`. 받는 사람별 상태(`DeliveryState`) 계산 | `MessageData`는 Common 공용이라 서버 전용 정보를 넣지 않는다(1.2). 서버 전용 정보는 이 클래스가 감싼다 |
| `PendingIndex` | `pending/{아이디}.txt` 추가·삭제·목록, 전체 다시 만들기(`rebuild`) | 색인 규칙을 한 곳에 모은다. `ReceiptQueue`와 같은 "사용자별 파일" 구조 |
| `LockStripes` | 잠금 64개를 미리 만들어 두고, ID의 해시값으로 하나를 고른다 | 아래 설명 |

**잠금: `LockStripes` (결정 11을 구체화, U16)**

- 메시지 ID마다 잠금 객체를 새로 만들면, 메시지 수만큼 잠금이 계속 늘어나 지워지지 않는다.
- 대신 잠금 **64개를 고정**해 두고 `ID의 해시값 % 64`로 하나를 고른다. 서로 다른 두 메시지가 같은 잠금에 걸리면 잠깐 줄을 설 뿐, 결과가 틀리지는 않는다.
- `MessageStore`(메시지 ID 기준)와 `PendingIndex`(아이디 기준)가 각자 하나씩 가진다.
- **두 잠금을 겹쳐 쥐지 않는다.** 메시지 잠금을 푼 뒤에 색인 잠금을 잡는다. 동시에 두 개를 쥐는 일이 없으므로 교착 상태(deadlock)가 생기지 않는다.

#### 3.8.5 동작별 순서와 "여기서 꺼지면?"

**① 보내기 (`SEND`)** — `MessageService.send()`

| 순서 | 하는 일 | 잠금 | 이 단계 직후 서버가 꺼지면 |
|---|---|---|---|
| 1 | 검사 (U5: 받는 사람, 인원, 본문) | — | 아무것도 남지 않음. 클라이언트는 10초 뒤 실패 처리, 같은 `messageId`로 다시 보낼 수 있음 |
| 2 | 메시지 파일 저장 (`sentAt` 결정, `delivered.*=false`). **같은 ID 파일이 이미 있으면 저장하지 않고 기존 `sentAt`을 돌려줌** (재전송 중복 방지) | 메시지 | 메시지는 있는데 색인이 없음 → 비정상 종료이므로 다음 시작 때 색인을 다시 만들어 복구 (3.8.6) |
| 3 | 받는 사람·참조마다 `pending/{아이디}.txt`에 ID 한 줄 추가 (2에서 중복이었으면, 아직 안 받았는데 색인에 없는 사람만 다시 넣음 — U45) | 아이디 (한 명씩) | 일부 사람만 추가됨 → 위와 같이 복구 |
| 4 | `SEND_OK`를 보낸 사람의 대기열에 넣기 | — | 클라이언트가 `SEND_OK`를 못 받음 → 재전송 → 2에서 중복으로 걸러짐 |
| 5 | 받는 사람 중 접속 중인 사람에게 `MSG`를 대기열에 넣기 (C2: **저장 먼저, 접속 확인 나중**) | — | 받는 사람은 다음 로그인 때 색인으로 받음 |

**② 로그인 때 밀린 메시지 보내기** — `MessageService.deliverPendingAsync()` (U44)

| 순서 | 하는 일 | 잠금 |
|---|---|---|
| 1 | 세션 등록 (C2: **등록 먼저**) | `SessionRegistry` |
| 2 | `PendingIndex.list(lee)` → 중복을 없앤 messageId 목록 | 아이디 (읽기만) |
| 3 | 각 ID마다 `MessageStore.load()` → `MSG`를 대기열에 넣기. 파일이 없거나 손상됐으면 색인에서 지우고 로그. **로그인 처리와 별도 작업으로 하고, 대기열이 절반(250개) 이상 차 있으면 빌 때까지 기다렸다가 넣는다**(U36) | 메시지 (읽기만) |
| 4 | 밀린 `RECEIPT` 보내기 (2.6) | `ReceiptQueue` 아이디 |

- 1과 2 사이에 새 메시지가 오면, 그 메시지는 `SEND`의 5단계와 이 2단계 양쪽에서 보내질 수 있다. 클라이언트가 `messageId`로 중복을 거르므로 괜찮다(C2).

**③ 수신 확인 (`ACK`)** — `MessageService.ack()`

| 순서 | 하는 일 | 잠금 | 이 단계 직후 서버가 꺼지면 |
|---|---|---|---|
| 1 | `MessageStore.markDelivered(id, lee)`: 파일 읽기 → lee가 받는 사람·참조가 아니면 무시 → 이미 `true`면 변경 없음 → `true`로 바꿔 저장 | 메시지 | 아무것도 바뀌지 않음 → 다음 로그인 때 다시 보냄 → 클라이언트는 중복이라 저장하지 않고 ACK만 다시 보냄 |
| 2 | `PendingIndex.remove(lee, id)`: 색인 파일에서 그 줄을 빼고 다시 저장(`AtomicFile`) | 아이디 | 파일은 `true`인데 색인에 남음 → 다시 만들 때 빠지고, 그 전에 로그인하면 다시 보내지지만 클라이언트가 중복으로 거름 |
| 3 | 1에서 실제로 바뀌었을 때만 보낸 사람에게 `RECEIPT(DELIVERED)` (접속 중이면 대기열, 아니면 `ReceiptQueue`) | — | 알림만 빠짐 → 보낸 사람이 메시지를 열 때 `STATUS`로 맞춰짐 |

**④ 읽음 (`READ`)** — ③과 같은 순서. 1단계에서 `delivered`가 아직 `false`면 함께 `true`로 바꾸고(2.6), `readAt`이 없으면 기록한다. 색인에서도 지운다.

**⑤ 상태 조회 (`STATUS`)** — 메시지 잠금 안에서 읽기만 하고, 받는 사람별 상태를 계산한다. 삭제된 사용자는 `DELETED`(U4).

#### 3.8.6 정상 종료 표시와 색인 복구 (U15)

```
[서버 시작] 버튼
 ├─ pending/.clean 있음 → 지난번에 정상 종료 → 색인을 그대로 믿고 .clean을 지움
 └─ .clean 없음 (처음 실행, 강제 종료, 정전)
      → 색인 다시 만들기 (PendingIndex.rebuild)
         1. pending/ 폴더의 색인 파일을 모두 지움
         2. messages/의 메시지 파일을 한 번씩 읽어, delivered.{아이디}=false인 사람의 색인에 ID 추가
            (삭제된 사용자도 포함 — U19, 손상된 파일은 건너뛰고 로그)

[서버 중지] 버튼, 관리 화면 종료
 → 모든 연결을 끊고(U8), 연결이 다 닫히고 처리 중인 SEND·ACK가 끝난 뒤 pending/.clean 만들기 (U43)
    (중지 중에 온 SEND는 SEND_FAIL "서버가 중지 중입니다", 관리 화면 종료는 이 작업을 최대 5초 기다림)
```

- 실행 중에는 `.clean`이 없다. 그래서 실행 중 어느 순간에 꺼지더라도, 다음 시작 때 반드시 다시 만들기를 한다.
- **정상 중지가 작업 중간에 끼지 않게(U43)**: `SEND`·`ACK`는 읽기 잠금, 저장소 열기(시작)·닫기(중지)는 쓰기 잠금을 잡는다(`ReentrantReadWriteLock`). 그래서 "메시지는 저장했는데 색인은 아직 안 쓴" 순간에 `.clean`이 만들어지지 않는다. `ServerListener`는 저장소를 모르고 `StorageHooks`(열기·닫기 약속)만 부른다.
- 다시 만들기는 전체 메시지를 훑지만 **비정상 종료 뒤에 한 번**만 한다. 매번 하면 메시지가 쌓일수록 서버 시작이 느려진다.
- 색인에 한 줄 추가하는 쓰기(파일 끝에 덧붙이기)는 원자적이지 않아 꺼지면 반쯤 쓴 줄이 남을 수 있다. 그런데 이때는 `.clean`이 없으므로 다시 만들기가 그 파일을 통째로 새로 쓴다.

#### 3.8.7 비용 비교

| 작업 | 색인 없이 | 색인 사용 |
|---|---|---|
| 로그인 때 밀린 메시지 찾기 | O(전체 메시지 수) 파일 열기 | **O(내 미전달 메시지 수)** |
| 보내기 | 메시지 파일 1개 쓰기 | 메시지 파일 1개 + 받는 사람 수만큼 색인에 한 줄 추가 |
| ACK | 메시지 파일 1개 다시 쓰기 | 메시지 파일 1개 + 내 색인 파일 다시 쓰기 (내 미전달 수만큼) |
| 서버 시작 | — | 정상 종료 뒤: 거의 0 / 비정상 종료 뒤: O(전체 메시지 수) 한 번 |

쓰기를 조금 늘리는 대신 가장 자주 일어나는 "로그인 때 찾기"를 빠르게 한다. DB의 인덱스와 같은 교환 관계다.

## 4. 클라이언트 설계

### 4.1 클래스 구조

**의존 방향**

```
 ┌──────┐   부름    ┌──────────────────┐   부름   ┌───────┐
 │  ui  │─────────▶│ ClientController │────────▶│  net  │
 └──────┘◀─────────└──────────────────┘◀────────└───────┘
     invokeLater로 화면 갱신     │          ServerEventListener로 알림
                                ▼
                        ┌──────────────┐
                        │ store, model │
                        └──────────────┘
```

| 패키지 | 클래스 | 역할 | 이렇게 둔 이유 |
|---|---|---|---|
| `coolmsg.client` | `ClientMain` | 시작점. 수업 예제 `MyFrame`은 삭제(U27) — 2단계 구현 | |
| | `ClientController` | **화면·통신·보관함 사이의 중재자.** 서버 알림을 받아 "보관함 저장 → `ACK` → 화면 갱신" 순서를 책임진다. **프로그램 생명주기도 여기 한 곳에 모은다**: 로그인·로그아웃·연결 끊김 처리, "메인 창 닫기 요청"(`requestCloseMainWindow`)과 "프로그램 종료"(`shutdown`) (U33) | 저장 먼저·ACK 나중 순서가 메시지 유실을 막는 핵심이라 한 곳에서만 지킨다. 종료 경로가 한 곳이라 나중에 트레이로 바꿀 때 이 두 메서드만 바꾸면 된다 |
| `coolmsg.client.net` | `Connection` | 소켓 + 받기 스레드 + 보내기 대기열 + `reqId` 대기표. 요청마다 10초 시간 제한(U10), 서버 침묵 90초 판정(U32), `BYE` 처리(U30) — 3단계 구현 | 서버와 같은 구조(받기 1, 보내기 1)라 이해하기 쉽다 |
| | `ServerApi` | `login()`, `logout()`, `heartbeat()` 등 요청 메서드 모음. 응답을 기다린다 — 3단계 구현(로그인) | 화면 코드가 패킷 형식을 몰라도 요청할 수 있다 |
| | `ServerEventListener` (인터페이스) | 서버가 먼저 보내는 것(`MSG`, `PRESENCE`, `RECEIPT`, 연결 끊김)을 받는 약속 | 통신 코드가 컨트롤러·화면을 직접 몰라도 알릴 수 있다 |
| | `Heartbeat` | 로그인 중 30초마다 `PING` — 3단계 구현 | |
| | `ConnectionTester` | 연결 테스트 (짧은 별도 연결). 결과: 성공(서버 이름·버전·응답 시간) 또는 실패 원인 — 2단계 구현 | 로그인 연결과 섞이지 않게 |
| | `ServerAddress` | 서버 칸의 `IP` 또는 `IP:포트`를 해석 (포트 생략 시 9000, IPv6 미지원) — 2단계 구현 | 입력 해석 규칙을 한 곳에 (U26) |
| `coolmsg.client.store` | `Mailbox` | `inbox/`, `sent/` 보관함. `messageId` 중복 확인, 상태는 앞으로만 갱신. 지운 메시지는 `deleted.txt`에 ID만 남겨 다시 받아도 저장하지 않음(U38) | 파일 형식은 Common의 `HeaderBodyFile` 사용 |
| | `ClientSettings` | 마지막 서버 주소·아이디를 `~/.coolmsg/client.txt`에 저장(키=값, 로그인 성공 때만) | |
| | `ClientPaths` | 클라이언트 저장 위치를 한 곳에서 정함: 사용자 홈 폴더 아래 `.coolmsg/` (U34) | 실행 위치와 상관없이 항상 같은 곳에 저장 |
| `coolmsg.client.model` | `UserEntry`, `Directory` | 사용자 한 명(아이디·이름·접속 상태), 사용자 목록 + 접속 상태 + 조직도 (메모리) — 3단계: `UserEntry`만, `Directory`는 5·6단계 | 조직도 화면과 받는 사람 선택 창이 같은 데이터를 본다 |
| `coolmsg.client.ui` | `LoginFrame`, `ConnectionTestDialog`, `MainFrame`(체크박스 조직도 `OrgCheckTree`, U53), `MessageManagerFrame`(받은·보낸 탭 + 오른쪽 본문, U48), `ComposeFrame`(받는 사람·참조 칸, 회신), `RichTextEditor`(서식 편집기, U58), `Toast`(알림 창), `WrapLayout`, `TransferDialog`(확장) | 화면. 별도 메시지 보기 창은 없앴다(U48) | |

**스레드 구성**

| 스레드 | 하는 일 |
|---|---|
| Swing 스레드 | 화면. 여기서 오래 걸리는 일(통신 대기)을 하지 않는다 |
| 받기 스레드 | 모든 패킷 읽기 → 응답이면 대기표에, 알림이면 `ServerEventListener`로 |
| 보내기 스레드 | 보내기 대기열에서 꺼내 소켓에 쓰기 |
| 하트비트 | 30초마다 `PING` |
| `SwingWorker` | 로그인·보내기·연결 테스트처럼 응답을 기다리는 작업 (화면이 멈추지 않게) |

**새 메시지가 왔을 때의 흐름 (가장 중요한 순서)**
```
받기 스레드: MSG 수신
  → ClientController.onMessage()
      1. Mailbox에 이미 있나, 지운 메시지인가(deleted.txt)? → 그렇다면 3번으로 (저장 안 함)
      2. Mailbox.inbox에 저장 (AtomicFile) → 실패하면 여기서 끝 (ACK 안 함 → 다음 로그인 때 다시 옴)
      3. ACK를 보내기 대기열에 넣기
      4. 새로 저장했을 때만 SwingUtilities.invokeLater(목록·개수 갱신, 1초 묶어 알림 창)
```

- 보관함(`Mailbox`)과 `ServerApi`는 **`LOGIN`을 보내기 전에** 준비한다. `LOGIN_OK` 바로 뒤에 밀린 `MSG`가 와서, 화면 전환보다 먼저 받기 스레드가 저장하려 하기 때문이다(U46).
- 받은 메시지는 메시지 관리함에서 **줄을 고를 때** 읽음으로 표시한다(U48). 5단계에서는 이때 한 번만 `READ`를 보낸다(U46, REQ-F-116).

### 4.2 로컬 보관함

사용자 PC에 사용자별로 **보낸 내역**과 **받은 내역**을 텍스트 파일로 저장한다. 파일 형식은 서버의 메시지 파일과 같다.

```
~/.coolmsg/{내 아이디}/       (사용자 홈 폴더, 예: C:\Users\홍길동\.coolmsg\kim\)
├─ inbox/{messageId}.txt   받은 내역
├─ sent/{messageId}.txt    보낸 내역
└─ deleted.txt             지운 받은 메시지의 ID 목록 (한 줄에 하나, U38)
```

- 아이디별로 폴더를 나누므로 한 PC에서 여러 아이디로 클라이언트를 띄워 테스트해도 보관함이 섞이지 않는다.


- 저장 항목: 메시지 ID, 상대방, 시각, 본문, 첨부파일 정보(ID, 파일 이름, 크기, 만료 시각)
- 첨부파일 원본은 저장하지 않는다. 사용자가 링크를 누르면 서버에서 내려받는다.
- 사용자가 삭제하면 로컬 보관함에서만 지운다.
- 같은 메시지를 두 번 받아도(ACK 전송 실패 후 재전달 등) 메시지 ID로 확인해 중복 저장하지 않는다.
- **지운 메시지가 되살아나지 않게(U38)**: 받은 메시지를 지우면 메시지 파일은 지우고, 그 `messageId`만 `deleted.txt`에 한 줄 남긴다. 같은 ID의 `MSG`가 다시 오면(지우기 전에 보낸 ACK가 유실된 경우) 저장하지 않고 `ACK`만 보낸다. 내용은 PC에 남지 않고 ID만 남는다.
- 받은 내역 파일에는 `read=true/false`(내가 읽었는지)와 `readReported=true/false`(서버에 `READ`를 알렸는지, U49)를 기록한다. `READ`는 한 번만 보내고, 끊겨서 못 알린 것은 다음 로그인 때 다시 보낸다.
- 보낸 내역 파일에는 `RECEIPT`·`STATUS_OK`로 받은 받는 사람별 상태(`state.{아이디}`, `readAt.{아이디}`)를 기록한다. 기록된 상태보다 앞선 상태일 때만 바꾼다.

### 4.3 화면 설계
**로그인 화면 (첫 화면)**

```
┌──────────── CoolMsg ────────────┐
│ 서버 IP  [ localhost          ] │
│ 아이디   [                    ] │
│ 비밀번호 [                    ] │
│                                 │
│   [연결 테스트]      [로그인]    │
└─────────────────────────────────┘
```

- **[연결 테스트]**: 서버 연결 테스트 창을 띄운다 (프로토콜 2.4).
- **서버 IP 칸**: `192.168.0.10`처럼 IP만 쓰면 포트 9000, `192.168.0.10:9100`처럼 쓰면 그 포트로 접속한다(U26). 형식이 틀리면 접속하지 않고 안내한다.
- **[로그인]**: `LOGIN` 요청. 성공하면 메인 화면으로 이동하고, 실패하면 이유를 표시한다.
- 접속 중 연결이 끊기면(서버 중지, 네트워크 문제, 하트비트 끊김) 안내 후 이 화면으로 돌아온다. 서버 IP·아이디는 채워 두고 비밀번호는 다시 입력받는다. 비밀번호는 메모리에도 들고 있지 않는다(U9).
- 마지막에 입력한 서버 주소와 아이디는 **로그인에 성공했을 때** `~/.coolmsg/client.txt`에 저장해 다음 실행 때 채워 둔다(U34). **비밀번호는 저장하지 않는다.**
- 서버가 `BYE`로 연결을 끊으면 그 이유(다른 곳에서 로그인, 계정 삭제, 서버 중지)를, 그 밖의 이유로 끊기면 "서버와 연결이 끊겼습니다"를 보여 주고 이 화면으로 돌아온다(U9, U30).
- **메인 창**: 메뉴의 [로그아웃]은 이 로그인 화면으로 돌아온다. 메인 창의 X 버튼은 확인 없이 로그아웃 후 프로그램을 종료한다(U33). 나중에 시스템 트레이로 바꿀 수 있도록, X 버튼은 `ClientController`의 "메인 창 닫기 요청"만 부른다.
- 계정은 사용자가 직접 만들지 않고, 관리자가 서버 관리 화면에서 만들어 준다(회원가입 버튼 없음).

**서버 연결 테스트 창**

```
┌──── 서버 연결 테스트 ────┐
│ 대상: 192.168.0.10:9000  │
│                          │
│ ✔ 연결 성공               │
│   서버 이름: CoolMsg 서버 │
│   프로토콜 버전: 1        │
│   응답 시간: 12ms         │
│                          │
│        [다시 시도] [닫기] │
└──────────────────────────┘
```

- 실패하면 원인별 안내를 보여 준다 (연결 거부 / 시간 초과 / 주소 오류 / 버전 다름).

**메인 화면 — 조직도**

```
┌──────── 조직도 ────────┐        ┌──── 조직도 (임시 표시) ────┐
│ ▣ 한빛초등학교     │        │ ⚠ 조직도 설정을 받지 못해   │
│  ▸ 교무실              │        │   등록 순서로 표시합니다.   │
│  ▾ 교육정보실           │        │ ● 김철수 (kim)             │
│     ● 이영희            │        │ ○ 이영희 (lee)             │
│     ○ 박민수            │        │ ○ 박민수 (park)            │
│  ▸ 행정실              │        │                           │
│  ▸ 미배치              │        │                           │
└────────────────────────┘        └───────────────────────────┘
       ORG_OK를 받았을 때                  ORG_NONE·시간 초과일 때
```

- `JTree`로 부서 트리를 그린다. 이름 앞에 온라인(●)/오프라인(○)을 표시하고, `PRESENCE`를 받으면 해당 사용자만 갱신한다.
- **체크박스 트리(U53)**: 부서와 사람 모두 이름 옆에 체크박스가 있다. 계층은 트리 그대로(펼치기·접기).
  - 부서를 체크하면 그 부서와 하위 부서의 사람이 **모두** 체크된다(나도 포함). 풀면 모두 풀린다.
  - 부서 체크박스는 사람들의 상태로 정해진다: 모두 ☑ / 일부 ▣ / 없음 ☐. 일부(▣)인 부서를 누르면 모두 체크.
  - 같은 사람은 한 부서에만 있으므로(3.2) 중복은 생기지 않는다.
  - 체크하고 [메시지 쓰기]를 누르면 체크된 사람들이 받는 사람으로 채워진 작성 창이 열리고, **체크는 모두 풀린다**. 아무도 체크하지 않으면 받는 사람 없는 작성 창.
  - 임시 표시(조직도를 못 받음)도 같은 체크박스 방식의 한 줄 목록이다.
  - 나를 체크하면 나에게도 보내진다(보낸 내역과 받은 내역에 모두 저장). 작성 창의 전용 "나에게 보내기" 체크박스(REQ-F-125)는 여전히 보류.
- **미배치** 부서는 맨 아래에, 배치되지 않은 사람이 있을 때만 보인다.
- 임시 표시일 때는 위쪽에 안내 문구를 보여 준다.

**메시지 관리함 — 받은 메시지 / 보낸 메시지 탭**

- 받은 메시지: 안 읽은 메시지는 굵게 표시한다.
- 보낸 메시지: 받는 사람이 여러 명이어도 **메시지 하나당 한 줄**만 표시한다. 목록에는 읽음 요약을 보여 준다.

```
┌ 받는 사람        ┬ 날짜/시간        ┬ 읽음 ┐
│ 이영희 외 2명    │ 2026-11-12 15:30 │ 1/3  │
│ 김철수           │ 2026-11-12 14:02 │ 1/1  │
└──────────────────┴──────────────────┴──────┘
```

**메인 창과 메시지 관리함 (U39~U42, U48, 구현 4단계)**

```
┌─ CoolMsg - 김철수 (kim) ─────┐
│ 파일                         │
│ ┌ 사용자 ────────────────┐   │
│ │ ● 김철수 (kim)         │   │
│ │ ○ 이영희 (lee)  ☑      │   │
│ │ ○ 박민수 (park) ☑      │   │
│ └────────────────────────┘   │
│ [메시지 쓰기] [메시지 관리함 (3)]│
└──────────────────────────────┘

┌─ 메시지 관리함 (받은 메시지 12개, 안 읽음 3개) ─────────────────────────────────────┐
│ [받은 메시지 (3)] [보낸 메시지]                                                      │
│ ┌ 보낸 사람 ┬ 날짜/시간        ┬ 내용 ───────┐ ┌─────────────────────────────────┐ │
│ │ 이영희    │ 2026-11-23 15:30 │ 회의 자료…  │ │ 보낸 사람  이영희 (lee)            │ │

│ └──────────┴──────────────────┴─────────────┘ └─────────────────────────────────┘ │
│                                                                       [삭제] [닫기] │
└──────────────────────────────────────────────────────────────────────────────────┘
```

- **화면 구성(U39, U48)**: 메인 창에는 사용자 목록(6단계에 조직도)과 [메시지 쓰기]·[메시지 관리함] 버튼을 둔다. 메시지 관리함은 [받은 메시지]/[보낸 메시지] 탭이 있는 **별도 창**이다. 관리함 안은 **왼쪽 목록 표 + 오른쪽 본문 영역**으로 나눈다(학교 메신저와 같은 배치). **별도의 메시지 보기 창은 없다.**
  - 목록에서 줄을 고르면 오른쪽에 머리글(보낸 사람, 받는 사람, 참조, 보낸 시각)과 본문을 보여 준다. 받는 사람·참조는 이름 상자로 보여 주고, 폭이 모자라면 다음 줄로 넘긴다(`WrapLayout`).
  - 아무것도 고르지 않았으면 오른쪽에 "메시지를 고르면 여기에 내용이 보입니다"를 보여 준다.
  - 아래 단추: 4단계는 [삭제] [닫기]. [회신] [전체회신] [전달]은 7단계에 [삭제] 앞에 추가한다. 학교 메신저의 [저장]·[메모저장], 별표, 검색은 요구사항에 없어 넣지 않는다.
  - 받은 메시지를 **고르는 즉시 읽음**으로 표시한다(굵게 → 보통, 안 읽은 개수 감소). 5단계에서는 이때 한 번만 `READ`를 보낸다(U46 변경).
  - 지우면 목록에서 바로 아래 줄(없으면 위 줄)을 고른다. 창 제목에 받은 메시지 수와 안 읽은 수를 보여 준다.
  - 탭을 바꾸면 그 탭에서 고른 줄의 내용을 보여 준다. 보낸 메시지 탭의 오른쪽 본문 아래에는 5단계에 읽음 확인이 붙는다.
- **받는 사람 고르기(U40)**
  - 메인 창 사용자 목록에서 여러 명을 고르고(Ctrl·Shift 클릭) [메시지 쓰기]를 누르면, 그 사람들이 받는 사람 칸에 채워진 작성 창이 열린다. **6단계부터는 조직도의 체크박스로 고른다(U53).**
  - 작성 창의 [받는 사람 선택]은 **메인 창과 같은 체크박스 조직도 창**을 연다(U57). 지금 받는 사람은 체크된 채로 열리고, 그 사람의 부서는 모두/일부로 보인다. 부서를 체크하면 그 부서 모두. [확인]하면 체크된 사람이 받는 사람이 된다(이미 있던 사람은 순서 유지, 새로 고른 사람은 조직도 순서로 뒤에). 조직도를 못 받았으면 등록 순서 목록(임시 표시). 받는 사람 칸의 이름 옆 `×`로도 뺄 수 있다.
  - 아이디를 직접 입력하지 않으므로 오타가 없다. 삭제된 사용자는 목록에 없다.
- **목록 표시(U42)**
  - 받은 메시지: 보낸 사람 | 날짜·시간 | 내용 미리보기(본문 앞 30자, 태그 제외)
  - 보낸 메시지: 받는 사람(여러 명이면 "이영희 외 2명") | 날짜·시간 | 내용 미리보기. 읽음 요약 열은 5단계에 추가한다.
  - 최신 메시지가 위. 안 읽은 받은 메시지는 굵게. 날짜·시간은 `yyyy-MM-dd HH:mm`으로 보여 준다.
  - [삭제]는 확인 창을 거친다. 보낸 메시지를 지우면 내 보낸 내역에서만 지운다(REQ-F-106).
  - 줄을 두 번 눌러도 따로 창을 열지 않는다(내용은 이미 오른쪽에 보인다).
- **받는 사람 칸의 배치**: 이름 단추(`이영희 ×`)는 창 폭이 모자라면 **다음 줄로 넘어간다**. 칸은 최대 3줄까지 늘어나고, 그보다 많으면 세로 스크롤한다(가로 스크롤 없음). 작성 창의 최소 크기는 380×300(이보다 좁으면 이름 단추 하나도 다 보이지 않음). `FlowLayout`은 필요한 높이를 항상 한 줄로 계산해 넘친 단추가 잘리므로, 폭에 맞춰 줄 수를 계산하는 `WrapLayout`을 쓴다(4단계 후 버그 수정).
- **메시지 작성 창(4단계)**: 받는 사람 칸, [받는 사람 선택], 본문(일반 텍스트 입력, 보낼 때 HTML로 바꿈 — U37), [보내기]. 보내는 동안 버튼을 막고, 실패하면 이유를 보여 주며 창을 그대로 둔다. 같은 창에서 다시 보내면 **같은 `messageId`**를 쓴다(서버가 중복을 거름, U10·U35). 서식 툴바·참조 칸은 7단계.
- **새 메시지 알림(U41)**
  - 받은 메시지 목록을 바로 갱신하고, 메인 창 버튼에 안 읽은 개수를 보여 준다: [메시지 관리함 (3)].
  - 화면 **오른쪽 아래에 작은 알림 창**을 5초 동안 띄운다. 메시지가 오면 **1초 기다려 그동안 더 온 메시지와 묶어** 한 번만 알린다(1개면 "새 메시지: 이영희", 여러 개면 "n개의 새 메시지"). 그래서 로그인 직후 밀린 메시지도 한 번만 알린다.
  - 알림 창을 누르면 메시지 관리함의 [받은 메시지] 탭을 연다. 1개면 그 메시지 줄을 골라 오른쪽에 내용을 보여 준다(그래서 읽음이 된다, U48). 소리는 내지 않고, 다른 창의 포커스를 빼앗지 않는다(입력 중인 글이 끊기지 않게).
  - 트레이를 넣을 때는 이 알림을 트레이 풍선 알림으로 바꿀 수 있다(U33).
- **읽음 알림(U51, U52, 5단계)**
  - 내가 보낸 메시지를 상대가 **읽었을 때만**(`RECEIPT state=READ`) 알림 창을 띄운다. 도착(`DELIVERED`)은 알리지 않는다. 로그인 때 오는 밀린 읽음(`queued=true`)은 목록만 갱신하고 알리지 않는다.
  - 새 메시지 알림처럼 **1초 안에 온 것은 묶어** 한 번만: 1건이면 "이영희님이 메시지를 읽었습니다"와 내용 미리보기, 여러 건이면 "n건의 읽음 알림".
  - 누르면 메시지 관리함의 [보낸 메시지] 탭을 연다. 1건이면 그 메시지 줄을 골라 오른쪽에 읽음 확인까지 보여 준다.
  - **새 메시지 알림과 읽음 알림은 위아래로 쌓는다(U52)**: 종류마다 알림 창은 하나씩(같은 종류의 새 알림은 그 창을 바꿈), 둘 다 있으면 새 메시지 알림이 아래, 읽음 알림이 그 위. 하나가 닫히면 남은 것이 아래로 내려온다. 5초 뒤 각각 닫힌다.

**보낸 메시지 탭 — 오른쪽 본문 아래 읽음 확인 (5단계)**

```
┌──────────────────────────────────────────┐
│ 받는 사람: 이영희, 박민수, 최지훈          │
│ 보낸 시각: 2026-11-12 15:30               │
├──────────────────────────────────────────┤
│ 안녕하세요. 회의 자료 공유드립니다.        │
│ 📎 회의자료.pdf (200KB)                   │
├──────── 읽음 확인 (1/3) ── [새로고침] ─────┤
│ ✔ 이영희   읽음      2026-11-12 15:42     │
│ ☐ 박민수   안 읽음                         │
│ ☐ 최지훈   전송됨 (아직 받지 않음)          │
└──────────────────────────────────────────┘
```

- 서버에는 메시지 파일이 하나뿐이고, 받는 사람별 상태는 그 안에 `delivered.{아이디}`, `readAt.{아이디}`로 기록되어 있다(3.2). 그래서 보낸 내역도 자연스럽게 메시지 하나당 한 줄이 된다.
- 화면을 열 때 `STATUS`로 최신 상태를 조회하고, 열려 있는 동안 `RECEIPT`가 오면 해당 줄만 갱신한다. **[새로고침]**은 `STATUS`를 다시 보낸다.
- 받는 사람 순서는 보낼 때 고른 순서(`receivers` 순서)를 따른다.
- 서버의 보관 기간(90일)이 지나 `STATUS_FAIL`을 받으면, 마지막으로 저장해 둔 상태를 보여 주고 "더 이상 갱신되지 않음"을 표시한다.

**메시지 작성 화면 — 회신할 때**

```
┌──────────────── 메시지 작성 ─────────────────────────┐
│ 받는 사람 [ 김철수 ×                    ] [받는 사람 선택] │
│ 참    조 [                            ] [참조 선택]     │
│ [맑은 고딕▾] [3 (12pt)▾] [B] [I] [U] [S] [A▾]           │
├──────────────────────────────────────────────────────┤
│ (커서) ← 여기에 회신 내용을 입력              │
│                                             │
│ 보낸 사람: 김철수                             │
│ 보낸 시각: 2026-11-12 15:30                   │
│                                             │
│ 안녕하세요. 회의 자료 공유드립니다.            │
│ (원본 본문 전체)                              │
├─────────────────────────────────────────────┤
│                                     [보내기]         │
└──────────────────────────────────────────────────────┘
```

- 학교 메신저의 [나에게 보내기] 체크박스(REQ-F-125)와 [파일 첨부](첨부파일)는 제출 범위에서 보류라 넣지 않는다(1.3).
- **본문 HTML 정화(U59)**: 보여 줄 때(관리함 오른쪽)와 보낼 때 **허용한 서식 태그만** 남긴다. 허용: `b strong i em u s strike font(face·size·color) span(style의 color·font-size·font-family·font-weight·font-style·text-decoration) br p div hr blockquote`. 그 밖의 태그(`img`·`a`·`script`·`style`·`iframe` 등)는 지우고 안의 글자만 남긴다(`script`·`style`은 글자도 지움). 규칙은 Common `HtmlText` 하나. 서버는 본문을 검사하지 않는다(빈 본문·크기 검사만, U5).
- **서식 도구(U58)**: 글꼴(맑은 고딕·굴림·돋움·바탕·궁서), 크기 1~7단계(8·10·12·14·18·24·36pt, 기본 3), 굵게·기울임·밑줄·취소선, 글자 색(16색 팔레트). 고른 글자에 적용하고, 고른 글자가 없으면 이후 입력하는 글자에 적용한다. 받는 사람 PC에 없는 글꼴은 보이지 않을 수 있어 Windows 한글판 기본 글꼴만 둔다.
- **참조 칸(U60)**: 받는 사람 칸과 같은 모양(이름 ×, 줄 바꿈). [참조 선택]은 같은 체크박스 조직도 창. 한 사람은 받는 사람·참조 중 한 곳에만 있다(참조로 고르면 받는 사람에서 빠짐, 반대도 같음). 받는 사람 1명 이상, 합쳐서 100명 이하(U5).

- 작성 창이 열리면 커서를 맨 위 입력 공간에 둔다.
- **문단으로 시작한다**: 편집기는 빈 본문도 빈 문단으로 연다. 문단 없이 시작하면 Enter가 HTML에 줄바꿈 문자만 넣어 받는 쪽에서 띄어쓰기로 보인다. 문단 사이 기본 여백은 편집기와 받은 메시지 표시 모두 0으로 맞춰 Enter 한 번이 한 줄이 되게 한다(U62 보완).
- **원본 인용은 한 편집기 안에 있어 고칠 수 있다(U61)**. 필요 없는 부분을 지워 1MB를 넘지 않게 할 수 있다. 원본 본문은 정화(U59)한 뒤 넣는다.
- [회신]·[전체회신]은 메시지 관리함 [받은 메시지] 탭의 오른쪽 아래 단추다. 받는 사람·참조는 2.11 표대로 채운다(전체회신은 나 제외).
- 원본 작성자·시각(회색 글자), 원본 본문은 회신 본문 HTML에 그대로 들어간다. **가로줄(구분선)은 넣지 않는다**(직접 사용 후 변경, U61 보완). 원본 본문은 서식(글꼴·크기·색 등)을 유지한다.
- 전달할 때는 원본 정보에 `받는 사람:` 줄이 추가되고, 원본 첨부파일이 첨부 목록에 만료일과 함께 표시된다.

**받은 메시지 탭 — 오른쪽 아래 버튼 (7단계에 회신·전달 추가)**

- [회신] [전체회신] [삭제] [닫기] — [전달]은 첨부파일과 함께 보류(REQ-F-124)

(받은 메시지 탭의 오른쪽 영역 구성은 위 "메인 창과 메시지 관리함" 참고, U48)

## 5. 구현 전 세부 결정 (2026-11-13)

구조 검토에서 찾은 "문서에 답이 없던 것"을 구현 전에 정했다. U11~U13은 Common을 구현하면서, U14~U16은 MessageStore를 설계하면서, U17~U23은 구현 1단계를, U24~U29는 구현 2단계를, U30~U34는 구현 3단계를, U35~U42는 구현 4단계를 시작하기 전에 추가했다. U43~U47은 4단계를 구현하면서 찾은 빈틈이다(구현 후 검토 대상). U48은 직접 실행 후 바꾼 것, U49~U52는 5단계를, U53~U56은 6단계를 시작하기 전에(U57은 6단계 구현 후), U58~U61은 7단계를 시작하기 전에, U62는 7단계를 구현하면서, U63은 마무리(배포)를 시작하기 전에 정했다. 구현할 때 이 표에 없는 동작이 필요하면, 임의로 채우지 말고 이 표에 추가한 뒤 진행한다.
