## 1. 시스템 구성

```
[클라이언트 A] ──TCP──┐
                      ├── [서버] ─┬─ [메시지 저장소]   (본문)
[클라이언트 B] ──TCP──┘           └─ [첨부파일 보관소] (파일, 30일)

각 클라이언트 PC: [로컬 보관함] (보낸 내역 / 받은 내역, 본문만)
```

- 클라이언트끼리는 직접 연결하지 않고, 모든 메시지는 서버를 거친다.

### 1.1 프로젝트 구성

```
CoolMsg_JAVA/                  (Eclipse 워크스페이스 겸 VS Code 작업 폴더)
├─ docs/                       기획·설계 문서
├─ CoolMSG_JAVA_Common/        서버·클라이언트 공용 코드 (패킷, 프로토콜 상수)
│  ├─ src/coolmsg/common/
│  └─ test/coolmsg/common/     테스트 (실행 파일에 포함되지 않음)
├─ CoolMSG_JAVA_Server/        서버 프로그램  → Common 참조
│  ├─ src/coolmsg/server/
│  ├─ config/                  관리자 설정 (users.txt, org.txt는 Git에 포함, admin.txt는 제외)
│  └─ data/                    실행 중 생기는 메시지·첨부파일 — Git 제외
├─ CoolMSG_JAVA_Client/        Swing 클라이언트 → Common 참조
│  ├─ src/
│  └─ data/                    PC의 보낸 내역·받은 내역 — Git 제외
└─ .vscode/launch.json         VS Code 실행·디버그 설정 (서버, 클라이언트)
```

| 프로젝트 | 패키지 | 내용 |
|---|---|---|
| `CoolMSG_JAVA_Common` | `coolmsg.common` | 패킷 읽기·쓰기, 프로토콜 상수, 메시지 데이터 모양, "키=값+본문" 파일 형식 등 양쪽이 같은 규칙을 지켜야 하는 코드 (1.2 참고) |
| `CoolMSG_JAVA_Server` | `coolmsg.server` | **Swing 관리 화면**(서버 시작·중지, 사용자 관리, 조직도 관리), 접속 관리, 메시지 저장·전달, 첨부파일 |
| `CoolMSG_JAVA_Client` | `coolmsg.client` (예정) | Swing 화면, 로컬 보관함, 서버 통신 |

- 공용 코드는 Eclipse의 **프로젝트 참조**로 공유한다(`.classpath`의 `/CoolMSG_JAVA_Common`). 복사하지 않으므로 프로토콜을 고치면 서버와 클라이언트에 함께 반영된다.
- 실행할 때 작업 폴더는 각 프로젝트 폴더다. 그래서 아래의 `config/`, `data/` 경로는 각 프로젝트 폴더 기준이다.

### 1.2 Common 클래스 구조

**원칙: 서버와 클라이언트가 "같은 규칙"을 지켜야 하는 코드는 Common에 한 벌만 둔다.** 패킷 형식이나 파일 형식을 양쪽에서 따로 구현하면, 한쪽만 고쳤을 때 서로 말이 통하지 않는다.

| 패키지 | 클래스 | 역할 | 이렇게 둔 이유 |
|---|---|---|---|
| `coolmsg.common` | `ProtocolInfo` | 버전, 기본 포트, 크기 제한, 시간 제한 상수 | 양쪽이 같은 값을 써야 한다 |
| | `FormatException` | 패킷·파일·시각 형식 오류 (`IOException`의 하위 클래스) | 부르는 쪽이 파일·통신 오류와 같은 방식으로 처리할 수 있다 (U12) |
| `coolmsg.common.net` | `PacketType` | 명령 이름 목록 (`enum`: `PING`, `LOGIN`, `SEND` …) | 문자열 `"SNED"` 같은 오타를 컴파일 단계에서 잡는다 |
| | `Packet` | 패킷 한 개: 종류 + 헤더(순서 유지 맵) + 데이터(`byte[]`) | 패킷을 "값"으로 다루면 테스트와 로그 출력이 쉽다 |
| | `PacketReader` | `read()`: 일반 패킷을 통째로 / `readFileTo()`: 파일 데이터를 64KB씩 디스크로 (**파일 메서드는 확장 때 구현**) | 작은 패킷은 단순하게, 10MB 파일은 메모리에 올리지 않게 (결정 12) |
| | `PacketWriter` | `write()`: 일반 패킷 / `writeFile()`: 디스크에서 64KB씩 소켓으로 | 위와 같음. 진행률 표시도 여기서 알린다 |
| | `ProgressListener` | "전체 몇 바이트 중 몇 바이트" 알림 인터페이스 | 통신 코드가 화면(`JProgressBar`)을 몰라도 진행률을 알릴 수 있다 |
| `coolmsg.common.model` | `MessageData` | 메시지 하나 (ID, 보낸 사람, 받는 사람, 참조, 시각, 본문, 첨부 목록, 회신·전달 원본) | 서버 파일·클라이언트 보관함·패킷이 모두 같은 모양을 쓴다 |
| | `AttachmentInfo` | 첨부파일 정보와 `ID\|크기\|만료\|이름` 변환 | 파일 이름을 맨 뒤에 두는 규칙을 한 곳에서만 구현 |
| | `DeliveryState` | `SENT` → `DELIVERED` → `READ`, "이 상태가 더 앞선가?" 판단 | "상태는 앞으로만" 규칙(2.6)을 한 곳에서만 구현 |
| `coolmsg.common.file` | `HeaderBodyFile` | "키=값 + 빈 줄 + 본문" 파일 읽기·쓰기 | 서버 메시지 파일과 클라이언트 보관함 파일의 형식이 같다 (결정 15) |
| | `AtomicFile` | **임시 파일에 다 쓴 뒤 이름을 바꿔** 저장 | 쓰는 도중 프로그램이 꺼져도 "반쯤 쓴 파일"이 남지 않는다 |
| | `HeaderFormat` | "키=값" 줄 읽기·쓰기 규칙(U1)과 엄격한 UTF-8 해석 | 패킷 헤더(`PacketReader`)와 파일 머리글(`HeaderBodyFile`)이 **같은 규칙**을 한 곳에서 쓴다 (U11) |
| | `TimeFormat` | 시각 문자열 형식을 한 곳에서 정함: **서버 PC 현지 시각, `yyyy-MM-ddTHH:mm:ss`** (U2) | 양쪽이 다른 형식을 쓰면 만료 계산이 틀어진다 |

- `HeaderBodyFile`은 **자기가 모르는 키도 지우지 않고 그대로 보존**한다. 그래서 서버는 `delivered.*`, `access`를, 클라이언트는 `read`, `state.*`를 같은 형식 위에 덧붙여 쓸 수 있다. 서버 전용·클라이언트 전용 정보는 Common에 넣지 않는다.
- **구현 상태 (2026-11-13)**: 위 표의 클래스를 모두 구현했다. 첨부파일 전송 메서드(`readFileTo`, `writeFile`)만 확장 때 구현한다(1.3). 테스트 71개 통과([테스트 기록](04_테스트기록.md)).
- `PacketReader`는 모르는 종류(`type`)의 패킷도 예외 없이 돌려준다(`getType()`이 `null`). 서버가 연결을 끊지 않고 `ERROR`로 응답하기 위해서다(3.7). 길이나 형식이 틀린 패킷은 `FormatException`이며, 이때는 스트림 위치가 어긋났으므로 연결을 닫는다.
- Common은 Swing도, 소켓 접속도, 서버·클라이언트 코드도 모른다. **아무것에도 의존하지 않는 바닥 계층**이라서 어느 쪽에서든 가져다 쓸 수 있다.

### 1.3 제출 범위와 확장 지점

과제 제출(2026-12-11) 범위는 요구사항분석서 9.1을 따른다. 빠진 기능 중 **첨부파일은 설계 뼈대만** 만든다. 프로토콜과 데이터 형식에 자리를 미리 두어, 나중에 기능을 채울 때 파일·패킷 형식을 바꾸지 않아도 되게 하기 위해서다.

**첨부파일 뼈대의 범위**

| 위치 | 제출 때 있는 것 | 제출 때 동작 | 확장할 때 할 일 |
|---|---|---|---|
| Common | `PacketType`의 `UPLOAD`·`DOWNLOAD`·`FILE*`, `AttachmentInfo`, `MessageData`의 첨부 목록, `attachment.N` 헤더 읽기·쓰기 | 형식만 있음. 첨부 목록은 항상 비어 있음 | `PacketReader.readFileTo()`, `PacketWriter.writeFile()` 구현 |
| 서버 | `AttachmentService`, `AttachmentStore` 클래스와 메서드 선언 | `UPLOAD`·`DOWNLOAD`에는 `ERROR reason=지원하지 않는 기능`, `attachment.N`이 있는 `SEND`에는 `SEND_FAIL` | 저장, 접근 권한(`access`), 만료 처리 |
| 클라이언트 | (없음) | 작성 창에 [파일 첨부] 버튼 없음 | 첨부 버튼, 첨부 링크, `TransferDialog` |

**그 밖의 제출 후 확장 항목**

| 기능 | 제출 때 상태 |
|---|---|
| 전달 | 첨부파일 재사용과 연결되어 있어 함께 미룸. `forwardOf` 헤더 자리는 있음 |
| 나에게 보내기 | 서버는 받는 사람에 자기 자신을 허용(설계 그대로). 클라이언트에 체크 상자만 없음 |
| 본문 속 이미지, 단체 대화방 | 없음 |
| 보관 기간 정리(`RetentionCleaner`), 보관 기간 설정 | 없음. 서버 데이터가 계속 쌓임(수업 규모에서는 문제없음) |
| 관리자 비밀번호 변경 | 없음. `admin.txt`를 지우고 다시 정하는 방법은 있음 |

### 1.4 컬렉션 활용

과제 요구사항 "컬렉션 활용"에 대응한다. 모두 **제네릭으로 타입을 지정**해 잘못된 타입이 들어가는 것을 컴파일 단계에서 막는다.

| 컬렉션 | 쓰는 곳 | 고른 이유 |
|---|---|---|
| `ArrayList<UserAccount>` | `UserDirectory`의 사용자 목록 | 등록 순서를 유지해야 한다(조직도가 없을 때 등록 순서로 표시, REQ-F-021) |
| `LinkedHashMap<String, String>` | `Packet` 헤더, `HeaderBodyFile` 머리글 | 키로 빨리 찾으면서도 **적힌 순서를 유지**한다. 파일을 다시 쓸 때 줄 순서가 바뀌지 않는다 |
| `ConcurrentHashMap<String, ClientSession>` | `SessionRegistry` (아이디 → 연결) | 아이디로 바로 찾고, 여러 스레드가 동시에 읽고 써도 안전하다 |
| `ConcurrentHashMap<String, Object>` | `MessageStore`(메시지 ID별 잠금), `ReceiptQueue`(아이디별 잠금) | 잠금 객체를 키별로 하나씩 만들어 둔다 (결정 11) |
| `LinkedHashSet<String>` | `SEND`의 받는 사람·참조 정리 | 같은 사람이 두 번 들어간 것을 없애면서 고른 순서는 유지한다 |
| `BlockingQueue<Packet>` (`LinkedBlockingQueue`) | `SendQueue` | 여러 스레드가 넣고 보내기 스레드 하나가 꺼내는 구조. 비어 있으면 꺼내는 쪽이 알아서 기다린다 (결정 9) |
| `ConcurrentHashMap<Integer, 대기표>` | 클라이언트 `Connection` (`reqId` → 응답 기다리는 곳) | 받기 스레드와 요청한 스레드가 동시에 쓴다 |
| `List<AttachmentInfo>` | `MessageData`의 첨부 목록 | 순서가 있는 목록. 제출 때는 항상 비어 있음 |
| `HashSet<String>` | 첨부파일 `access` 목록 (확장) | "이 사람이 들어 있나?"를 빠르게 확인 |
| `DefaultTableModel`, `DefaultListModel` | 관리 화면의 사용자 표, 접속자 목록 | Swing 표·목록이 쓰는 데이터 모델 |

## 2. 통신 프로토콜

클라이언트와 서버는 **TCP 소켓 하나**를 로그인부터 종료까지 유지하며 **패킷**을 주고받는다.

### 2.1 패킷 구조

`DataOutputStream` / `DataInputStream`으로 아래 순서대로 쓰고 읽는다.

```
┌──────────────┬─────────────────────────┬───────────────┬──────────────────────┐
│ int 헤더길이 │ 헤더 (UTF-8 텍스트)      │ int 데이터길이 │ 데이터 (byte[])       │
│ 4바이트      │ "키=값" 줄들            │ 4바이트       │ 없으면 길이 0         │
└──────────────┴─────────────────────────┴───────────────┴──────────────────────┘
```

- **헤더**: 메시지 파일의 머리글과 같은 `키=값` 형식이다. 첫 줄은 항상 `type=명령`이다.
- **헤더 규칙 (U1, 엄격)** — 패킷 헤더와 파일 머리글에 똑같이 적용한다.
  - 줄바꿈은 `\n`만 쓴다. `\r`이 섞여 있으면 형식 오류.
  - 키와 값은 **처음 나오는 `=`에서만** 나눈다. 값 안의 `=`는 그대로 값이다(예: `reason=a=b`의 값은 `a=b`).
  - 같은 키가 두 번 나오면 형식 오류.
  - 값에 줄바꿈이 들어 있으면 **쓰기 전에 예외**를 던진다. 잘못된 패킷은 아예 만들어지지 않는다.
  - 이유: 형식이 조금 틀린 입력을 받아 주면 버그가 조용히 넘어가 나중에 엉뚱한 곳에서 터진다. 엄격하게 거부하면 문제가 생긴 그 자리에서 드러난다.
- **데이터**: 메시지 본문(HTML, UTF-8)이나 첨부파일 내용(바이너리)을 담는다.
- 길이를 먼저 보내는 이유: 본문에 줄바꿈이 있어도, 데이터가 이미지 같은 바이너리여도 어디까지가 한 패킷인지 정확히 알 수 있다. 받는 쪽은 `readInt()`로 길이를 읽고 `readFully()`로 그만큼 읽는다.
- **안전 장치**: 헤더는 최대 64KB, 데이터는 최대 11MB(첨부 10MB + 여유)로 제한한다. 이보다 큰 길이가 오면 잘못된 패킷으로 보고 연결을 끊는다(메모리 폭주 방지).
- 이 형식을 읽고 쓰는 `Packet` 클래스는 서버와 클라이언트가 **같은 코드를 공유**한다.

**예시: 메시지 보내기 패킷**

```
[헤더]
type=SEND
reqId=7
messageId=3f2a9c1e-8b4d-4c1a-9e2f-1a2b3c4d5e6f
receivers=lee,park
attachment.0=a81b0c2d-...

[데이터]
안녕하세요 <font color="red">중요 공지</font>입니다.
```

### 2.2 요청 번호(reqId)와 서버가 먼저 보내는 패킷

서버는 클라이언트가 요청하지 않아도 새 메시지(`MSG`), 접속 상태 변경(`PRESENCE`), 수신·읽음 알림(`RECEIPT`)을 **언제든 보낼 수 있다.** 그래서 클라이언트가 `SEND`를 보내고 응답을 기다리는 사이에 다른 패킷이 먼저 도착할 수 있다.

- 클라이언트는 요청마다 `reqId`(1부터 증가하는 번호)를 붙이고, 서버는 응답에 같은 `reqId`를 붙인다.
- 클라이언트는 **수신 전용 스레드 하나**가 모든 패킷을 읽는다.
  - `reqId`가 있는 응답 → 그 요청을 기다리던 쪽에 전달
  - `MSG` → 받은 내역에 저장하고 `ACK` 전송
  - `PRESENCE` → 조직도의 온라인 표시 갱신
  - `RECEIPT` → 보낸 내역의 수신·읽음 상태 갱신
  - 화면 갱신은 `SwingUtilities.invokeLater()`로 Swing 스레드에서 한다.

### 2.3 명령 목록

프로토콜 버전: **1** (`PONG`, `LOGIN`에서 확인)

**클라이언트 → 서버 (요청)**

| type | 헤더 | 데이터 | 서버 응답 | 로그인 전 |
|---|---|---|---|---|
| `PING` | `reqId` | 없음 | `PONG` | **가능** |
| `LOGIN` | `reqId`, `version`, `userId`, `password` | 없음 | `LOGIN_OK` / `LOGIN_FAIL` | **가능** |
| `UPLOAD` | `reqId`, `fileName` | 파일 내용 | `UPLOAD_OK` / `UPLOAD_FAIL` | 불가 |
| `SEND` | `reqId`, `messageId`, `receivers`, `cc`, `replyTo`, `forwardOf`, `attachment.N` | 본문 HTML | `SEND_OK` / `SEND_FAIL` | 불가 |
| `DOWNLOAD` | `reqId`, `attachmentId` | 없음 | `FILE` / `FILE_EXPIRED` / `FILE_DENIED` | 불가 |
| `ACK` | `messageId` | 없음 | 없음 | 불가 |
| `READ` | `messageId` | 없음 | 없음 | 불가 |
| `STATUS` | `reqId`, `messageId` | 없음 | `STATUS_OK` / `STATUS_FAIL` | 불가 |
| `ORG` | `reqId` | 없음 | `ORG_OK` / `ORG_NONE` | 불가 |
| `LOGOUT` | 없음 | 없음 | 없음 (서버가 연결 종료) | 불가 |

- `password`는 사용자가 입력한 비밀번호 원문이다. 서버는 `users.txt`의 솔트로 해시를 만들어 저장된 해시와 비교한다(3.2 참고). 원문은 저장하지 않는다.
- 통신을 암호화(TLS)하지 않으므로 같은 네트워크에서 패킷을 엿보면 비밀번호가 보일 수 있다. 수업 과제 범위의 알려진 한계다.
- 아이디가 없는 경우와 비밀번호가 틀린 경우 모두 `LOGIN_FAIL reason=아이디 또는 비밀번호가 틀렸습니다`로 똑같이 응답한다. 어느 쪽이 틀렸는지 알려 주면 있는 아이디를 알아내는 데 쓰일 수 있기 때문이다.
- 로그인 전에 '불가' 명령을 보내면 서버는 `ERROR`로 응답한다.
- `UPLOAD`·`DOWNLOAD`와 `FILE*` 응답은 **제출 범위에서 형식만 정의**되어 있다. 서버는 `ERROR reason=지원하지 않는 기능`으로 응답한다(1.3 참고).

**서버 → 클라이언트 (응답)**

| type | 헤더 | 데이터 | 의미 |
|---|---|---|---|
| `PONG` | `reqId`, `serverName`, `version`, `serverTime` | 없음 | 서버가 살아 있음 (연결 테스트·하트비트) |
| `LOGIN_OK` | `reqId` | 사용자 목록 + 접속 상태 | 로그인 성공, 이어서 밀린 `MSG`를 보냄 |
| `LOGIN_FAIL` | `reqId`, `reason` | 없음 | 아이디 또는 비밀번호 불일치(없는 아이디·삭제된 아이디 포함, **모두 같은 문구**), 프로토콜 버전 불일치 |
| `UPLOAD_OK` | `reqId`, `attachmentId`, `expiresAt` | 없음 | 업로드 성공 |
| `UPLOAD_FAIL` | `reqId`, `reason` | 없음 | 10MB 초과 등 |
| `SEND_OK` | `reqId`, `messageId`, `sentAt` | 없음 | 서버에 저장 완료 → 보낸 내역에 저장 |
| `SEND_FAIL` | `reqId`, `reason` | 없음 | 없는 받는 사람, 없는 첨부파일 ID, 접근 권한 없는·만료된 첨부파일 등 |
| `FILE` | `reqId`, `attachmentId`, `fileName` | 파일 내용 | 첨부파일 다운로드 |
| `FILE_EXPIRED` | `reqId`, `attachmentId` | 없음 | 30일이 지나 삭제됨 |
| `FILE_DENIED` | `reqId`, `attachmentId` | 없음 | 이 파일이 첨부된 메시지를 보내거나 받은 적이 없음 |
| `STATUS_OK` | `reqId`, `messageId`, `state.{아이디}`, `readAt.{아이디}` | 없음 | 받는 사람별 상태 (2.6 참고) |
| `STATUS_FAIL` | `reqId`, `reason` | 없음 | 보낸 사람이 아님, 보관 기간(90일)이 지나 삭제됨 |
| `ORG_OK` | `reqId` | 조직도 데이터 (`org.txt` 형식) | 서버 설정대로 조직도 표시 (2.10 참고) |
| `ORG_NONE` | `reqId`, `reason` | 없음 | 조직도 설정 없음·읽기 실패 → 등록 순서로 임시 표시 |
| `ERROR` | `reqId`(있으면), `reason` | 없음 | 로그인 전 요청, 알 수 없는 명령 등 |

**서버 → 클라이언트 (서버가 먼저 보냄)**

| type | 헤더 | 데이터 | 보내는 때 |
|---|---|---|---|
| `MSG` | `messageId`, `sender`, `receivers`, `cc`, `sentAt`, `replyTo`, `forwardOf`, `attachment.N` | 본문 HTML | 새 메시지가 왔을 때 → 클라이언트는 저장 후 `ACK` |
| `PRESENCE` | `userId`, `online` (`true`/`false`) | 없음 | 누군가 로그인·로그아웃하거나 연결이 끊겼을 때, 접속 중인 **모든** 사용자에게 |
| `RECEIPT` | `messageId`, `userId`, `state` (`DELIVERED`/`READ`), `at` | 없음 | 받는 사람이 `ACK`·`READ`를 보냈을 때 보낸 사람에게. 보낸 사람이 오프라인이면 모아 두었다가 **로그인할 때** 보냄 (2.6 참고) |

**사용자 목록 형식** (`LOGIN_OK`의 데이터): 한 줄에 한 명, `아이디|이름|online` (등록 순서). 솔트·해시는 보내지 않는다. 부서는 조직도(`ORG_OK`)로 받는다.

```
kim|김철수|true
lee|이영희|false
```

**첨부파일 헤더 형식**: `attachment.0=attachmentId|크기|만료시각|파일이름`

- 파일 이름에 `|`나 `,`가 들어갈 수 있어서 **파일 이름을 맨 뒤**에 둔다. 앞의 세 칸만 `|`로 자르고 나머지는 전부 파일 이름으로 본다.
- `SEND`에서는 `attachment.0=attachmentId`만 보내고, 서버가 나머지 정보를 채워 `MSG`로 전달한다.

### 2.4 서버 연결 테스트

로그인 화면의 **[연결 테스트]** 버튼을 누르면 테스트 창을 띄우고, 입력한 서버 IP로 연결되는지 확인한다. 로그인과는 **별개의 짧은 연결**이다.

```
클라이언트                                       서버
  │ IP:9000에 연결 (제한 3초)                      │
  │── PING (reqId=1) ───────────────────────────▶│
  │◀──── PONG (reqId=1, serverName, version, serverTime)
  │ 응답 시간 계산 후 연결 종료                     │
```

| 결과 | 원인 (Java 예외) | 테스트 창 표시 |
|---|---|---|
| 성공 | — | 연결 성공, 서버 이름, 프로토콜 버전, 응답 시간(ms) |
| 버전 다름 | `PONG`의 `version`이 1이 아님 | 서버와 프로그램 버전이 다름 |
| 연결 거부 | `ConnectException` | 서버가 꺼져 있거나 포트가 다름 |
| 시간 초과 | `SocketTimeoutException` (연결 3초, 응답 3초) | IP가 틀렸거나 방화벽이 막음 |
| 주소 오류 | `UnknownHostException` | 서버 주소를 찾을 수 없음 |

- 연결 시간 제한은 `socket.connect(new InetSocketAddress(ip, 9000), 3000)`, 응답 시간 제한은 `socket.setSoTimeout(3000)`으로 건다.
- 테스트는 Swing 스레드가 아닌 별도 스레드(`SwingWorker` 등)에서 실행한다. 그래야 최대 6초 동안 창이 멈추지 않는다.

### 2.5 접속 상태 (온라인/오프라인)

조직도에 누가 온라인인지 표시한다. **상태는 바뀔 때만 서버가 알려 주고, 클라이언트는 살아 있다는 신호만 주기적으로 보낸다.**

**방식 비교**

| 방식 | 동작 | 문제점 |
|---|---|---|
| 클라이언트가 주기적으로 조회 | 모든 클라이언트가 20~30초마다 "누가 온라인이야?" 요청 | 아무 변화가 없어도 계속 요청이 오고, 상태 변화가 최대 30초 늦게 보인다. |
| 서버가 주기적으로 전체 목록 전송 | 서버가 30초마다 모두에게 목록 전송 | 변화가 없어도 매번 전송한다. |
| **서버가 바뀔 때만 전송 (채택)** | 로그인·로그아웃이 생길 때만 `PRESENCE` 한 개 전송 | 연결이 조용히 끊긴 경우를 알아차리지 못한다 → **하트비트**로 보완 |

서버는 소켓 연결을 이미 갖고 있으므로 **누가 접속 중인지 원래 알고 있다.** 그래서 물어볼 필요 없이 바뀔 때만 알려 주면 된다. 부하는 시간이 아니라 로그인·로그아웃 횟수에 비례하고, 패킷 하나가 수십 바이트라 사내 규모(수백 명)에서는 문제가 없다.

**하트비트: 클라이언트가 주기적으로 보내는 것은 '살아 있음' 신호다**

- PC가 갑자기 꺼지거나 랜선이 빠지면 TCP는 연결이 끊긴 것을 한동안 알아차리지 못한다. 그러면 서버는 그 사람을 계속 온라인으로 보여 준다.
- 그래서 로그인한 클라이언트는 **30초마다 `PING`**을 보낸다.
- 서버는 한 클라이언트에게서 **90초 동안 아무 패킷도 오지 않으면** 연결을 끊고, 모두에게 `PRESENCE online=false`를 보낸다.
  - 구현: 서버에서 클라이언트별 소켓에 `socket.setSoTimeout(90000)`을 걸면, 90초 동안 읽을 것이 없을 때 `SocketTimeoutException`이 발생한다.

**흐름**
```
lee                            서버                          kim (접속 중)
  │── LOGIN ───────────────────▶│
  │◀── LOGIN_OK + 목록(상태 포함)│
  │                             │── PRESENCE (lee, true) ────▶│ 조직도에서 lee 온라인
  │── PING (30초마다) ─────────▶│
  │◀── PONG ────────────────────│
  ✕ (PC 강제 종료)               │
                                │ 90초 동안 패킷 없음 → 연결 종료
                                │── PRESENCE (lee, false) ───▶│ 조직도에서 lee 오프라인
```

### 2.6 수신 확인과 읽음 확인

받는 사람별로 메시지 상태를 세 단계로 관리한다.

| 상태 | 의미 | 바뀌는 때 | 보낸 사람 화면 |
|---|---|---|---|
| `SENT` | 서버에 저장됨 | `SEND_OK` | 전송됨 |
| `DELIVERED` | 받는 사람 PC에 도착함 | 받는 사람의 `ACK` | 안 읽음 |
| `READ` | 받는 사람이 열어 봄 | 받는 사람의 `READ` | 읽음 (읽은 시각) |

**`ACK`(수신 확인)와 `READ`(읽음 확인)를 나누는 이유**

- `ACK`는 "PC에 저장했다"는 신호라서 서버가 **다시 보낼지**를 판단하는 데 쓴다. `ACK`를 읽을 때 보내면, 받았지만 아직 안 읽은 메시지를 서버가 미전달로 보고 로그인할 때마다 다시 보낸다.
- 그래서 `ACK`는 메시지를 받아 저장하는 즉시 자동으로 보내고, `READ`는 사용자가 메시지를 열 때 보낸다.
- `READ`가 `ACK`보다 먼저 서버에 도착하면 서버는 `DELIVERED`까지 함께 처리한다.

**흐름**
```
kim (보낸 사람)                서버                           lee (받는 사람)
  │── SEND ───────────────────▶│ 저장 (lee: SENT)
  │◀── SEND_OK ─────────────────│── MSG ──────────────────────▶│ 받은 내역에 저장
  │                             │◀───────────────────── ACK ───│ (자동)
  │◀── RECEIPT (lee, DELIVERED)─│ lee: DELIVERED               │
  │    "안 읽음"                 │                              │ (사용자가 메시지 열기)
  │                             │◀──────────────────── READ ───│
  │◀── RECEIPT (lee, READ, at) ─│ lee: READ, readAt 기록        │
  │    "읽음 15:42"              │                              │
```

**보낸 사람이 오프라인일 때: 밀린 `RECEIPT`를 모아 두었다가 로그인할 때 보낸다**

- 서버는 상태를 메시지 파일에 기록하고(`delivered.{아이디}`, `readAt.{아이디}`), 보내지 못한 `RECEIPT`는 **보낸 사람별 대기 파일**에 한 줄씩 추가한다.
  - 파일: `data/receipts/{보낸 사람 아이디}.txt`
  - 한 줄 형식: `messageId|userId|state|at`
  - 보낸 사람이 접속 중이었지만 `RECEIPT`를 보내다 연결이 끊긴 경우에도 대기 파일에 넣는다.
- 보낸 사람이 로그인하면 서버는 `LOGIN_OK` → 밀린 `MSG` → **밀린 `RECEIPT`** 순서로 보내고, 다 보낸 뒤 대기 파일을 비운다.
- 클라이언트는 받은 상태를 자기 보낸 내역 파일에 기록한다. 그래서 로그인 직후부터 보낸 메시지 목록의 읽음 요약(예: `3/3`)이 맞게 표시된다.
- 메시지를 열 때의 `STATUS` 조회와 [새로고침]은 그대로 둔다. 대기 파일을 보내다 연결이 끊겨 일부를 잃더라도 이 조회로 다시 맞출 수 있다.

```
lee가 READ (kim은 오프라인)          서버
                                     │ readAt.lee 기록
                                     │ kim이 오프라인 → data/receipts/kim.txt 에 추가
                                     │   3f2a9c1e-...|lee|READ|2026-11-12T18:05:40
          ⋮ (다음 날)
kim ── LOGIN ──────────────────────▶│
kim ◀── LOGIN_OK ───────────────────│
kim ◀── MSG ... (kim이 받을 메시지)  │
kim ◀── RECEIPT (3f2a9c1e-..., lee, READ, 18:05:40)
                                     │ kim.txt 비우기
```

**상태는 앞으로만 바뀐다**

- 상태는 `SENT` → `DELIVERED` → `READ` 한 방향으로만 바뀐다. 클라이언트는 받은 상태가 **지금 기록된 상태보다 앞설 때만** 반영한다.
- 그래서 같은 `RECEIPT`가 두 번 오거나(대기 파일 + `STATUS`), `DELIVERED`가 `READ`보다 늦게 와도 결과가 같다.
- 보관 기간이 지나 보낸 내역에 없는 `messageId`의 `RECEIPT`는 무시한다.
- 받는 사람이 삭제되면 `STATUS_OK`에 그 사람을 `state.{아이디}=DELETED`로 알려 준다. 보낸 사람 화면은 '삭제된 사용자'로 표시하고 읽음 요약의 분모에서 뺀다(U4). `DELETED`는 저장되는 상태가 아니라 `STATUS` 응답에서만 쓰는 표시다.

**`STATUS_OK` 예시**
```
type=STATUS_OK
reqId=12
messageId=3f2a9c1e-...
state.lee=READ
readAt.lee=2026-11-12T15:42:07
state.park=DELIVERED
```

### 2.7 주요 흐름

**로그인과 밀린 메시지 받기**
```
클라이언트(lee)                          서버
  │── LOGIN (reqId=1, version=1, userId=lee, password) ─▶│ 버전 → 아이디·비밀번호 확인
  │◀──── LOGIN_OK (reqId=1) + 사용자 목록·상태 │── PRESENCE (lee, true) → 접속 중인 모두
  │◀──── MSG (messageId=A) ──────────────────│ delivered.lee=false 인 메시지
  │── ACK (messageId=A) ───────────────────▶│ delivered.lee=true → 보낸 사람에게 RECEIPT
  │◀──── MSG (messageId=B) ──────────────────│
  │── ACK (messageId=B) ───────────────────▶│
  │◀──── RECEIPT (messageId=C, kim, READ) ───│ data/receipts/lee.txt 의 밀린 알림
  │                                         │ (lee가 보낸 메시지 C를 kim이 읽음)
  │                                         │ 다 보낸 뒤 lee.txt 비우기
```

- 순서: `LOGIN_OK` → 밀린 `MSG`(받을 메시지) → 밀린 `RECEIPT`(내가 보낸 메시지의 수신·읽음 알림)

**첨부파일이 있는 메시지 보내기**
```
클라이언트(kim)                         서버                      lee (접속 중)
  │── UPLOAD (reqId=2) + 파일 ─────────▶│ 10MB 확인, 저장
  │◀──── UPLOAD_OK (attachmentId=X) ─────│
  │── SEND (reqId=3, attachment.0=X) ──▶│ 메시지 파일 저장
  │◀──── SEND_OK (reqId=3, sentAt) ──────│
  │  보낸 내역에 저장                     │── MSG ──────────────────▶│
  │                                      │◀────────────────── ACK ──│
  │◀──── RECEIPT (lee, DELIVERED) ───────│
```

### 2.8 규칙과 예외 처리

| 상황 | 처리 |
|---|---|
| `messageId`는 누가 만드나 | **클라이언트**가 UUID로 만든다. `SEND_OK`를 못 받아 다시 보내도 서버는 같은 ID가 이미 있으면 새로 저장하지 않고 `SEND_OK`만 다시 보낸다(중복 방지). |
| `sentAt`, `readAt`은 누가 정하나 | **서버**가 정한다. PC마다 시계가 다를 수 있기 때문이다. |
| 같은 아이디로 두 번 로그인 | 기존 연결을 끊고 새 연결을 허용한다. 이때는 `PRESENCE`를 보내지 않는다(계속 온라인). |
| ACK 전에 연결이 끊김 | `delivered`가 false로 남아 다음 로그인 때 다시 보낸다. 클라이언트는 이미 받은 `messageId`면 저장하지 않고 `ACK`만 보낸다. |
| 같은 메시지를 여러 번 열어 봄 | `READ`는 처음 한 번만 보낸다(받은 내역 파일에 읽음 여부 기록). 서버도 `readAt`이 이미 있으면 바꾸지 않는다. |
| 업로드는 했는데 `SEND`를 안 보냄 | 첨부파일은 30일 뒤 자동 삭제되므로 따로 처리하지 않는다. |
| 하트비트가 90초 동안 없음 | 서버가 연결을 끊고 `PRESENCE online=false`를 보낸다. 클라이언트는 "서버와 연결이 끊겼습니다"를 알리고 로그인 화면으로 돌아간다(자동 재접속 없음, U9). |
| 여러 스레드가 한 클라이언트에 동시에 보냄 | 연결마다 **보내기 대기열(`SendQueue`)과 보내기 전용 스레드**를 둔다. 다른 스레드는 대기열에 넣기만 하므로 패킷이 섞이지 않고, 느린 수신자 때문에 멈추지도 않는다. (예: kim의 스레드와 park의 스레드가 동시에 lee에게 `MSG`·`PRESENCE`를 보내는 경우, 3.6 참고) |
| 보낸 사람이 오프라인일 때 생긴 수신·읽음 | 서버가 `data/receipts/{보낸 사람}.txt`에 모아 두었다가 로그인할 때 `RECEIPT`로 보내고 비운다. |
| 같은 `RECEIPT`가 두 번 오거나 순서가 뒤바뀜 | 클라이언트는 기록된 상태보다 앞선 상태(`SENT` → `DELIVERED` → `READ`)만 반영하므로 결과가 같다. |
| `SEND` 검사 (U5) | 받는 사람 1명 이상 필수(참조만으로는 불가), 받는 사람+참조 합계 100명 이하, 없는·삭제된 아이디 불가, 본문이 비었거나 공백뿐이면 불가, 본문 1MB(UTF-8) 이하. 하나라도 어기면 `SEND_FAIL`(무엇이 잘못됐는지 `reason`에 적음). 중복된 아이디는 하나로 합친다. |
| 응답이 오지 않는 요청 (U10) | 클라이언트는 요청마다 **10초** 시간 제한을 두고, 넘으면 실패로 처리해 화면에 알린다. `reqId` 없는 `ERROR`는 로그만 남긴다. 보내기가 시간 초과로 실패해도 같은 `messageId`로 다시 보내면 서버가 중복을 거른다. |
| 삭제된 사용자에게 가던 메시지 (U4) | 메시지 파일은 그대로 둔다. 보낸 사람의 읽음 확인에는 '삭제된 사용자'로 표시하고 읽음 요약(예: 1/3)의 분모에서 뺀다. 그 사람의 `receipts` 대기 파일은 지운다. |

### 2.10 조직도

조직도의 부서 구조와 표시 순서는 **서버의 조직도 설정 파일(`org.txt`)**을 따른다. 설정을 받지 못하면 **사용자 등록 순서**로 보여 준다.

**흐름**
```
클라이언트                               서버
  │── LOGIN ──────────────────────────────▶│
  │◀──── LOGIN_OK + 사용자 목록 (등록 순서) │
  │── ORG (reqId=2) ──────────────────────▶│ 서버 메모리의 조직도 (org.txt와 같음)
  │◀──── ORG_OK (reqId=2) + 조직도 데이터   │  → 정상이면 ORG_OK
  │       또는 ORG_NONE (reqId=2, reason)  │  → 파일 없음·읽기 실패면 ORG_NONE
```

**클라이언트가 조직도를 그리는 규칙**

| 상황 | 화면 |
|---|---|
| `ORG_OK`를 받음 | 설정대로 부서 트리를 그리고, 부서·사용자를 설정 파일에 적힌 순서대로 표시 |
| `ORG_NONE`을 받음, 3초 안에 응답이 없음, 데이터 형식 오류 | **임시 표시**: `LOGIN_OK`의 사용자 목록을 받은 순서(= `users.txt` 등록 순서) 그대로 한 줄 목록으로 표시 (이름과 아이디) |
| 설정에는 없지만 `users.txt`에 있는 사용자 | 조직도 맨 아래 **'미배치'** 부서에 등록 순서대로 표시 (아무도 조직도에서 빠지지 않게) |
| 설정에는 있지만 `users.txt`에 없는 아이디 | 서버가 `org.txt`를 읽을 때 건너뛰고 서버 로그에 경고 |

- 등록 순서가 지켜지려면 서버가 사용자 목록을 **순서가 유지되는 자료구조**(`ArrayList`, `LinkedHashMap`)로 들고 있어야 한다. `HashMap`은 순서가 뒤섞인다.
- 서버는 시작할 때 `org.txt`를 읽어 메모리에 둔다. 관리 화면의 [조직도 관리]에서 저장하면 파일과 메모리가 **즉시** 바뀌고, 그다음 `ORG` 요청부터 새 조직도를 보낸다(서버 재시작 불필요, 3.5 참고).
- 조직도 데이터 형식은 `org.txt`와 같다 (3.2 참고).

### 2.11 참조, 회신·전체회신, 전달, 나에게 보내기

**참조 (`cc`)**

- `SEND`와 `MSG`에 `cc`(참조 대상 아이디 목록)를 추가한다. 비어 있으면 줄을 생략한다.
- 서버의 처리(저장 후 전달, `ACK`, `READ`, `RECEIPT`)는 받는 사람과 **똑같다.** 화면에서만 '받는 사람'과 '참조'로 나누어 보여 준다.
- 보낸 메시지의 읽음 확인에는 참조 대상도 포함하고 `(참조)`라고 표시한다. 목록의 읽음 요약(예: `2/4`)도 받는 사람과 참조 대상을 합쳐 센다.
- 같은 사람이 `receivers`와 `cc`에 모두 있으면 서버는 `receivers`에만 남긴다.

**회신·전체회신** — 클라이언트 기능 (프로토콜 변경은 `replyTo` 헤더 하나)

| 기능 | 받는 사람 | 참조 |
|---|---|---|
| 회신 | 원본을 보낸 사람 | 없음 |
| 전체회신 | 원본을 보낸 사람 + 원본의 받는 사람 (나 제외) | 원본의 참조 대상 (나 제외) |

- 작성 창 본문은 **맨 위에 새로 입력할 공간**, 그 아래 **원본의 작성자와 보낸 시각**, 그 아래 **원본 본문 전체**로 채운다 (4.3 화면 참고).
- 인용한 원본도 본문의 일부로 함께 전송된다. 그래서 회신이 이어질수록 인용이 아래로 쌓인다.
- `SEND`에 `replyTo=원본 messageId`를 넣는다. 지금은 기록만 해 두고, 나중에 대화 묶어 보기에 쓸 수 있다.
- 첨부파일은 회신에 포함하지 않는다.

**전달** — 원본 본문과 첨부파일을 다른 사람에게 보낸다 *(제출 후 확장, 1.3)*

- 작성 창 본문은 회신과 같은 형태로 채우되, 원본 정보에 **받는 사람**도 함께 넣는다. 받는 사람은 비워 둔다.
- 첨부파일은 PC에 원본이 없으므로 **서버에 있는 파일 ID를 그대로 다시 쓴다** (`attachment.N=원본 attachmentId`). 파일을 다시 올리지 않는다.
- 서버는 `SEND`를 받으면 각 첨부파일을 확인한다.
  - 보내는 사람이 그 파일에 **접근할 수 있는 사람**이어야 한다(첨부파일 정보의 `access` 목록, 3.2 참고). 아니면 `SEND_FAIL`.
  - 만료된 파일이면 `SEND_FAIL`. 클라이언트는 작성 창을 열 때 이미 만료된 첨부파일을 빼고 "만료된 첨부파일 1개는 제외됨"을 안내한다.
- 전달한 첨부파일의 만료 시각은 **원본 업로드 기준**이다. 작성 창의 첨부파일 옆에 만료일을 표시한다.
- `SEND`에 `forwardOf=원본 messageId`를 넣는다(기록용).

**나에게 보내기** *(제출 후 확장, 1.3)*

- 작성 창의 [나에게 보내기]를 체크하면 `receivers`에 내 아이디를 넣는다. 서버는 받는 사람에 자기 자신이 있는 것을 허용한다.
- 내 PC에서는 보낸 내역(`sent/`)과 받은 내역(`inbox/`)에 각각 저장된다. 폴더가 달라 중복 저장 검사와 충돌하지 않는다.
- 내가 받은 내역에서 열면 `READ` → 나에게 `RECEIPT`가 오며, 다른 받는 사람과 똑같이 처리된다.

### 2.12 파일 전송 진행률 *(제출 후 확장, 1.3)*

파일 크기 제한(10MB)과 패킷 구조는 그대로 두고, 파일 데이터를 **64KB씩 나누어 쓰고 읽으면서** 진행률 창을 갱신한다.

- 보내기(`UPLOAD`): 헤더와 데이터 길이를 먼저 쓴 뒤, 파일을 `FileInputStream`으로 64KB씩 읽어 소켓에 쓴다. 한 번 쓸 때마다 보낸 바이트 수를 진행률 창에 알린다.
- 받기(`FILE`): 데이터 길이를 읽은 뒤 64KB씩 읽어 `FileOutputStream`으로 바로 파일에 쓴다. 파일 전체를 메모리에 올리지 않는다.
- 이 방식은 상대방 입장에서 보면 패킷 하나와 똑같아서 **프로토콜 변경이 없다.**
- 진행률 창(`JProgressBar`)에는 진행률(%), 보낸 크기 / 전체 크기, 전송 속도, 남은 시간을 표시한다. 갱신은 `SwingWorker`의 `publish()` / `process()`로 Swing 스레드에서 한다.
- **취소**: 패킷 중간에 멈추면 받는 쪽은 다음 패킷의 시작을 찾을 수 없다. 그래서 취소하면 **연결을 끊고 로그인 화면으로 돌아간다**(자동 재접속 없음, U9). 서버는 연결이 끊긴 업로드의 미완성 파일을 지운다.
- 파일을 주고받는 동안에는 같은 연결의 다른 패킷(새 메시지 알림 등)이 잠시 늦어진다. 10MB는 사내망에서 몇 초 안에 끝나므로 허용한다. 더 큰 파일을 지원하려면 파일 전용 연결을 따로 여는 방식이 필요하다(추가 기능).

## 3. 서버 설계

### 3.1 클래스 구조

서버는 **Swing GUI 관리 프로그램**이다. 관리자가 서버 PC에서 실행하고, 관리 화면에서 서버 시작·중지, 사용자 등록, 조직도 설정을 한다.

**의존 방향** — 화살표 방향으로만 알고(부르고), 반대 방향은 모른다

```
            ┌──────────┐
            │    ui    │  관리 화면 (Swing)
            └────┬─────┘
       ┌─────────┼──────────┐
       ▼         ▼          ▼
  ┌────────┐ ┌────────┐ ┌────────┐
  │  net   │─▶│service │ │ config │  사용자 목록, 조직도, 설정
  └───┬────┘ └───┬────┘ └───┬────┘
      │          ├──────────┤
      │          ▼          ▼
      │      ┌────────┐ ┌────────┐
      │      │ store  │ │security│
      │      └───┬────┘ └────────┘
      ▼          ▼
  ┌──────────────────────┐
  │  common (Common 프로젝트) │
  └──────────────────────┘
```

| 패키지 | 클래스 | 역할 | 이렇게 둔 이유 | 상태 |
|---|---|---|---|---|
| `coolmsg.server` | `ServerMain` | 시작점. 관리자 확인 → `ServerContext` 생성 → 관리 화면 | 시작 순서를 한 곳에서 본다 | 구현 (뼈대) |

| `coolmsg.server.config` | `ServerConfig` | `config/server.txt` 읽기, 없는 값은 기본값 | 포트·보관 기간을 코드 수정 없이 바꾼다 (결정 13) | 예정 |

| | `ClientSession` | 연결 하나 = 받기 스레드 + `SendQueue` + 로그인한 아이디 | 연결마다 상태를 한 객체에 모은다 | 예정 |
| | `SendQueue` | 보낼 패킷 대기열(`BlockingQueue`) + 보내기 전용 스레드 | 다른 스레드는 대기열에 넣고 바로 돌아간다. 느린 수신자 때문에 아무도 멈추지 않고, 보내는 순서도 대기열 순서로 보장된다 (결정 9) | 예정 |
| | `SessionRegistry` | "아이디 → 지금 연결" 목록. 등록·해제·전체 알림(`PRESENCE`). `Outbox`를 구현 | 접속 상태의 원본을 한 곳에 둔다 | 예정 |
| | `RequestDispatcher` | 받은 패킷의 `type`을 보고 알맞은 서비스 메서드로 넘김 | 소켓 코드와 업무 규칙을 분리한다 | 예정 |
| `coolmsg.server.service` | `LoginService` | `PING`, `LOGIN`, 로그인 직후 밀린 `MSG`·`RECEIPT` 보내기 | **업무 규칙만** 담는다. 소켓을 몰라서 화면 없이 테스트할 수 있다 | 예정 |
| | `MessageService` | `SEND`, `ACK`, `READ`, `STATUS` | 위와 같음 | 예정 |
| | `AttachmentService` | `UPLOAD`, `DOWNLOAD`, 접근 권한 | 위와 같음 | **뼈대만** (1.3) |
| | `Outbox` (인터페이스) | "이 아이디에게 이 패킷을 보내 줘" | 아래 설명 참고 | 예정 |
| `coolmsg.server.store` | `MessageStore` | 메시지 파일 생성·수정. **메시지 ID별 잠금** | 같은 메시지를 고치는 작업만 줄을 세우고 다른 메시지는 동시에 처리 (결정 11) | 예정 |
| | `AttachmentStore` | 첨부파일 본체(`.bin`)와 정보(`.meta`) | | **뼈대만** (1.3) |
| | `ReceiptQueue` | `receipts/{아이디}.txt`. **아이디별 잠금**으로 "추가"와 "보내고 비우기"를 묶음 | 비우는 순간 새로 들어온 알림이 같이 지워지지 않게 (C4) | 예정 |
| | `RetentionCleaner` | 서버 시작 때와 하루 한 번 보관 기간 정리 | | 제출 후 확장 |
| `coolmsg.server.ui` | `AdminLoginDialog`, `ServerFrame`, `StatusPanel`, `UserPanel`, `OrgPanel` | 관리 화면 | | 일부 구현 |
| | `ServerEventListener` (인터페이스) | 로그·접속자 변화 알림을 화면이 받음 | 서버 내부가 Swing을 몰라도 화면에 알릴 수 있다. 화면은 `invokeLater`로 갱신 | 예정 |

**`Outbox` 인터페이스를 두는 이유 — 순환 의존 끊기**

- `net`(소켓)은 패킷을 받으면 `service`를 부른다. 그런데 `service`도 처리 중에 다른 사람에게 패킷을 보내야 한다(예: `SEND` 처리 중 받는 사람에게 `MSG`). 그러려면 `service`가 `net`을 불러야 해서 **서로가 서로를 아는 순환**이 생긴다.
- 그래서 `service` 패키지에 `Outbox`라는 **약속(인터페이스)**만 두고, `net`의 `SessionRegistry`가 그 약속을 구현한다. `service`는 "누군가 보내 준다"는 것만 알고 소켓은 모른다.
- 덕분에 테스트할 때 `Outbox` 자리에 "보낸 패킷을 목록에 모아 두기만 하는 가짜"를 끼우면, 소켓 없이 `MessageService`를 검증할 수 있다.

**스레드 구성**

| 스레드 | 개수 | 하는 일 |
|---|---|---|
| Swing 스레드 | 1 | 관리 화면 (Swing 규칙상 화면은 이 스레드에서만 고친다) |
| 접속 받기 | 1 | `ServerListener`: `accept()`로 새 연결을 기다림 |
| 연결마다 받기 | 접속자 수 | 패킷 읽기 → `RequestDispatcher` → 서비스 |
| 연결마다 보내기 | 접속자 수 | `SendQueue`에서 꺼내 소켓에 쓰기 |
| 정리 | 1 | `RetentionCleaner` |

**시작 순서**
```
ServerMain.main()
  └─ SwingUtilities.invokeLater()            Swing 화면은 Swing 전용 스레드에서 만든다
       ├─ config/admin.txt 가 없음 → 관리자 비밀번호 설정 창 (4자 이상, 두 번 입력)
       ├─ config/admin.txt 가 있음 → 관리자 로그인 창 (5번 틀리면 종료)
       └─ 성공 → ServerContext 생성 (설정·사용자·조직도 읽기) → ServerFrame 표시
```

- 현재 코드의 `UserStore`(읽기 전용)는 `UserDirectory`를 구현할 때 그 안의 "파일 읽기·저장" 부분으로 흡수한다.

### 3.2 메시지 저장 방식

본문과 첨부파일을 **따로 저장**하고, 본문에는 첨부파일 ID 목록만 넣는다. 저장 매체는 **텍스트 파일**이다.

**메시지 (본문)**

| 항목 | 설명 |
|---|---|
| messageId | 메시지 고유 ID (`java.util.UUID`) |
| sender | 보낸 사람 아이디 |
| receivers | 받는 사람 아이디 목록 (여러 명, 나 자신 포함 가능) |
| cc | 참조 대상 아이디 목록 (없으면 줄 생략) |
| replyTo / forwardOf | 회신·전달한 원본 메시지 ID (없으면 줄 생략) |
| sentAt | 보낸 시각 |
| body | 본문 (서식 있는 텍스트, HTML 문자열) |
| attachment.N | 첨부파일 정보 `attachmentId\|크기\|만료시각\|파일이름` (프로토콜 2.3과 같은 형식) |
| delivered.{아이디} | 받는 사람·참조 대상별 전달 완료 여부 (그 사람의 ACK를 받으면 true) |
| readAt.{아이디} | 받는 사람이 읽은 시각 (그 사람의 READ를 받으면 기록, 안 읽었으면 줄 없음) |

**메시지 파일 형식** — 머리글(`키=값`) 다음 빈 줄, 그 뒤는 모두 본문

```
messageId=3f2a9c1e-...
sender=kim
receivers=lee,park
cc=choi
sentAt=2026-11-12T15:30:12
attachment.0=a81b...|204800|2026-12-12T15:30:12|회의자료.pdf
delivered.lee=true
delivered.park=false
delivered.choi=true
readAt.lee=2026-11-12T15:42:07

안녕하세요 <font color="red">중요 공지</font>입니다.
```

- 본문을 빈 줄 뒤에 두어 본문에 줄바꿈이나 `=`가 있어도 문제가 없게 한다.
- 아이디는 영문 소문자와 숫자만 허용해 `,`와 `=`가 섞이지 않게 한다.

**첨부파일** *(설계 뼈대만, 1.3)*

| 항목 | 설명 |
|---|---|
| attachmentId | 첨부파일 고유 ID |
| fileName | 원래 파일 이름 |
| size | 파일 크기 |
| uploadedAt | 업로드 시각 |
| expiresAt | 만료 시각 (업로드 후 30일, 전달해도 바뀌지 않음) |
| access | 이 파일에 접근할 수 있는 아이디 목록. **업로드할 때 올린 사람을 먼저 넣고**, 이 파일이 첨부된 메시지가 저장될 때마다 보낸 사람·받는 사람·참조 대상을 추가한다. `DOWNLOAD`와 `SEND`(첨부·전달) 때 확인 |
| 실제 파일 | 서버 보관 폴더에 `attachmentId` 이름으로 저장 |

- 최대 크기는 10MB (서버 설정값). 넘으면 업로드를 거부한다.

**사용자 목록 (`users.txt`)** — 관리 화면의 [사용자 관리]에서 추가·수정, 한 줄에 한 명 (`아이디|이름|솔트|비밀번호해시|상태`)

```
kim|김철수|6dfaf622a12019bd1d0f676016ec6564|6fe8c531475980...(64자)
lee|이영희|a457db60284bf89d9b3452f5ec832209|43f9aea4ef0b08...(64자)
```

- 소속 부서는 여기에 두지 않고 조직도(`org.txt`)에만 둔다. 같은 정보를 두 곳에 두면 한쪽만 고쳐 어긋나기 쉽다.
- **상태**: `active` 또는 `deleted`. 사용자를 삭제하면 줄을 지우지 않고 `deleted`로 바꾼다. 삭제된 아이디는 로그인·받는 사람 선택에서 빠지고, **같은 아이디로 다시 등록할 수 없다**(결정 14). 다른 사람이 같은 아이디로 등록되어 이전 사람의 미전달 메시지와 첨부파일 권한을 받는 일을 막기 위해서다.
- 5번째 칸이 없는 줄은 `active`로 읽는다(지금 예시 파일과 `UserStore`는 4칸 형식).

**비밀번호 저장** — 원문을 저장하지 않고 **솔트 + 해시**만 저장한다

| 항목 | 내용 |
|---|---|
| 방식 | `PBKDF2WithHmacSHA256` (Java 기본 라이브러리 `javax.crypto`) |
| 솔트 | 사용자마다 16바이트 무작위 값 (`SecureRandom`). 같은 비밀번호여도 해시가 달라진다. |
| 반복 횟수 | 65,536회. 일부러 느리게 만들어, 파일이 유출돼도 비밀번호를 하나씩 대입해 보기 어렵게 한다. |
| 결과 | 256비트 해시. 솔트와 해시 모두 16진수 문자열로 저장 |
| 비교 | 입력값을 같은 솔트로 해시해 `MessageDigest.isEqual()`로 비교 (비교 시간으로 정답을 추측하지 못하게) |

- 이 방식은 관리자 비밀번호(`admin.txt`)와 사용자 비밀번호(`users.txt`)에 똑같이 쓴다. 구현은 `coolmsg.server.security.PasswordHasher`.
- 저장소에 있는 예시 `users.txt`의 테스트 비밀번호는 파일 맨 위 주석에 적혀 있다.

**관리자 비밀번호 (`admin.txt`)** — 키=값 형식, **Git에 올리지 않는다**

```
salt=16진수
hash=16진수
```

**서버 설정 (`server.txt`)** — 키=값 형식, 서버 시작 때 읽음 (결정 13)

```
port=9000
serverName=CoolMsg 서버
bodyRetentionDays=90
attachmentRetentionDays=30
maxAttachmentMB=10
```

- 파일이나 항목이 없으면 `ProtocolInfo`의 기본값을 쓴다. 바꾸려면 파일을 고친 뒤 서버를 다시 켠다.
- `serverName`은 연결 테스트(`PONG`)에 표시된다.

**조직도 설정 (`org.txt`)** — 관리 화면의 [조직도 관리]에서 저장, **적힌 순서가 곧 화면 순서**

```
# D|부서 경로        (하위 부서는 > 로 구분)
# U|부서 경로|아이디  (그 부서에 속한 사용자)
D|한빛초등학교
D|한빛초등학교>교무실
U|한빛초등학교>교무실|kim
D|한빛초등학교>교육정보실
U|한빛초등학교>교육정보실|lee
U|한빛초등학교>교육정보실|park
D|한빛초등학교>행정실
U|한빛초등학교>행정실|choi
```

- `#`으로 시작하는 줄과 빈 줄은 무시한다.
- 줄마다 `|`로 나누기만 하면 되어 들여쓰기 방식보다 읽기 쉽다.
- `U` 줄의 부서 경로가 앞에서 `D`로 정의되지 않았으면 그 줄을 건너뛰고 서버 로그에 경고한다.
- 한 사용자가 여러 부서에 나오면 처음 나온 부서만 쓴다.

**서버 폴더 구조**

```
CoolMSG_JAVA_Server/
├─ config/                            관리 화면에서 편집하는 설정
│  ├─ admin.txt                       관리자 비밀번호 해시 (처음 실행 때 생성, Git 제외)
│  ├─ server.txt                      서버 설정 (포트, 서버 이름, 보관 기간, 첨부 크기)
│  ├─ users.txt                       사용자 목록 (등록 순서 = 임시 표시 순서)
│  └─ org.txt                         조직도 설정 (없어도 서버는 동작)
└─ data/                              서버가 실행 중 만드는 데이터 (Git 제외)
   ├─ messages/{messageId}.txt        메시지 (본문)
   ├─ receipts/{아이디}.txt            그 사람이 오프라인일 때 생긴 수신·읽음 알림 (로그인 때 보내고 비움)
   └─ attachments/
      ├─ {attachmentId}.meta          첨부파일 정보 (키=값)
      └─ {attachmentId}.bin           실제 파일
```

- **설정(`config/`)과 실행 데이터(`data/`)를 나눈다.** 사용자 목록과 조직도는 관리자가 관리 화면에서 고치는 설정이라 예시와 함께 Git에 올리고, 메시지·첨부파일은 실행할 때마다 생기므로 올리지 않는다.
- 단, `admin.txt`는 PC마다 관리자가 따로 정하는 값이라 Git에 올리지 않는다(`.gitignore`).
- `data/` 폴더가 없으면 서버가 시작할 때 만든다.

### 3.3 보관 기간과 삭제

| 대상 | 보관 기간 | 기간이 지나면 |
|---|---|---|
| 첨부파일 | 업로드 후 30일 | 파일 삭제, 이후 요청에는 '만료' 응답 |
| 메시지 본문 | 보낸 후 90일 (전달 여부와 관계없음) | 삭제, 그때까지 못 받은 사람은 받지 못함 |

- `RetentionCleaner`가 서버 시작 때와 하루 한 번 기간이 지난 데이터를 정리한다. 메시지 파일을 지울 때도 `MessageStore`의 메시지 ID별 잠금을 거친다(정리 중에 온 `ACK`와 겹치지 않게).
- 만료된 첨부파일의 정보(`.meta`)를 언제 지울지는 첨부파일을 확장할 때 정한다(5장 U3).
- **보관 기간 정리 전체가 제출 후 확장이다**(REQ-F-009 보류, 1.3).

### 3.5 서버 관리 화면

**관리자 확인 (서버를 켤 때)**

```
┌─ CoolMsg 서버 - 관리자 비밀번호 설정 ─┐     ┌─ CoolMsg 서버 - 관리자 로그인 ─┐
│ 처음 실행입니다. 관리자 비밀번호를     │     │ 관리자 비밀번호를 입력하세요.  │
│ 정해 주세요. (4자 이상)               │     │ [●●●●●●        ]             │
│ 비밀번호      [●●●●●●        ]        │     │          [확인]  [취소]       │
│ 비밀번호 확인 [●●●●●●        ]        │     └───────────────────────────────┘
│              [확인]  [취소]           │       틀리면 "(1/5)"처럼 남은 횟수 표시
└───────────────────────────────────────┘       5번 틀리면 서버 종료
        config/admin.txt 가 없을 때
```

- 관리자 계정은 **비밀번호 하나만** 있다(아이디 없음). 서버 PC 앞에 있는 사람만 관리 화면을 쓰기 때문이다.
- 비밀번호를 잊으면 `config/admin.txt`를 지우고 서버를 다시 실행해 새로 정한다. 서버 PC의 파일에 접근할 수 있는 사람을 관리자로 본다.

**관리 메인 창 — 탭 3개**

```
┌─ CoolMsg 서버 관리 ───────────────────────────────────────────────┐
│ [서버 상태] [사용자 관리] [조직도 관리]                              │
├──────────────────────────────────────────────────────────────────┤
│ 포트: 9000  프로토콜 버전: 1  ● 실행 중  [서버 중지]                 │
│ ┌ 접속자 ──────┐ ┌ 서버 로그 ───────────────────────────────────┐   │
│ │ 김철수 (kim) │ │ [09:01:12] 서버 시작 (포트 9000)              │   │
│ │ 이영희 (lee) │ │ [09:03:40] kim 로그인                         │   │
│ │              │ │ [09:05:02] kim → lee, park 메시지 저장         │   │
│ └──────────────┘ └──────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────┘
```

- 창을 닫으면 "접속 중인 사용자의 연결이 모두 끊어집니다" 확인 후 종료한다.
- 관리 화면과 소켓 서버는 따로 동작한다. 서버가 중지된 상태에서도 사용자와 조직도를 편집할 수 있다.
- **[서버 중지] (U8)**: 접속 받기를 멈추고 접속 중인 연결을 **모두 끊는다**. 저장된 데이터는 그대로이고, [서버 시작]으로 같은 포트에서 바로 다시 열 수 있다. 클라이언트는 '연결 끊김'으로 처리해 로그인 화면으로 돌아간다.

**[사용자 관리] 탭 — 사용자 표 (DB 목록처럼)**

```
┌ 순서 ┬ 아이디 ┬ 이름   ┬ 소속 부서     ┬ 비밀번호      ┬ 상태   ┐
│ 1    │ kim    │ 김철수 │ 교무실        │ ●●●● (설정됨) │ 접속 중 │
│ 2    │ lee    │ 이영희 │ 교육정보실    │ ●●●● (설정됨) │ 접속 중 │
│ 3    │ park   │ 박민수 │ 교육정보실    │ ●●●● (설정됨) │        │
│ 4    │ choi   │ 최지훈 │ (미배치)      │ ●●●● (설정됨) │        │
└──────┴────────┴────────┴───────────────┴───────────────┴────────┘
[추가] [수정] [비밀번호 초기화] [삭제] [새로고침]
```

- 표(`JTable`)에서 직접 고치지 않고, 버튼으로 여는 창에서 고친다. 실수로 값을 바꾸는 일을 막기 위해서다.
- 비밀번호는 해시만 저장하므로 원문을 보여 줄 수 없다. '설정됨'만 표시한다.
- 지금 구현된 열은 순서·아이디·이름·비밀번호다. 소속 부서와 상태 열은 조직도 관리와 소켓 서버를 구현할 때 추가한다.

**사용자 추가 창**

```
┌─ 사용자 추가 ──────────────────┐
│ 이름          [ 정다은       ] │
│ 아이디        [ jung         ] │  영문 소문자·숫자, 중복 불가
│ 비밀번호      [ ●●●●         ] │  4자 이상
│ 비밀번호 확인 [ ●●●●         ] │
│              [저장]  [취소]    │
└────────────────────────────────┘
```

- [저장]을 누르면 검사 후 `users.txt` 맨 아래에 추가하고 **바로 파일에 저장**한다. 새 사용자는 조직도의 '미배치'에 들어간다.
- 검사: 이름·아이디 비어 있음, 아이디 형식(`[a-z0-9]+`), 아이디 중복(**삭제된 아이디 포함**), 비밀번호 4자 이상, 두 비밀번호 일치
- **수정**: 이름만 바꾼다. 아이디는 메시지 파일 곳곳에 기록되므로 바꿀 수 없다.
- **비밀번호 초기화**: 새 비밀번호를 두 번 입력받아 새 솔트로 다시 해시한다.
- **삭제**: 확인 후 `users.txt`에서 **`deleted`로 표시**하고(줄은 남김) 조직도에서 뺀다. 접속 중이면 연결을 끊는다. 이미 저장된 메시지는 지우지 않는다. 같은 아이디는 다시 쓸 수 없다. 그 사람의 `receipts` 대기 파일은 지우고, 보낸 사람 화면에는 '삭제된 사용자'로 표시된다(U4).

**[조직도 관리] 탭**

```
┌ 조직도 ─────────────────────┐   ┌ 미배치 사용자 ──┐
│ ▣ 한빛초등학교               │   │ 최지훈 (choi)  │
│  ▾ 교무실                    │   │ 정다은 (jung)  │
│     김철수 (kim)             │   │                │
│  ▾ 교육정보실                │ ◀ │                │
│     이영희 (lee)             │ ▶ │                │
│     박민수 (park)            │   │                │
│  ▸ 행정실                    │   │                │
└─────────────────────────────┘   └────────────────┘
[부서 추가] [이름 변경] [부서 삭제] [▲ 위로] [▼ 아래로]        [저장]
```

- 왼쪽 `JTree`에서 부서를 고르고 [부서 추가]하면 그 아래에 하위 부서가 생긴다.
- [◀]: 오른쪽에서 고른 사용자를 왼쪽에서 고른 부서에 넣는다. [▶]: 부서에서 빼서 미배치로 보낸다.
- [▲ 위로] / [▼ 아래로]: 같은 부서 안에서 부서·사용자 순서를 바꾼다. 이 순서가 그대로 클라이언트 조직도 순서가 된다.
- [부서 삭제]: 하위 부서가 없을 때만 가능. 그 부서의 사용자는 미배치로 간다.
- [저장]: `org.txt`를 새로 쓰고 서버 메모리에도 바로 반영한다. 저장하지 않고 탭을 떠나려 하면 확인한다.

**편집 내용이 반영되는 시점**

| 바꾼 것 | 서버 | 클라이언트 |
|---|---|---|
| 사용자 추가 | 저장 즉시 로그인 가능 | 다른 사용자는 다음 로그인 때 사용자 목록에서 보임 |
| 비밀번호 초기화 | 저장 즉시 새 비밀번호로만 로그인 가능 | 접속 중인 연결은 **유지**, 다음 로그인부터 새 비밀번호 (U7) |
| 사용자 삭제 | 즉시 로그인 불가, 접속 중이면 연결 끊김 | 다음 로그인 때 목록에서 빠짐 |
| 조직도 저장 | 저장 즉시 `ORG` 요청부터 새 조직도 | 다음 로그인 때 새 조직도 (실시간 갱신은 추가 기능) |

### 3.6 동시성 규칙

여러 스레드가 동시에 같은 데이터를 건드리는 경우와, 그때 무엇이 막아 주는지 정리한다. **"절대 일어나면 안 되는 일"** 기준이다.

| # | 상황 | 막지 않으면 | 막는 곳 | 규칙 |
|---|---|---|---|---|
| C1 | lee와 choi의 `ACK`가 같은 메시지 파일을 동시에 고침 | 한쪽 `delivered`가 덮어써져 사라짐 → 재전송, 읽음 표시 오류 | `MessageStore` | 같은 메시지 ID의 "읽기 → 고치기 → 쓰기"는 그 메시지의 잠금 안에서만 |
| C2 | lee가 로그인하는 순간 kim이 lee에게 `SEND` | 서버가 lee를 오프라인으로 보고 안 보냄 + 로그인 쪽 밀린 메시지 조회는 저장 전에 끝남 → **다음 로그인까지 메시지 안 옴** | `LoginService`, `MessageService` | 로그인: **세션 등록 먼저 → 밀린 메시지 조회**. 보내기: **파일 저장 먼저 → 접속 확인**. 두 작업이 어떻게 겹쳐도 둘 중 하나는 반드시 메시지를 본다. 두 번 보내지는 경우는 클라이언트가 `messageId`로 거른다 |
| C3 | 같은 아이디 재로그인 후, 옛 연결의 정리 코드가 늦게 실행됨 | 옛 연결이 새 연결을 접속자 목록에서 지우고 `PRESENCE offline` 전송 → 접속 중인데 메시지를 못 받음 | `SessionRegistry` | 해제는 "이 아이디의 **현재 연결이 바로 나일 때만**" 한다. 아이디만이 아니라 연결 객체로 비교 |
| C4 | 로그인 때 `receipts/kim.txt`를 보내는 도중 새 `RECEIPT`가 추가됨 | "다 보낸 뒤 비우기"에서 새 줄까지 지워짐 → 읽음 알림 유실 | `ReceiptQueue` | "추가"와 "꺼내고 비우기"를 같은 아이디별 잠금으로 묶는다 |
| C5 | `LOGIN_OK`의 접속자 목록을 만든 직후 다른 사람이 로그인 | 그 사람의 `PRESENCE`를 못 받아 오프라인으로 보임 | `SessionRegistry` | 등록과 접속자 목록 만들기를 한 잠금 안에서. 등록 이후 일어난 변화는 내 `SendQueue`로 들어오므로 빠지지 않는다 |
| C6 | 느린 수신자(10MB 내려받는 중)에게 다른 스레드가 패킷을 보내려 함 | 보내는 스레드가 몇 초씩 멈춤 | `SendQueue` | 다른 스레드는 대기열에 넣기만 한다. 실제 쓰기는 그 연결의 보내기 스레드만 |
| C7 | 관리 화면에서 사용자 삭제와 그 사용자의 요청이 동시에 일어남 | 삭제된 사용자의 메시지가 저장됨 | `UserDirectory`, `SessionRegistry` | 삭제는 "삭제됨 표시 → 연결 끊기" 순서. 서비스는 요청을 처리할 때 보낸 사람이 아직 활성인지 확인한다 |
| C8 | 관리 화면(Swing 스레드)과 소켓 스레드가 사용자 목록을 동시에 읽고 씀 | 반쯤 바뀐 목록을 읽음 | `UserDirectory` | 모든 읽기·쓰기를 `synchronized` 메서드로만. 목록을 밖으로 줄 때는 복사본을 준다 |
| C9 | 소켓 스레드가 Swing 화면을 직접 고침 | 화면이 깨지거나 가끔 멈춤 (Swing은 스레드 안전하지 않음) | `ServerEventListener`, 클라이언트 `ClientController` | 화면 변경은 항상 `SwingUtilities.invokeLater()`로 Swing 스레드에 맡긴다 |

**잠금을 걸 때 지킬 것**

- **잠금 안에서는 네트워크로 보내지 않는다.** 보낼 패킷은 잠금을 푼 뒤 `SendQueue`에 넣는다. 잠금을 쥔 채 느린 작업을 하면 다른 스레드가 줄줄이 멈춘다.
- **잠금은 항상 같은 순서로 잡는다.** 두 잠금이 필요하면 `UserDirectory` → `MessageStore`(메시지 ID) → `ReceiptQueue`(아이디) 순서로만 잡는다. 순서가 엇갈리면 서로를 기다리며 영원히 멈추는 교착 상태(deadlock)가 생긴다.

|---|---|---|---|

| 관리자가 [서버 중지] | — | 서버가 모든 연결을 끊음. 클라이언트는 위와 같이 처리 (U8) | 예정 |
| 하트비트 90초 없음 | `SocketTimeoutException` | 서버가 연결 종료 | 예정 |
| 응답이 끝내 오지 않는 요청 | — | 10초 후 실패 처리. `reqId` 없는 `ERROR`는 로그만 (U10) | 예정 |

## 4. 클라이언트 설계

### 4.1 클래스 구조

**의존 방향**

```
 ┌──────┐   부름    ┌──────────────────┐   부름   ┌───────┐
 │  ui  │─────────▶│ ClientController │────────▶│  net  │
 └──────┘◀─────────└──────────────────┘◀────────└───────┘
     invokeLater로 화면 갱신     │          ServerEventListener로 알림
                                ▼
                        ┌──────────────┐
                        │ store, model │
                        └──────────────┘
```

| 패키지 | 클래스 | 역할 | 이렇게 둔 이유 |
|---|---|---|---|
| `coolmsg.client` | `ClientMain` | 시작점 | |
| | `ClientController` | **화면·통신·보관함 사이의 중재자.** 서버 알림을 받아 "보관함 저장 → `ACK` → 화면 갱신" 순서를 책임진다 | 이 순서(저장 먼저, ACK 나중)가 메시지 유실을 막는 핵심이라 한 곳에서만 지킨다. 화면과 통신이 서로를 몰라도 된다 |

| | `ClientSettings` | 마지막 서버 IP·아이디 | |

**스레드 구성**

| 스레드 | 하는 일 |
|---|---|
| Swing 스레드 | 화면. 여기서 오래 걸리는 일(통신 대기)을 하지 않는다 |
| 받기 스레드 | 모든 패킷 읽기 → 응답이면 대기표에, 알림이면 `ServerEventListener`로 |
| 보내기 스레드 | 보내기 대기열에서 꺼내 소켓에 쓰기 |
| 하트비트 | 30초마다 `PING` |
| `SwingWorker` | 로그인·보내기·연결 테스트처럼 응답을 기다리는 작업 (화면이 멈추지 않게) |

**새 메시지가 왔을 때의 흐름 (가장 중요한 순서)**
```
받기 스레드: MSG 수신
  → ClientController.onMessage()
      1. Mailbox에 이미 있나? → 있으면 3번으로 (중복)
      2. Mailbox.inbox에 저장 (AtomicFile)
      3. ACK를 보내기 대기열에 넣기
      4. SwingUtilities.invokeLater(받은 메시지 목록 갱신)
```

### 4.2 로컬 보관함

사용자 PC에 사용자별로 **보낸 내역**과 **받은 내역**을 텍스트 파일로 저장한다. 파일 형식은 서버의 메시지 파일과 같다.

```
CoolMSG_JAVA_Client/data/{내 아이디}/      (Git 제외)
├─ inbox/{messageId}.txt   받은 내역
└─ sent/{messageId}.txt    보낸 내역
```

- 아이디별로 폴더를 나누므로 한 PC에서 여러 아이디로 클라이언트를 띄워 테스트해도 보관함이 섞이지 않는다.


- 저장 항목: 메시지 ID, 상대방, 시각, 본문, 첨부파일 정보(ID, 파일 이름, 크기, 만료 시각)
- 첨부파일 원본은 저장하지 않는다. 사용자가 링크를 누르면 서버에서 내려받는다.
- 사용자가 삭제하면 로컬 보관함에서만 지운다.
- 같은 메시지를 두 번 받아도(ACK 전송 실패 후 재전달 등) 메시지 ID로 확인해 중복 저장하지 않는다.
- 받은 내역 파일에는 `read=true/false`를 기록해 `READ`를 한 번만 보낸다.
- 보낸 내역 파일에는 `RECEIPT`·`STATUS_OK`로 받은 받는 사람별 상태(`state.{아이디}`, `readAt.{아이디}`)를 기록한다. 기록된 상태보다 앞선 상태일 때만 바꾼다.

### 4.3 화면 설계
**로그인 화면 (첫 화면)**

```
┌──────────── CoolMsg ────────────┐
│ 서버 IP  [ localhost          ] │
│ 아이디   [                    ] │
│ 비밀번호 [                    ] │
│                                 │
│   [연결 테스트]      [로그인]    │
└─────────────────────────────────┘
```

- **[연결 테스트]**: 서버 연결 테스트 창을 띄운다 (프로토콜 2.4).
- **[로그인]**: `LOGIN` 요청. 성공하면 메인 화면으로 이동하고, 실패하면 이유를 표시한다.
- 접속 중 연결이 끊기면(서버 중지, 네트워크 문제, 하트비트 끊김) 안내 후 이 화면으로 돌아온다. 서버 IP·아이디는 채워 두고 비밀번호는 다시 입력받는다. 비밀번호는 메모리에도 들고 있지 않는다(U9).
- 마지막에 입력한 서버 IP와 아이디는 PC에 저장해 다음 실행 때 채워 둔다. **비밀번호는 저장하지 않는다.**
- 계정은 사용자가 직접 만들지 않고, 관리자가 서버 관리 화면에서 만들어 준다(회원가입 버튼 없음).

**서버 연결 테스트 창**

```
┌──── 서버 연결 테스트 ────┐
│ 대상: 192.168.0.10:9000  │
│                          │
│ ✔ 연결 성공               │
│   서버 이름: CoolMsg 서버 │
│   프로토콜 버전: 1        │
│   응답 시간: 12ms         │
│                          │
│        [다시 시도] [닫기] │
└──────────────────────────┘
```

- 실패하면 원인별 안내를 보여 준다 (연결 거부 / 시간 초과 / 주소 오류 / 버전 다름).

**메인 화면 — 조직도**

```
┌──────── 조직도 ────────┐        ┌──── 조직도 (임시 표시) ────┐
│ ▣ 한빛초등학교     │        │ ⚠ 조직도 설정을 받지 못해   │
│  ▸ 교무실              │        │   등록 순서로 표시합니다.   │
│  ▾ 교육정보실           │        │ ● 김철수 (kim)             │
│     ● 이영희            │        │ ○ 이영희 (lee)             │
│     ○ 박민수            │        │ ○ 박민수 (park)            │
│  ▸ 행정실              │        │                           │
│  ▸ 미배치              │        │                           │
└────────────────────────┘        └───────────────────────────┘
       ORG_OK를 받았을 때                  ORG_NONE·시간 초과일 때
```

- `JTree`로 부서 트리를 그린다. 이름 앞에 온라인(●)/오프라인(○)을 표시하고, `PRESENCE`를 받으면 해당 사용자만 갱신한다.
- 임시 표시일 때는 위쪽에 안내 문구를 보여 준다.

**메시지 관리함 — 받은 메시지 / 보낸 메시지 탭**

- 받은 메시지: 안 읽은 메시지는 굵게 표시한다.
- 보낸 메시지: 받는 사람이 여러 명이어도 **메시지 하나당 한 줄**만 표시한다. 목록에는 읽음 요약을 보여 준다.

```
┌ 받는 사람        ┬ 날짜/시간        ┬ 읽음 ┐
│ 이영희 외 2명    │ 2026-11-12 15:30 │ 1/3  │
│ 김철수           │ 2026-11-12 14:02 │ 1/1  │
└──────────────────┴──────────────────┴──────┘
```

**보낸 메시지 보기 — 본문 아래 읽음 확인**

```
┌──────────────────────────────────────────┐
│ 받는 사람: 이영희, 박민수, 최지훈          │
│ 보낸 시각: 2026-11-12 15:30               │
├──────────────────────────────────────────┤
│ 안녕하세요. 회의 자료 공유드립니다.        │
│ 📎 회의자료.pdf (200KB)                   │
├──────── 읽음 확인 (1/3) ── [새로고침] ─────┤
│ ✔ 이영희   읽음      2026-11-12 15:42     │
│ ☐ 박민수   안 읽음                         │
│ ☐ 최지훈   전송됨 (아직 받지 않음)          │
└──────────────────────────────────────────┘
```

- 서버에는 메시지 파일이 하나뿐이고, 받는 사람별 상태는 그 안에 `delivered.{아이디}`, `readAt.{아이디}`로 기록되어 있다(3.2). 그래서 보낸 내역도 자연스럽게 메시지 하나당 한 줄이 된다.
- 화면을 열 때 `STATUS`로 최신 상태를 조회하고, 열려 있는 동안 `RECEIPT`가 오면 해당 줄만 갱신한다. **[새로고침]**은 `STATUS`를 다시 보낸다.
- 받는 사람 순서는 보낼 때 고른 순서(`receivers` 순서)를 따른다.
- 서버의 보관 기간(90일)이 지나 `STATUS_FAIL`을 받으면, 마지막으로 저장해 둔 상태를 보여 주고 "더 이상 갱신되지 않음"을 표시한다.

**메시지 작성 화면 — 회신할 때**

```
┌──────────────── 메시지 작성 ────────────────┐
│ 받는 사람 [ 김철수 ×                       ] │
│ 참    조 [                               ] │
│ ☐ 나에게 보내기                              │
│ [글꼴크기▾] [색▾] [B]                        │
├─────────────────────────────────────────────┤
│ (커서) ← 여기에 회신 내용을 입력              │
│                                             │
│ ──────────── 원본 메시지 ────────────         │
│ 보낸 사람: 김철수                             │
│ 보낸 시각: 2026-11-12 15:30                   │
│                                             │
│ 안녕하세요. 회의 자료 공유드립니다.            │
│ (원본 본문 전체)                              │
├─────────────────────────────────────────────┤
│ [파일 첨부]                        [보내기]   │
└─────────────────────────────────────────────┘
```

- 작성 창이 열리면 커서를 맨 위 입력 공간에 둔다.
- 구분선, 원본 작성자·시각, 원본 본문은 회신 본문 HTML에 그대로 들어간다. 원본 본문은 서식(글자 크기·색)을 유지한다.
- 전달할 때는 원본 정보에 `받는 사람:` 줄이 추가되고, 원본 첨부파일이 첨부 목록에 만료일과 함께 표시된다.

**받은 메시지 보기 — 버튼**

- [회신] [전체회신] [전달] [삭제] [닫기]

(받은 메시지 보기의 나머지 화면 구성은 작성 예정)

## 5. 구현 전 세부 결정 (2026-11-13)

구조 검토에서 찾은 "문서에 답이 없던 것"을 구현 전에 정했다. U11~U13은 Common을 구현하면서 추가했다. 구현할 때 이 표에 없는 동작이 필요하면, 임의로 채우지 말고 이 표에 추가한 뒤 진행한다.

| # | 정한 것 | 결정 | 이유 | 반영한 곳 |
|---|---|---|---|---|
| U1 | 헤더 세부 규칙 | **엄격하게**: `\n`만, 첫 `=`에서만 나눔, 같은 키 중복은 형식 오류, 값에 줄바꿈이 있으면 쓰기 전에 예외 | 형식 오류를 받아 주면 버그가 조용히 넘어간다. 문제가 생긴 그 자리에서 드러나게 한다 | 2.1 |

| U8 | [서버 중지]의 의미 | **모든 연결을 끊고 새 접속 거부**. 데이터 유지, 같은 포트로 바로 다시 시작 가능 | 동작이 단순하고 예측 가능하다. "중지인데 메시지가 오가는" 애매한 상태가 없다 | 3.5, 3.7 |

| U10 | 응답이 오지 않는 요청 | 요청마다 **10초 제한** 후 실패 처리, `reqId` 없는 `ERROR`는 로그만 | "보내는 중…" 화면이 영원히 남지 않는다. 보내기는 같은 `messageId`로 다시 보내면 서버가 중복을 거른다 | 2.8, 2.9, 3.7, 4.1 |

| U12 | 형식 오류를 나타내는 예외 | `FormatException` 하나 (`IOException`의 하위 클래스, 검사 예외) | 패킷·파일·시각 형식 오류를 같은 방식으로 처리한다. 검사 예외라서 부르는 쪽이 처리를 빠뜨리면 컴파일 오류가 난다 | 1.2 |
