## 2026-11-12 (3)

### 한 일

### 관찰한 내용 (실제 학교 메신저)
- 보낸 사람의 보낸 내역, 받는 사람의 받은 내역에는 **본문만** 보인다.
- 첨부파일은 서버의 파일 자원을 가리키는 **다운로드 링크**로 표시된다.
- 1달이 지난 첨부파일은 '만료'가 뜬다. 본문은 그보다 오래 남는다.
- 사용자가 PC에서 정리하면 메시지가 지워진다. → PC의 로컬 보관함에 저장되는 것으로 보인다.

### 결정 사항
- **메시지를 본문과 첨부파일로 나누어 보관·전달한다.**
  - 본문: 서버에 저장 → 수신자가 접속하면 자동으로 전달 → 양쪽 PC의 로컬 보관함(보낸 내역/받은 내역)에 저장
  - 첨부파일: 서버에만 30일 보관, 사용자가 링크를 누를 때 내려받음
  - 이유: 큰 첨부파일 때문에 메시지 알림이 늦어지지 않게 하고, 서버 저장 공간을 관리하기 위해서다.
- **수신 확인(ACK)을 받은 뒤에 '전달 완료'로 표시한다.**
  - 이유: 서버가 보내는 도중 연결이 끊기면 메시지가 유실될 수 있다. ACK를 못 받으면 다음 접속 때 다시 보내고, 클라이언트는 메시지 ID로 중복을 거른다.
- 우선순위: 텍스트 메시지 송수신과 로컬 보관함(상) → 첨부파일·서식 있는 본문(중) → 본문 속 이미지(하)

- 통신 프로토콜 설계 (설계서 v0.4, 2장)

### 결정 사항
- **패킷 = [헤더 길이][헤더][데이터 길이][데이터]**, `DataInputStream`/`DataOutputStream` 사용
  - 이유: 줄 단위(`readLine`)로 주고받으면 본문 속 줄바꿈과 첨부파일 바이너리를 처리할 수 없다. 길이를 먼저 보내면 둘 다 같은 방식으로 처리된다.
  - 헤더는 메시지 파일과 같은 `키=값` 형식이라 파일 저장 코드와 통신 코드가 같은 방식을 쓴다.
- **요청에 `reqId`를 붙이고, 클라이언트는 수신 전용 스레드 하나로 모든 패킷을 받는다.**
  - 이유: 서버가 새 메시지(`MSG`)를 언제든 보내므로, 요청의 응답보다 `MSG`가 먼저 올 수 있다.
- **`messageId`는 클라이언트가, `sentAt`은 서버가 만든다.**
  - 이유: 클라이언트가 ID를 정해야 재전송 시 서버가 중복을 거를 수 있고, 시각은 PC마다 시계가 다르므로 서버 기준으로 통일한다.
- 같은 아이디로 다시 로그인하면 기존 연결을 끊는다. 포트는 9000.

## 2026-11-12 (6)

### 한 일
- 프로토콜에 서버 연결 테스트, 접속 상태, 수신·읽음 확인 추가 (설계서 v0.5, 요구사항분석서 v0.4)
- 로그인 화면, 연결 테스트 창, 메인 화면(조직도 + 받은/보낸 내역) 화면 구성 초안

### 결정 사항
- **연결 테스트는 `PING`/`PONG`으로, 로그인 전에도 허용한다.**
  - 첫 화면에서 서버 IP만 입력하고 연결되는지 확인할 수 있어야 하기 때문이다. `PONG`에 프로토콜 버전을 넣어 서버와 클라이언트 버전이 맞는지도 확인한다.
- **접속 상태는 서버가 바뀔 때만 알리고(`PRESENCE`), 클라이언트는 30초마다 하트비트(`PING`)만 보낸다.**
  - 처음에는 클라이언트가 20~30초마다 상태를 보내는 방식을 생각했다. 하지만 서버는 소켓 연결로 누가 접속 중인지 이미 알고 있으므로, 상태를 물어보거나 주기적으로 보낼 필요 없이 바뀔 때만 알리면 된다.
  - 다만 PC 강제 종료나 랜선 분리는 TCP가 바로 알아채지 못하므로, 클라이언트의 주기적 신호는 '살아 있음' 확인용으로 쓴다. 90초 동안 아무 패킷도 없으면 끊긴 것으로 본다.
- **`ACK`(수신 확인)와 `READ`(읽음 확인)를 나눈다.**
  - 처음에는 읽음 처리할 때 `ACK`를 보내는 방식을 생각했다. 하지만 `ACK`는 서버가 메시지를 다시 보낼지 판단하는 기준이라, 읽을 때 보내면 받았지만 안 읽은 메시지가 로그인할 때마다 다시 전송된다.
  - 그래서 상태를 전송됨(`SENT`) → 안 읽음(`DELIVERED`, 자동 `ACK`) → 읽음(`READ`) 세 단계로 나누었다.
  - 보낸 사람이 접속 중이면 `RECEIPT`로 바로 알리고, 오프라인이었다면 보낸 내역에서 메시지를 열 때 `STATUS`로 조회한다.

### 한 일

### 결정 사항
- **보낸 메시지는 받는 사람 수와 관계없이 보낸 내역에 한 줄로 표시하고, 본문 아래에 받는 사람별 읽음 확인을 체크로 보여 준다.**
  - 서버의 메시지 파일이 원래 하나이고 받는 사람별 상태(`delivered.{아이디}`, `readAt.{아이디}`)를 그 안에 기록하므로, 지금 구조에 그대로 맞는다.
  - 목록에는 `1/3`처럼 읽은 사람 수만 요약한다.
- **조직도는 서버의 설정 파일(`org.txt`)을 따르고, 설정을 받지 못하면 `users.txt` 등록 순서대로 임시 표시한다.**
  - 형식은 `D|부서경로`, `U|부서경로|아이디` 줄 단위로 정했다. 들여쓰기 방식보다 `split("\\|")`만으로 읽을 수 있어 구현이 쉽다.
  - 조직도 설정이 잘못되어도 메신저는 써야 하므로, 서버는 설정 없이도 동작하고 클라이언트는 등록 순서로 대체한다.
  - 설정에 빠진 사용자는 '미지정' 부서에 넣어 아무도 조직도에서 사라지지 않게 한다.
  - 등록 순서를 지키려면 서버가 사용자 목록을 `ArrayList`/`LinkedHashMap`으로 들고 있어야 한다(`HashMap`은 순서가 섞임).

- **첨부파일에 접근 권한(`access` 목록)을 추가한다.**

  - 그래서 파일이 첨부된 메시지의 보낸 사람·받는 사람·참조 대상만 받거나 전달할 수 있게 하고, 그 외에는 `FILE_DENIED`로 거부한다.
- **파일 전송 취소는 연결을 끊고 다시 로그인하는 방식으로 한다.**
  - 길이를 먼저 보내는 패킷 구조에서는 데이터 중간에 멈추면 받는 쪽이 다음 패킷의 시작을 찾을 수 없기 때문이다.

- **로그인 방식을 '아이디만'에서 '아이디 + 비밀번호'로 바꾼다.** (2026-11-12 결정 변경)
  - 서버에 관리 화면을 두면서 관리자가 사용자를 등록할 때 비밀번호도 함께 정할 수 있게 되었다. 다른 사람 아이디로 접속할 수 있던 한계도 함께 해결된다.
- **사용자 등록은 관리자만 한다.** 서버 관리 화면의 표(DB 목록처럼 보이는 `JTable`)에서 이름·아이디·비밀번호를 입력해 저장한다. 사내 메신저처럼 사용자가 스스로 가입하지 않는다.

- **비밀번호는 원문 대신 솔트 + PBKDF2 해시로 저장한다.**

  - `admin.txt`는 Git에 올리지 않는다.
- **소속 부서는 `users.txt`에서 빼고 조직도(`org.txt`)에만 둔다.** 같은 정보를 두 곳에 두면 한쪽만 고쳐 어긋나기 쉽다.
- **조직도를 관리 화면에서 저장하면 서버 재시작 없이 즉시 반영한다.** (기존: 서버 시작 때만 읽음)

### 문제와 해결
- Python으로 만든 예시 비밀번호 해시를 Java `PasswordHasher`가 검증하는지 확인했다. 두 언어 모두 PBKDF2-HMAC-SHA256과 UTF-8을 써서 결과가 같다.
- 화면 없이 확인하는 검사 코드로 12개 항목(사용자 4명 읽기, 등록 순서, 한글 이름, 비밀번호 일치·불일치, 관리자 비밀번호 저장·재확인, 파일에 원문 없음, 형식 오류 줄 건너뛰기)을 확인했다. GUI 창 자체는 직접 실행해 확인해야 한다.

- **U12 형식 오류는 `FormatException` 하나로.** `IOException`의 하위 클래스라서 파일·통신 오류와 같은 방식으로 처리된다.

### 구현하면서 배운 점
- `new String(bytes, UTF_8)`은 깨진 UTF-8을 `?`로 **조용히 바꿔 버린다.** 오류를 숨기지 않으려고 `CharsetDecoder`에 `REPORT`를 걸어 형식 오류로 처리했다.
- `DateTimeFormatter`에서 `yyyy`는 "연호 기준 연도"라서 엄격 모드(`STRICT`)에서는 읽기가 실패한다. `uuuu`를 써야 하고, 엄격 모드여야 2월 30일 같은 없는 날짜를 3월 2일로 바꾸지 않고 오류로 본다.
- 모르는 종류의 패킷은 예외로 처리하지 않고 그대로 돌려준다. 그래야 서버가 연결을 끊지 않고 `ERROR`로 응답할 수 있다. 반면 길이가 틀린 패킷은 이후 바이트 위치가 모두 어긋나므로 연결을 닫아야 한다. 두 경우를 구분하는 것이 핵심이었다.

- `switch`와 enum: enum을 쓴다고 자동으로 `switch`가 되는 것은 아니다. enum으로 `switch`하면 오타와 처리 누락을 컴파일러가 잡아 준다. 여기서 `if-else`와의 속도 차이는 네트워크 지연(밀리초)에 비해 무시할 만하다.
- 시간 복잡도: 패킷 해석은 O(패킷 크기), 헤더에서 키로 찾기는 O(1)(`HashMap`), 종류별 분기는 O(1). 실제 비용은 처리 함수 안에서 생긴다. 특히 로그인 때 밀린 메시지를 찾으려면 메시지 파일을 모두 훑어야 해서 O(전체 메시지 수)가 된다.

- DBMS를 쓰지 않은 이유: 과제가 파일 입출력을 요구하고, 외부 jar는 "README만 보고 실행" 조건에서 실패 위험이 있다. 대신 DB가 해 주던 일(트랜잭션 → `AtomicFile`, 행 잠금 → 메시지 ID별 잠금, 인덱스 → 사용자별 대기 파일)을 직접 구현하며 그 필요성을 체감하는 프로젝트가 되었다.

- U33을 정하기 전에 **"나중에 트레이로 바꾸는 비용"**을 먼저 검토했다. 트레이 코드 자체는 100~150줄로 작지만, 진짜 병목은 "창 닫기"와 "프로그램 종료"가 갈라지는 생명주기였다. 그래서 지금은 기능을 넣지 않되, 바꿀 지점을 한 곳으로 모아 두는 것으로 대비했다.

### 문제와 해결
- **의도한 동작 변경으로 깨진 테스트**: U30으로 서버 중지 시 `BYE`를 먼저 보내게 되자, 2단계 테스트 "서버 중지 → 바로 EOF"가 실패했다. 버그가 아니라 **결정이 바뀌어 기대값이 바뀐 것**이라 테스트를 "BYE → EOF"로 고쳤다. 테스트가 깨졌을 때 "코드가 틀렸나, 기대가 바뀌었나"를 먼저 구분해야 한다.
- **BYE가 전달되지 않을 수 있는 문제**: 원래 연결을 닫으면 보내기 대기열을 비우고 바로 소켓을 닫았다. 그러면 마지막에 넣은 `BYE`가 사라진다. 그래서 `SendQueue.finish()`(이미 넣은 것은 끝까지 보내고 멈춤)를 추가하고, 끊기는 최대 2초 기다린 뒤 닫도록 했다. 서버 관리 화면을 닫을 때도 `BYE`가 전달될 시간(최대 3초)을 준 뒤 종료한다.
- **안전 장치에 막힘**: 테스트 빌드 폴더를 지우려던 명령이 "변수가 비면 전체를 지울 수 있다"는 이유로 차단됐다. 지우지 않고 새 폴더에 빌드하는 방식으로 바꿨다.

### 구현하면서 배운 점
- **C3를 코드로**: `byUser.get(userId) == session`일 때만 지운다. 아이디만으로 지우면, 늦게 실행된 옛 연결의 정리 코드가 방금 로그인한 새 연결을 지운다. 테스트로 "옛 연결이 닫힌 뒤에도 kim은 접속 중"을 확인했다.
- **C5를 코드로**: 로그인 등록과 `LOGIN_OK`의 접속자 목록 만들기를 `synchronized` 블록 하나 안에서 한다. 화면 알림은 잠금을 푼 뒤에 보낸다(잠금 안에서 다른 일을 하지 않기).
- **대기표(`CompletableFuture`)**: 요청마다 `reqId`로 대기표를 만들고, 받기 스레드가 같은 `reqId`의 응답을 받으면 채운다. `orTimeout`으로 10초 제한을 걸었다. 서버가 먼저 보내는 패킷은 대기표가 없으므로 Listener로 넘긴다.
- **우리가 닫은 끊김과 서버 쪽 끊김 구분**: 로그아웃 때 "서버와 연결이 끊겼습니다"가 뜨면 이상하다. `AtomicBoolean`으로 "먼저 닫은 쪽"을 기록해, 우리가 닫은 경우에는 알리지 않는다.

- **작성 창**: 받는 사람·참조 두 칸(같은 조직도 선택 창, 한 사람은 한 칸에만), 회신·전체회신이면 받는 사람·참조·인용이 채워져 열림(커서는 맨 위, 인용도 고칠 수 있음), `replyTo` 기록.
- **관리함**: 받은 메시지 탭에 [회신] [전체회신].
- [나에게 보내기]·[파일 첨부]·[전달]은 만들지 않음(보류).
- 테스트: Common 96, 서버 206, 클라이언트 105 — 모두 통과.

### 구현 중 찾은 문제 (U62)
- **한글이 숫자 참조로 저장**: Swing의 HTML 출력은 한글을 `&#44032;`로 쓴다. 본문이 몇 배로 커지고 목록 미리보기에 숫자가 보였다. 보낼 때 글자로 되돌리되, `&lt;`처럼 HTML에서 뜻이 있는 문자는 그대로 둔다.
- **글꼴 이름이 사라짐**: `FontFamilyAction`으로 글꼴을 바꾸면 HTML에 `face=""`가 나왔다. 글자의 속성을 찍어 보니 CSS 글꼴 값 자체가 빈 문자열이었다(JDK의 변환 문제). CSS 속성을 문자열로 직접 넣어 해결했다.

### 배운 점
- **"동작한다"와 "저장된 결과가 맞다"는 다르다.** 편집기 화면에서는 글꼴도 한글도 정상으로 보였다. 출력된 HTML을 직접 찍어 보고서야 두 문제를 찾았다. 서식 같은 기능은 화면이 아니라 **실제로 전송되는 데이터**를 검사해야 한다.
- **원인이 라이브러리일 때도 "어디서 사라지는가"를 좁혀 간다.** 출력(HTMLWriter) → 문서 속성(CSS$FontFamily) 순서로 내려가 값이 비는 지점을 찾았고, 그 단계만 우회했다.
- **테스트 통로는 테스트 폴더에.** 같은 패키지의 메서드를 테스트에서 부르려고 만든 통로 클래스를 처음에 `src`에 뒀다가, 같은 패키지 이름의 `test` 폴더로 옮겼다(제출물에 테스트 코드가 섞이지 않게).

## 2026-11-16 (16) — 버그 수정: 새 메시지의 줄바꿈이 띄어쓰기로, 회신 가로줄 제거

- **증상**: 서식은 적용되는데, 처음 쓰는 메시지에서 Enter로 바꾼 줄이 받는 쪽에서 띄어쓰기로 보였다. 회신은 괜찮았다.
- **원인**: 편집기 HTML을 찍어 보니 새 메시지는 `첫줄\n둘째줄`처럼 문단 없이 줄바꿈 문자만 들어가 있었다. HTML에서 줄바꿈 문자는 띄어쓰기다. 회신은 인용(`<p>`)으로 시작해서 Enter가 문단을 나눴기 때문에 정상이었다.
- **수정**: 빈 본문도 빈 문단으로 시작한다. 그러면 Swing 기본 문단 여백이 생기므로 편집기와 받은 메시지 표시 모두 문단 여백을 0으로 맞췄다.
- **변경**: 회신 인용의 가로줄은 요청대로 뺐다(보낸 사람·시각은 회색 글자로 남김).
- **배운 점**: "회신은 되는데 새 메시지는 안 된다"처럼 **같은 기능이 조건에 따라 다르게 동작하면, 두 조건의 시작 상태 차이**를 먼저 본다. 여기서는 "문단이 있느냐"였다.
- 기록: 설계서 v0.32(4.3, 2.11, U62 ③), 테스트기록 9.4. 클라이언트 테스트 107개 통과.

## 2026-11-16 (17) — 개념 정리: 패킷이라는 용어, 프레이밍, 서버 실행 방식

- 질문에서 정리한 개념을 설계서 2.1 "용어"로 남겼다(v0.33).
  - **왜 길이 + key=value인가**: TCP는 바이트를 순서대로 전달할 뿐 메시지 경계를 지켜 주지 않는다(잘리거나 붙어서 옴). "0101로 바꾸기"(인코딩)만으로는 어디까지가 무엇인지 알 수 없어 칸막이(길이, 이름표)가 필요하다.
  - **"패킷"이라는 이름**: 교과서에서는 IP 계층의 단위. 우리 것은 응용 계층 메시지이고, 방식은 길이 접두사 프레이밍. 코드 이름은 관례대로 두고 문서에서 뜻을 밝힘.
  - **서버 실행**: IIS·Tomcat 같은 웹 서버/WAS가 아니라 스스로 포트를 여는 독립 소켓 서버. 자바만 있으면 실행되지만, 관리 화면이 Swing이라 화면 없는 리눅스 서버에서는 "화면 없는 실행 모드"가 필요(제출 후 확장 후보).
